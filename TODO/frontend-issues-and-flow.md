# 前端问题记录与用户介入流程

记录日期：2026-10-12。来源：用户实际使用反馈及静态告警列表截图。状态：UI-01～UI-03 待规划与实现；UI-04 已实现。

首次反馈只记录问题和流程表；随后按用户逐步测试反馈，实现 UI-04 的补充规则区域默认展开和状态提示。实现以 `design/` 中的功能和模块边界为依据；本表结合当前四阶段链路列出交互和展示要求，不表示这些要求已全部实现。

## 已记录的界面问题

| 编号 | 问题 | 用户受到的影响 | 改造方向 |
| --- | --- | --- | --- |
| UI-01 | 功能、操作入口和可选项过多，操作逻辑混乱 | 难以判断当前应该做什么、哪些设置必须填写 | 主界面只展示当前阶段的目标、结果和主要操作；使用明确默认值，将低频配置折叠到高级设置 |
| UI-02 | CodeQL 静态告警未选中时缺少明显背景框 | 看起来像普通文字，不知道每一项可以点击查看 | 每个告警在未点击时就显示比页面背景略深的矩形区域，选中、悬停和键盘聚焦状态进一步区分 |
| UI-03 | LLM 初审进度及发现情况不直观 | 不知道是否正在分析、检查到了哪里、已经发现了什么 | 在发现阶段并列展示 CodeQL 与 LLM 初审的状态、进展、候选和覆盖限制，不要求用户切到复核页或展开 JSON 才能了解状态 |
| UI-04 | 新建审计的补充规则区域默认收起，空列表的原因不清楚 | 需要额外点击，不知道没有规则版本是否正常 | 已实现：默认展开；区分加载、读取失败和空列表，说明无补充规则仍会执行内置扫描和 AI 初审 |
| UI-05 | 模型调用失败缺少明确的重试策略 | 临时服务异常可能中断分析 | 待实现：失败后最多重试 3 次，分别等待 2s、4s、8s，并保留每次尝试记录 |
| UI-06 | 模型漏洞简报的标题和说明大量使用英文 | 阅读候选和问题依据不方便 | 待实现：调整并版本化提示词，除关键词、标识符和源码引用外，尽量使用中文 |

### UI-05：模型调用失败重试（待实现，2026-10-12）

- [ ] 首次调用失败后重试最多 3 次，等待间隔依次为 2s、4s、8s；最多 4 次调用尝试。
- [ ] 保留原始任务与输入，记录每次失败、等待、重试及最终状态；重试耗尽仍明确报告失败，并保留已保存候选。
- [ ] 区分可重试的临时调用失败与预算耗尽、取消和证据校验失败。截图中的 `model_budget_exhausted` 是阶段调用预算耗尽，不能靠无限重试绕过预算；预算策略需单独处理。

### UI-06：漏洞简报中文输出（待实现，2026-10-12）

- [ ] 调整初审及复核相关提示词，要求候选标题、问题描述、风险、缺失前提及简报正文尽量使用中文。
- [ ] 保留必要关键词，例如 CodeQL、Flask、CWE 编号、API / 函数名、文件路径；源码证据和原文引用保持原样。
- [ ] 新增提示词版本并保留历史版本和执行快照，中文表达不得改变证据含义，不把初审候选写成已确认漏洞。

以上两项本次仅记录，待后续实现。

### UI-04：新建审计与补充规则（已实现）

测试反馈：源码包上传和可选项目名称符合预期；补充规则区域应默认展开，空列表需要说明原因。

- [x] 补充已发布规则区域默认展开，最多选择 4 个版本。
- [x] 加载中与读取失败分别提示，不将接口失败显示为没有可选规则。
- [x] 空列表说明不影响内置 CodeQL 扫描和 AI 初审，并提示规则发布后可选。

2026-10-12 核对：当前本地工作区规则版本数量为 0，因此列表为空正常。此处仅列出本工作区、与所选语言匹配且状态为 `published` 的版本；知识库范例和内置 CodeQL 标准规则不属于补充规则列表。生成规则并完成验收、发布后，对应语言的版本才会出现。

### UI-01：收敛操作逻辑

- [ ] 明确正常使用主线：上传 → 双引擎发现 → 复核与人工判断 → 按需修复 / 生成规则。
- [ ] 每个阶段突出一个主要下一步；必须先做的操作直接说明，不堆叠多个同等权重的按钮。
- [ ] 将模型预算、检索策略、查询包版本、自定义范围等低频设置放到高级区域，提供可解释的默认值。
- [ ] 操作不可用时显示具体原因，例如“请先确认缺陷”“尚未选择验收测试集”。
- [ ] 原始日志、调用记录与 JSON 放在执行详情中；正文优先展示状态、结果和证据。
- [ ] 修复与规则生成可分支执行或跳过，报告不要求等到两者都完成。

### UI-02：静态告警列表的可点击性

- [ ] 未选中告警也具有完整矩形背景、统一间距和可辨识的点击区域。
- [ ] 选中状态比未选中状态更明确，能够看出右侧 / 下方正在展示哪条告警。
- [ ] 提供悬停反馈和清晰的键盘聚焦状态，整条告警支持键盘访问。
- [ ] 保留规则名称、文件路径和行号，长路径可读，正常状态不依赖悬停才显现。
- [ ] 浅色和深色主题中都可区分背景；同时使用边框或选中标记表达状态。

截图中的 `py/template-injection · app.py:205` 只有选中后才明显呈现矩形区域，其他未选中条目近似普通文字。后续验收应检查没有任何选中项时的列表，而不只检查点击后的样式。

### UI-03：LLM 初审进展与发现

- [ ] 在同一个发现页面并列展示 CodeQL 和 LLM 初审；任一分支完成都不能隐藏另一分支的执行状态。
- [ ] LLM 状态覆盖排队、项目梳理、分析中、完成、部分完成、失败和取消。
- [ ] 展示已处理 / 计划检查单元、当前模块或文件、最近动作与更新时间；尚无可靠分母时使用明确阶段和计数，不伪造百分比。
- [ ] 将已处理单元、实际检查范围和未检查范围分开；计划窗口处理完成不代表整个项目已检查。
- [ ] 动态展示已持久化的 AI 候选数量与可查看的候选列表，包含标题、位置、问题类别及证据摘要。
- [ ] 候选明确标注“待复核 / 待确认”；不把初审输出直接计为已确认漏洞，也不把模型给出的高置信度当作人工确认。
- [ ] 显示停止原因：正常完成、调用 / 时间 / token 预算耗尽、上下文限制、模型错误或用户取消。
- [ ] 失败、取消或部分完成时，保留已经保存的候选和证据，说明可用结果及覆盖限制。
- [ ] 若没有发现候选，区分“尚未产出”“已检查范围未发现候选”和“初审失败”，避免统一显示零漏洞。

## 用户介入与进展展示表

“必要人工”指继续相应分支必须作出的判断；其他节点通常自动执行，不要求用户逐步批准。CodeQL 与 LLM 初审并行，修复与规则生成从审计结果分支，报告可以提前生成。

| 节点 | 用户可以在哪些地方介入 | 需要展示给用户的进展和数据 |
| --- | --- | --- |
| 1. 上传与范围确认 | 上传 ZIP、确认项目及所选语言；按需选已发布补充规则；启动审计 | 文件解析状态、识别的语言与文件范围、未扫描范围、环境是否可用；源码快照和工具版本在详情中查看 |
| 2A. CodeQL 静态分析 | 查看告警与代码路径、取消执行、失败后创建重试任务；无需逐条批准查询 | 排队 / 建库 / 查询 / 解析状态、已运行耗时、告警数量、可点击告警、源码与路径证据、失败原因 |
| 2B. LLM 独立初审 | 查看进展和逐步保存的候选，按需取消或补充重跑；无需逐文件确认 | 当前检查步骤和范围、已处理 / 计划单元、候选数量及位置、证据摘要、未检查范围、预算停止或错误原因 |
| 3. 双引擎结果汇总 | 查看两个来源的结果与覆盖限制，进入统一复核 | 两个分支各自的状态、静态告警与 AI 候选分项统计、可用与缺失结果；部分完成明确标注 |
| 4. LLM 统一复核 | 启动复核、调整范围或补充业务背景，按需取消 / 重跑 | 已复核 / 待复核候选、当前对象、模型支持 / 排除 / 未决判断、源码引用、已检查前提、反证及未知信息 |
| 5. 人工判断候选（必要人工） | 确认、排除或保持待定；填写依据、选择真实证据，审阅根因关联建议 | 候选来源、代码与证据、模型判断、人工判断分别展示；待判断 / 已确认 / 已排除数量及判断历史 |
| 6. 选择修复目标与业务要求 | 勾选已确认缺陷、说明需保留的正常行为，必要时限定修改范围 | 修复目标、关联文件、业务前提、未知条件、可否启动修复及阻断原因 |
| 7. 准备项目验收测试 | 生成或导入测试、审阅断言、选择固定测试集与项目验证镜像 | 测试生成进展、安全用例和正常功能用例、目标覆盖、依赖与镜像要求、测试集版本及待核实条件 |
| 8. 生成补丁与自动检查 | 查看 Diff、尝试历史及失败诊断，按需取消 / 重跑 | 项目理解、修改文件、补丁生成 / 应用 / 检查状态、当前尝试次数、语法 / 项目测试 / CodeQL 复扫结果、验证限制 |
| 9. 原代码与补丁对比验收 | 选择固定测试集并启动前后验证，审阅测试断言和结果 | 原代码漏洞是否可复现、补丁是否阻断、正常功能是否保持、两轮执行是否一致、未执行检查及证据引用 |
| 10. 接受修复交付（必要人工） | 在验收门通过后填写依据并接受补丁、下载 Diff | 通过与未通过的验收项、最终 Diff、人工接受记录；明确原始快照保留，下载后由用户应用到自己的项目 |
| 11. 审计报告 | 按需生成 / 更新、核对并导出，不要求修复和规则分支都完成 | 生成状态、静态与 AI 发现、人工确认、覆盖限制、修复 / 验收状态、报告是否与最新结果一致 |
| 12. 确认规则目标 | 选择已确认缺陷或明确需求、确认规则用途，必要时补充源码范围及独立验收集 | 目标问题、目标语言、已有覆盖与缺口、用途及验收要求；区分漏洞检测、复审锚点和框架建模 |
| 13. RAG 检索与规则生成 | 查看检索依据和草稿；材料不足时补充匹配版本知识后重跑，通常无需逐条批准检索 | 检索 / 生成 / 编译反馈状态、实际引用的参考资料与范例、版本匹配、规则源码、尝试次数和失败原因 |
| 14. 批准规则正反例（必要人工） | 检查正例确有目标问题、反例确实安全，填写批准依据或保留草稿 | 正反例代码、预期检测位置、区分依据、待批准状态、批准记录及恢复执行状态 |
| 15. 规则综合验收与原项目确认 | 查看样例、独立验收和原项目执行结果；必要时确认原项目命中是否对应同一根因 | 编译、正例命中、反例误报、独立验收、原项目结果分别展示；命中代码、根因证据、未评估项及阻断发布的原因 |
| 16. 发布与复用规则（必要人工） | 验收满足条件后发布；后续上传项目时明确选用；按需停用 | 规则版本、用途、验收范围、发布状态、来源项目及启用范围；发布不等于自动加入所有默认扫描 |

规则的编译与原项目试跑可能在生成反馈期间提前执行；表中将其归入统一验收展示，不能据此把后台图改成不必要的串行流程。用户对原项目根因的确认只在验收需要时介入，并非每条规则都必然有同一审批项。

## 页面信息层级

1. 默认显示：当前状态、已得到的结果、覆盖限制、需要用户处理的事项、主要下一步。
2. 点开某条结果：代码位置、实际证据、判断依据、历史记录。
3. 高级详情：工具与知识版本、预算、调用统计、原始日志、JSON 和产物下载。

所有后台阶段都应显示执行中 / 等待人工 / 成功 / 部分完成 / 失败 / 取消、最近更新时间、耗时及下一步。无法可靠估算整体进度时展示步骤和工作量，不把 token 消耗比例当作审计完成比例。

用户应能取消活动执行、在允许状态下新建重跑并查看历史。取消与暂停 / 恢复不是同一功能，不能把当前取消入口描述为可任意断点续跑。失败、未评估和等待模型结果都不得伪装成成功的空结果。

## 数据与实现核对

- 双引擎入口：`system/backend/app/workflows/dual_scanning.py` 与 `services/dual_scanning.py`，两个分支并行后汇合。
- 初审过程中会逐检查单元保存 `StageRun.result.units` 及候选，最终汇总覆盖；当前不存在可直接解释为全项目审计百分比的统一字段。
- 当前 `DiscoveryCoverage.tsx` 位于 AI 页面，并主要通过展开 JSON 展示覆盖，需改为面向用户的进展摘要和候选视图。
- 当前 `RunDetails.tsx` 中未选中告警使用 `ghost` 按钮，后续样式应覆盖未选中状态。
- 修复接受需检查当前测试断言、前后结果和补丁一致性；语法通过不能代替修复验收。
- 规则样例批准为图中人工暂停点；发布还需实际验收门通过，不能简化为编译完成即发布。
- 实时更新应读取已持久化结果；新增展示数据需按检查单元保存，并绑定审计 / 阶段 ID，避免显示其他任务或旧执行的数据。

## 后续验收清单

- [ ] 首次进入阶段页面能立即知道当前状态、结果和主要下一步，正常主线无需遍历高级选项。
- [ ] 静态告警全部未选中时仍明显可点击，选中、悬停、键盘聚焦及两种主题状态可辨。
- [ ] CodeQL 先完成而 LLM 仍执行时，页面持续展示 LLM 的真实状态和已保存候选。
- [ ] LLM 失败或预算耗尽时，已经保存的发现仍可查看，未检查范围与停止原因可见。
- [ ] 正常零候选、尚未产出、读取失败与部分完成能够明确区分。
- [ ] 模型判断与人工确认分别计数、分别展示；初审候选不直接计入已确认漏洞。
- [ ] 用户等待点与审批原因清晰，门禁未满足时解释具体缺项，而不提供无效的主要操作。
- [ ] 不要求用户审批每次模型或工具调用；高级能力可保留但不干扰正常使用主线。
- [ ] 重跑和刷新不会混用任务或阶段执行的进展、候选和历史。
