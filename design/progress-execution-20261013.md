# 按进展执行审计

2026-10-13。依据 RealVuln 日志诊断和用户授权，解除新初审/复核任务的保守总预算限制。四阶段边界不变，检测假设与证据确认保持分离。

## 执行配置

- `AI_AUDIT_EXECUTION_MODE=progress` 为新 Scout/Review 默认配置：冻结为 `max_calls=0, max_tokens=0, max_seconds=0`，其中 0 表示不设置阶段总量上限。保持每次请求超时、每个窗口/批次取证步数上限与结构恢复次数。
- `AI_AUDIT_EXECUTION_MODE=bounded` 恢复原 `AI_STAGE_MAX_CALLS/TOKENS/SECONDS` 上限。修复、规则和其他阶段继续使用有界预算。旧执行保留已有模型/提示/预算快照，不修改历史记录。
- `AI_STAGE_MAX_NO_PROGRESS=3`：连续三个窗口/批次没有有效调查产物即停止；带有结构化证据门拒绝记录的 partial 批次视为调查进展，不阻断其他候选，保留 `no_progress` 和未完成覆盖。不把未决判为误报。重复读取仍由现有只读工具防进展循环控制处理。
- 服务请求超时、连接失败、429 限流会中断并保留真实调用账本；429 单独记录 `rate_limited` 和服务提供的 `retry-after`，不会在限流期间持续重试。没有假设服务的 5 小时额度或复位时间。初审可从现有补审入口继续；复核可针对未完成候选创建新执行。
- 审计/扫描 Celery 任务取消全任务墙钟强杀，仍由模型请求、CodeQL 命令超时、局部步骤、进展检测和人工取消约束；避免后台强杀后只留下 running 状态。

## 计量与覆盖

token 仍按服务返回 usage 记录实际输入/输出；服务不返回 usage 时明确记录 unknown_usage_calls。原字节上界保留并标明方法，只在 bounded 模式充当保守限额，不再阻断 progress 模式。没有将估计 token 冒充实际用量。

新 ScoutRequest 的 `max_units=0`、ReviewRequest 的 `max_batches=0` 表示调度全部范围；显式非零值仍限制范围。不把大项目多个窗口压进一次模型请求，仍按局部窗口/批次处理。文件优先级修正：views.py、apis.py 作为入口导航，迁移文件独立分类且延后，但仍在完整范围内，不默认当作安全。

26 个 RealVuln 项目一直是独立 audit_id、独立快照、独立阶段、候选池和账本，运行器项目并发为 2。本次问题不是多个项目拼接或共享候选预算。真实模型运行后的覆盖仍须测量；调度全部窗口不等于所有任务都能成功取证。
