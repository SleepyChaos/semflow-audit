# Repair3：有进展的取证、范围保持与隔离候选

## 与现有系统的关系

Repair3 使用既有阶段 API、RepairService、LangGraph 修复图、EvidenceService、阶段持久化和隔离验证器。新阶段默认版本 3；历史版本和原阶段冻结的提示词、模型策略及预算保留。修复候选仍需既有比较验证和人工接受；模型一致性结论不替代执行证据。

## 输入及证据边界

- 确认候选的描述是修复诉求。以 `repair_request` 保存并可引用，但不能证明实际源码行为或安全性。理解必须有实际代码引用。
- 用户选择的验收套件需校验审计所属、目标覆盖、套件哈希和测试文件完整性。只向修复上下文提供需求及预期行为，不提供执行测试代码或任何隐藏基准资料。
- `repair_scope` 在初次理解、重新理解和应用中使用同一组授权可写文件。其他源文件只能作为当前目标的只读依赖或调用方，不能自行变成修复目标。
- 只读工具有显式参数契约，返回完整行分页、实际返回范围及 EOF；分页联合给出已覆盖和未读区间。重复请求不会新增读取预算，持续重复或无效请求会停止。
- 文档按需读取，不将未读文档默认为已检查。只有最终解释可成为受校验的语义事实，工具请求里的临时猜测不成为证据。
- 可写区间恰好为授权文件中已读源码区间的并集。不会因大文件重采样而丢失已读正文，也不会因文件较小而允许修改未读行。旧文本仍必须在原快照中唯一匹配。

## 运行预算

`progress` 模式保留调用及 token 用量，不以累计调用/token/耗时总量切断持续进展。取证次数、候选次数、重复停滞、结构纠正次数、单次模型超时和隔离命令超时仍有界。`bounded` 模式保留操作者配置的总量限额。

模型载荷默认优选 40,000 字符，Repair3 的源码驱动扩展硬上限默认 80,000 字符，可由操作者配置。仅实际提供的源代码推动扩展，非源码开销仍须在优选范围；不静默截断正文或事实。每次保存字段大小、实际上限、扩展原因及调用收据。字符数不是供应商计费 token 数，也不声明模型上下文容量。旧阶段缺少扩展字段时保持旧上限。

新阶段的本地调用预留依据有限图计划计算，默认 `(tool_limit + 4) * repair_attempts`，避免又被独立的 12 次上限切断。真实模型适配器冻结这些字段，脚本模型与生产入口共享机制；不能只在基准配置中关闭预算。

## 候选与理解的相互校验

语法/所选项目验证成功后，Repair3 进行代码证据关联的语义一致性检查：

1. 原确认诉求是授权来源；先检验模型解释本身是否扩大了范围。
2. 再检查候选是否符合原始诉求、读到的业务约束及合法调用行为。
3. Python 改动函数产生两层语法调用线索，每个位置提供实际读取的源码 ID，要求逐项判断保持、授权改变、冲突或未知。函数调用方文本未改变不能证明其行为未改变。
4. 调用线索最多提供八个窗口，明确报告遗漏；名称匹配不解析完整 Python 动态派发，不可据无匹配推断无调用方。
5. 每项必须引用该调用点自身的已读正文。未知不视为通过。

明确的实现冲突直接复用保存的评估作为反馈，不再付费请第二个模型重复解释。解释错误进入 `refresh_understanding`；关键不确定性保留未决并停止猜测。候选均从原始快照重新生成，保留每次失败、检查和 Diff。

一致性检查仍可能误判，不能把其通过写成安全/业务正确证明。有效性依赖真正执行的功能和安全验收，报告必须标明验证范围。

## 验证与报告口径

生产回归覆盖：真实 API 默认版本、真实 provider 的 Mock HTTP 计量与恢复、旧预算冻结、合法和非法源码区间、实际修复图对冲突/错误解释的不同反馈路线、任务/候选/套件隔离、真实源码引用、原始快照不变。

真实小测固定失败样本和正向控制，逐轮冻结。既不覆盖退化记录，也不按样本挑选最佳轮拼成成绩。模型生成、依赖准备、真实验证耗时分开。没有成功应用候选是修复失败，不因流程返回记录就归为成功或排除。

基准依赖上游新增函数/异常名称时，保留原始未通过。可另做三方公共接口行为探针（漏洞版、官方修复版、候选），但必须单列为开发验证，不改原始分数、不回流隐藏测试给模型。

## 已选择验收套件的候选反馈

当且仅当新Repair3阶段已明确选择冻结验收套件时，在准备阶段固定项目镜像摘要。候选语法检查通过后、模型一致性复审前，沿用现有Docker runner和compare_runs执行同一测试：原始快照运行两次，安全断言必须失败、正常功能必须通过；不符合则停止猜测代码。通过校准的原始基线以快照/套件/测试文件/镜像身份缓存，各候选只执行两次补丁后测试。

实际断言未通过进入有限候选重试；缺依赖、未复现、缺失/跳过和不稳定结果作为未决，不把环境错误归因于实现。模型只收到固定测试预期与逐案例状态，不收到执行测试代码。原始/候选/测试在执行前后重校验，每次执行保存身份与结果摘要，不重写失败记录。

旧已冻结上下文不追溯启用此行为。没有选择套件时仍保留验证范围限制。该内循环不替代最终verification阶段的两轮前后比较和人工审阅；也不会自动生成或修改测试来凑通过。

性能优先顺序：明确执行失败的候选直接复用断言诊断进入有限重试，避免付费复审已知失败代码；最终通过候选仍须独立语义检查。重试载荷仅对完全相同的诊断正文去重并指向现存全文，原检查产物保留。
