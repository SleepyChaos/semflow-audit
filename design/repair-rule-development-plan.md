## 3. 共用基础：证据、上下文与执行身份

### C1：可复用的只读取证

复用现有 `services/evidence.py`、`services/review.py` 中的能力，提炼读源码、源码搜索、调用线索、文档/测试读取的服务端边界。不另造通用 Agent 框架，也不让修复和规则服务直接访问任意文件系统。

- 每次工具请求绑定 owner、audit、stage、源码快照、允许读取范围和预算；工具返回正文、文件/行范围、内容 hash、证据引用。
- 读取范围和修改范围分开：可以为理解读取调用方，不代表可以修改调用方。
- 工具失败、未解析调用、未读取部分保持显式未知；所有代码/注释/文档/日志作为分析数据，不能改变工具权限。
- 能复用的已有证据按快照/位置/hash 复用；跨源码版本不合并。租户/任务/版本不匹配必须拒绝。

### C2：上下文装配与完整性

共用证据引用、去重、预算检查和输入 manifest；各模块独立定义必需材料，避免一个上下文服务承担全部业务判断。

- 原文、语义视图、约束、候选和日志在 ArtifactStore/持久化记录中保存；LangGraph 状态传 ID 与小状态。
- 每轮重新装配，保留当前目标、关键事实原文、条件/冲突/未知和最新相关诊断，不不断追加整段历史。
- 预算包含系统/schema、实际输入、预留输出及余量；关键材料放不下则补读/缩小目标或报告不足，不硬截断。
- 保存提示词/模型/检索/配置版本和输入 hash；明确“未读”“已读但本轮压缩”“推断”。

### C3：有限循环、产物与恢复

- 统一沿用阶段调用/token/时间预算，工具补证与候选生成分别计数；恢复不得重置预算。
- 每次外部调用/工具执行持久化 receipt 和产物身份，checkpoint 恢复核验后才复用；候选/源码/配置变化使验证失效。
- 错误分类：模型/契约、证据不足、候选应用、编译/测试、环境、资源/取消；环境错误不诱导模型改业务代码。
- 每节点计时，失败也计调用/耗时；原有规则人工批准使用 interrupt。修复关键未知/环境问题目前结束阶段并要求补资料重建，专门人工澄清 interrupt 后续实现。

## 4. 模块一：业务语义修复

### 4.1 执行链路

**冻结确认目标与读写范围 → 项目业务地图 → 目标业务流程 → 按需源码取证 → 修改点业务/安全约束 → 上下文装配 → 生成完整候选 → 原版隔离副本应用 → 已有检查 → 失败分类与有限反馈 → 报告/Diff/人工接受。**

项目地图先从目录、README、入口、依赖/配置和已有测试构建；目标理解集中在实际影响范围。正常行为依据可追溯的代码、文档、测试和业务要求，不能把已有缺陷当必须保留的业务逻辑。

### 4.2 工作包

| 工作包 | 原因 | 改造与产物 | 完成条件 |
|---|---|---|---|
| S1 分层理解 | 当前修复缺乏跨模块和业务前提 | 项目地图、目标流程、修改点视图、事实/未知/冲突索引；复用 C1 | 能按需读取关联代码，语义结论引用正确快照原文；关键未知可阻断修复 |
| S2 契约与上下文 | 自然语言概要容易遗漏关键行为或膨胀 | 业务不变量、安全属性、允许改变行为、影响范围、已有验证映射、输入 manifest；复用 C2 | 权限/参数/输出等关键条件不被压缩丢弃；缺材料或超预算显式处理；读写范围隔离 |
| S3 有限修订图 | 当前检查失败后不会补证或修订 | 失败诊断、取证/补丁路由、逐次完整 Diff 与检查历史；复用 C3 | 实现错误回候选，理解缺口回取证，环境受阻暂停；检查失败不能自动接受 |

已实施局部上限：最多 3 个完整补丁候选、累计 8 次只读补证、最多 12 次语义模型调用，并同时受阶段总预算约束。当前上下文先使用 40000 Unicode 字符预算，模型适配器继续控制实际请求/token/时间；详细设计中的约 8k token 分层份额是后续校准目标，没有宣称已精确分配。

每轮从原始快照创建新副本，补丁相对原版完整表达，不继续叠加失败工作区。候选变更重新检查；沿用现有人工接受，不直接覆盖上传源码。

### 4.3 结果表述

报告分别呈现理解依据、业务约束、实际运行的已有检查、通过/失败/未执行/未决和最终 Diff。允许写“依据这些业务约束生成，并通过这些检查”，不能写“已证明全部业务语义保持”或“没有新漏洞”。

暂缓 V1/V2/V3：自动利用脚本与原版校准、攻击变体/新业务回归矩阵、精细根因/静态差分。其进程内验证边界及未来设计见[修复详细计划第 5–7 节](semantic-repair-plan.md)，本批不依赖它们。

## 5. 模块二：RAG 规则生成与补漏验证

### 5.1 三类必需输入与执行链路

| 必需素材 | 最小要求 |
|---|---|
| RAG | 匹配固定语言/API 版本的知识与范例，含来源、适用条件、依赖及 digest |
| 源码 | 漏洞位置及判断 source→传播→sink/防护所需的真实原文，绑定路径/行号/快照；可以按需补读 |
| 漏洞描述 | 类型、触发条件、可控性、根因、关键路径、防护、确认状态与基线覆盖；事实/假设/未知分列 |

**加载描述与已有证据正文 → 有限源码取证 → 确定建模问题 → 双集合检索 → 三类材料就绪检查 → 受限规格/模板或约束生成 → 静态检查 → 开发正反例 → 原项目单规则复测 → 基线与根因比较 → 独立验收 → 人工发布。**

三类材料缺一先补充；源码路径/证据 ID 不代替正文，模型生成的测试代码不代替原项目源码。已确认漏洞用于补漏验收；仅有任务描述时可形成待验证规则，不能自动成为真实漏洞真值。

### 5.2 工作包

| 工作包 | 原因 | 改造与产物 | 完成条件 |
|---|---|---|---|
| R1 双集合与索引 | 资料/范例混检，版本身份不足 | reference/rule_example 元数据及 API、可信迁移、独立混合召回、完整范例依赖取回、索引配置身份 | 语言/版本/集合/租户预过滤有效；向量不跨模型版本混用；两集合可复用查询向量 |
| R2 材料建设 | 当前背景和范例覆盖不足 | 官方 CodeQL/框架 API、漏洞机制、完整规则及开发正反例；来源/许可/版本清单、覆盖缺口表 | 首批目标 30 独立知识主题、20 完整范例单元；代码/依赖可恢复且验证状态真实；切片不重复计数 |
| R3 源码与描述输入 | 默认生成缺正文且不能补读 | 三类输入契约、初始证据注入、按 source/传播/sink/防护有限取证、版本化 prompt/上下文 | 缺材料阻断正式生成；关联证据/读取范围正确；推断不成为已确认事实 |
| R4 单规则补漏 | 样例通过无法说明原项目漏检被补上 | 复用数据库的单入口查询、原始 SARIF、根因匹配、基线对照和验收身份 | 原基线成功且未覆盖目标，新规则命中同一已确认遗漏根因；已有覆盖/待确认/未命中/失败分列 |
| R5 正式流程接入 | 实验策略与 GUI 默认能力不同 | 显式图节点、结构化状态/API、历史版本兼容、人工发布门、CLI 实验与用户校准说明 | 真实工具与普通测试验收后启用新版本；旧任务不被静默改输入/提示词或验证口径 |

R1/R2 采用已有 PostgreSQL + pgvector、Haystack BM25/RRF。RRF 为融合；未配置重排。索引身份已包含实际模型版本、维度、端点/协议和预处理版本，过期索引排除；重建及规模化性能后续评价。

R2 优先官方固定 CodeQL 源码/指南及框架文档，针对已经观察到的 API/类型/框架建模失败补材料；资料与完整范例的采集、核验、开发验证、冻结流程见[RAG 详细计划第 6 节](rag-two-corpus-plan.md)。

### 5.3 两道门槛与补漏口径

1. **静态门槛**：契约、元数据、路径、固定依赖/API 检查＋真实 CodeQL 编译。通过只表示可执行，正反例及独立验收继续保留。
2. **原项目补漏门槛**：同源码/数据库快照只运行一个新 `.ql` 入口及其必要依赖；模型扩展使用引用该模型的单条检测查询。核对原扫描覆盖了相关文件，按根因/source/sink/路径确认原基线确实遗漏。

**补漏成功 = 有效原基线未覆盖 + 单规则成功执行并命中同一已确认遗漏根因。** 换查询 ID、换告警行号或新增一条告警都不能单独满足条件。其他告警分别记录确认 TP、确认 FP、重复或待核实；无目标时标补漏未评估。

明确以补漏为目标的规则未通过目标复测，保持待改进。通用规则仍可按已有通用样例/独立验收发布，但不能标记为已验证补漏。规则/模块/依赖/源码/目标/基线变更，旧验收失效。

原项目目标、编译和开发样例允许有限反馈，复用已有最多 2 次候选预算；源码读取另计但共享阶段预算。独立留出内容/补丁/真值不反馈给生成器，补漏成功与跨项目泛化分开评分。

## 8. 测试、实验和完成标准

### 8.1 普通代码/API/CLI 验收

- 共用：跨用户/任务/版本拒绝、读取与修改范围隔离、缺材料/超预算、关键条件保留、产物篡改/失效、恢复不重复调用、取消及等待状态。
- 修复：跨文件理解有证据；冲突和未知保留；候选从原版重建；实现/语义/环境错误分流；预算耗尽不接受失败候选；验证器和测试不被改动来让结果通过。
- 规则：双集合及版本过滤、完整依赖取回、三类材料就绪检查、编译失败阻断、原基线已有覆盖不计增益、确实遗漏目标命中、同根因去重、其他告警未决/误报不计 TP、失败/超时/快照不匹配不计成功。
- 使用替身的测试只检验流程和权限；真实模型/CodeQL/运行时结果另报。所有测试只清理自己的临时任务，不清空用户数据。继续不做 GUI 测试。
