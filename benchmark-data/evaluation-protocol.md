# 正式评测协议草案

日期：2026-10-05。当前阶段是收集与校准，不从已有小样本结果推断真实世界性能。

## 1. 先冻结材料与运行条件

按仓库、CVE/GHSA 别名、修复根因分组拆分开发和隐藏测试；同一漏洞的多个入口、版本、变体不得跨组。另保留完整 CWE 家族外推组。检查旧实验、RAG 文档/范例与作者生成输出的重叠，记录文件哈希和暴露状态。新候选尚未全部完成这一步。

三条链路分别保存任务清单；不要只选 CodeQL 已经发现且容易修复的漏洞。发现输入是漏洞版完整源码；规则输入允许源码、漏洞描述和检索材料；修复输入允许源码、最终审计报告、业务上下文和开发测试反馈。公开 CVE 描述作为给定输入的任务，必须与完全无漏洞提示的发现任务分开。

评测器独占官方修复 diff、修复版源码、隐藏测试、漏洞 trace、标签与作者查询。PatchEval `input.json` 自带 `fix_func` 和 one-shot，不能整项传给模型。源代码注释中的答案、案例名与 manifest 也要审查，保留正常业务注释，记录任何去标签改动。

固定模型、提示版本、温度、重试上限、token/时间/工具预算、CodeQL CLI/pack、硬件与网络条件。先冻结任务再运行；构建失败、超时、弃权和跳过分别登记，禁止把失败换成零漏洞或删除不利样本。

## 2. 双引擎发现

对比 CodeQL 单独、Agent 单独、并发合并不复审、并发合并加取证复审。默认 CodeQL 套件保持一致；扩展套件后续作为独立实验加入。

主指标：根因级 precision/recall/F1，按 CWE/框架/仓库规模分层；CodeQL 之外新增且核实的真漏洞数、误报数、重复数；Agent 入口/危险操作/跨模块路径定位准确度；复审误删真漏洞率和弃权覆盖率。以相同根因合并多入口，不允许输出多条重复报告抬高召回。

OWASP 有正负例，可以测误报率。真实 CVE、VulnGym 等标签不完备，未匹配告警进入独立盲审，不能自动全判 FP。保留官方原评分和经复核的补充结果两张表。VulnGym 官方 evaluator 主要测 coverage，不能将其称为完整精确率。SastBench 是告警 triage，单列真假过滤效果，不当作全项目发现召回。

## 3. RAG 与 QL 生成

**检索与生成分别评估。** 人工标注冻结任务的资料相关性、API 版本适配、范例结构适配，报告 Recall@k、nDCG@k、MRR 和上下文重复率。BM25 是检索方法，RAG 是检索后增强生成的流程；应对比 BM25、向量、混合三种检索，再比较无检索和固定 oracle 资料组。

控制相同语料、top-k、token 上限、生成模板与执行反馈。消融知识库、范例库、源码读取、约束规格、开发执行反馈；检索主消融保持生成侧不变。每任务至少 3 个独立随机种子，重复不是新增样本，置信区间按仓库/任务组计算。

生成主指标：静态/编译通过率、单规则执行完成率、目标根因命中率、隐藏正例召回、隐藏安全负例误报、复用到另一个仓库的效果、修复反馈轮数和耗时。禁止靠硬编码文件行号获得检测分数。CodeQL 原套件未发现但新规则确实命中的根因才算新增检测增益；复制官方已有规则测的是再现能力。

规则开发测试反馈允许模型访问，隐藏测试不回流优化。先在开发样例编译和运行，再执行冻结的隐藏原版/官方修复版/正常业务变体。官方修复版仅是同根因负例，经校准后使用，不能直接认为整项目无漏洞。

当前缺少完整的公开 Python/JS 黄金 QL 独立任务集。利用新项目配对和 OWASP 构造衍生任务时，明确写成自建评测协议并引用上游来源，不能改名宣称为某论文官方 benchmark。QLCoder/IRIS 的 Java/C 任务先作流程参考。

## 4. 语义辅助修复

两类任务分开：已知漏洞的修复（固定 gold 描述）、平台实际审计结果驱动的端到端修复（包含漏报和误报）。后者另报告从全部漏洞项目到正确修复的总体比例，不能只对已成功发现部分评分。

业务语义分解为可检验的不变量：合法请求行为、权限矩阵、数据完整性、返回值/异常合同、跨模块副作用。比较无语义上下文、自动语义摘要、分层取证上下文、带失败反馈循环；保持相同修复预算。摘要有证据出处但最终以用例验证，不以 LLM 互评当语义保持证据。

本阶段校准目标是确认原版正常用例通过且安全用例暴露目标缺陷，官方修复保持正常功能并解决目标缺陷。平台补丁必须同时满足安全与功能 oracle 才可记为 verified。缺失/skip/超时/依赖失败一律为 unknown 或 infra-failure；PatchEval 非空测试命令不等于能运行，Vul4Py `functional_rc=999` 不算功能通过。

按此前决定，暂不把漏洞利用复测加入产品修复流程，不启动目标服务。先收集 oracle 并分类为纯单元可验证、需要独立环境、需要服务集成；当前普通测试只能支持语法/已覆盖功能保持。未运行安全 oracle 的修复不能标为“根源已修复”；静态复扫也不能证明未引入新漏洞。若后续扩展隔离安全评测，需明确阶段和运行边界。

## 5. 速度、公平比较与复现

分别记录端到端墙钟、数据库构建、CodeQL 扫描、Agent 粗筛、取证复审、检索、QL 编译/执行、修复各阶段。并发链路用实际墙钟计算，不能把两分支时长相加当总耗时。报告冷/暖缓存、p50/p95、token/请求量与达到固定覆盖目标所需成本；失败和超时纳入分母。

竞品第一组为相同 CodeQL 套件、Semgrep CE 明确规则集、Python Bandit；Agent/阿里 Open Code Review 单列模型和上下文预算。QLCoder/IRIS/CQLLM 属方法参考，只有真实适配并执行了同一语言任务才能填平台对照结果。使用实际运行版本和许可，不搬用作者分数。

执行顺序：①材料完整性与暴露审计；②冻结每链路 10–20 个跨仓库校准候选，人工审核根因/业务合同/测试可得性；③通过校准后分开发与隐藏集；④先跑确定性基线，再跑公平预算对照；⑤按首次冻结样本报告结果与置信区间。校准失败可以排除，但预先规定理由并保留数量和记录，不能根据模型表现选样。
