## 3. 规则生成任务怎样从材料形成

首批准备目标 6–10 个 Py/JS 合格任务；优先至少两个语言均有代表，但不足时诚实缩小范围。每条任务具备：

1. 已裁决的目标根因、CWE、项目/API 身份与允许给模型的漏洞描述。
2. 去标签源码；允许读取范围；已冻结的检索语料身份。
3. 模型可见的开发正/负例，以及评测器独占的隐藏正/负例。
4. 编译、执行、根因命中和误报评分；固定基线是否已命中。

目标隐藏集合每任务至少 2 正+2 安全负例，后续扩充到 5+5；人工变体与自然项目分别标记。只有同一原版和官方修复版时，先称“配对定位任务”，不声称跨项目泛化。跨仓库版本只有完成根因/合法行为校准才进复用主表。

漏检增益任务与已覆盖再现任务分别统计。不要因为 CodeQL 发现了才入选，也不要只保留模型生成成功的任务。基线信息留在评测器；生成输入三组素材保持完整：知识/范例、源码、漏洞描述。

检索标注首批目标 24 条查询需求，按 6–8 个 CWE/API/语言组合分组，知识与范例分别评价。查询出自冻结任务，相关性候选池由三种检索结果并集构造；初标附适配理由，复核状态单列。不把 LLM 自动评价当成人工金标。

当前 271 参考来源/141 范例仅为待冻结起点，以 E00 实际 inventory 为准。原 18 次规则共同集、官方已收入 RAG 的规则及其样例属于开发/再现，不进入未见任务主榜。

## 4. 修复候选怎样筛选

从 PatchEval 先筛 Python/JavaScript、测试命令非空的记录，按仓库/根因去重，按公开日期和稳定 ID 排序取最多 12 条校准候选；日期缺失放后、披露排序来源。元数据不是可运行项目，随后才准备完整源码和测试。

补充最多 8 条 Vul4Py 候选，排除旧 pilot 仓库与同根因重复。首次 10–20 条校准后，目标得到 4–6 个双 oracle 合格任务；若不足，给出接纳/排除原因，不强凑数量。

接纳条件：

- 根因与安全合同明确，源码版本可固定，安装和普通测试可在独立工作区执行。
- 只需纯函数/模块单元测试，无服务启动、浏览器、真实账号、云资源或运行期外网。
- 原版正常测试通过、目标安全测试失败；官方修复后两者通过。缺失/skip/999/依赖异常不算通过。
- 目标测试只验证该根因；正常测试覆盖至少一个关键业务不变量，明确其有限覆盖。
- 隐藏测试与 gold diff 不传给模型；若同一候选兼做规则任务，统一仓库/根因拆分，防止链路间交叉泄漏。

原 8 个小 oracle 可用于 runner 校准；不能重新冠名独立测试。EduCollab 两个业务项目当前只收集到选定源码且多为 HTTP 测试，暂作语义合同案例，不纳入可运行主榜。BugsInPy 作为测试工作流参考，不作为安全修复真值。

## 5. 暂缓的材料与竞品层次

- QLCoder、IRIS：Java/C 主任务不匹配当前语言，作规则反馈方法参考。
- CQLLM：Py 资料可参考，但源码/金标完整性与 RAG 重叠未核清，暂不当隐藏集。
- VulnGym / SastBench：第二批证据路径与复审专项；需要不同输入/分母。
- SecBench.js / VulnRepairEval / SEC-bench：涉及环境或利用执行的部分暂缓。
- VLoc / VEX / QueryGen 未完整下载部分：保留来源，不进入当前可运行列表。
- 首批必跑竞品为相同 suite 的 CodeQL；Bandit 和固定许可规则的 Semgrep 为静态补充；Open Code Review 完成公平输入适配后再跑。

不得把“已收集 29 条材料目录”写成“29 个已经跑通的基准”。此阶段项目名具体，正式任务数量由校准收据确定。
