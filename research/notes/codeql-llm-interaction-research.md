# LLM 与 CodeQL 深度协同：研究方向与创新边界

日期：2026-10-08。状态：研究建议，尚未实现或实验验证；不替换现有实验计划。

## 1. 结论与当前实现

当前双引擎链路具有工程价值，但把并行扫描、合并候选、Agent 复审作为主要方法贡献，差异不足。建议把研究问题收敛为：**如何把 LLM 推测的框架语义转化为带条件、可核查的 CodeQL 模型，并控制错误模型造成的误报与漏报？**

CodeQL 的调用图、数据流摘要、source/sink 与安全屏障模型都可以影响检测能力。研究贡献可以落在这些分析模型及其推理过程；无需以修改 CodeQL 内核行数衡量创新程度。

源码核查：

- `backend/app/services/dual_scanning.py`：CodeQL 与 Scout 分别执行；join 汇总状态、覆盖与候选，未在发现阶段自动精化 CodeQL 模型。
- `backend/app/services/review.py`：已有 `static_query` 工具，默认最多三次查询。
- `backend/app/services/rules_execution.py`：该工具执行已发布、语言匹配且通过验证的规则，返回范围内证据；当前不允许 Agent 任意提交新的分析模型。
- `backend/app/adapters/codeql/model_spec.py`：规则侧已有窄范围 Python code-injection sink 模型与固定模板；不能据此认为发现链路已实现通用框架语义精化。

因此，当前具备工具交互基础，缺少的是**分析假设进入 CodeQL、接受检验并反馈修订的协同机制**。本建议延续 10 月 4 日论文可行性评估中的条件化规格方向，进一步明确其与最新工作的差异和发现链路的接入位置。

## 2. 已有论文覆盖了什么

以下来自论文方法和局限章节的定向阅读；并非完整系统综述，也不构成全球首创证明。预印本与正式发表分别标注。

| 工作 | 时间/状态 | 已覆盖的机制 | 对本项目的影响 |
|---|---|---|---|
| [IRIS](https://arxiv.org/html/2405.17238v3)，[ICLR 正式记录](https://proceedings.iclr.cc/paper_files/paper/2025/hash/582d4e27fa24168f3af1f4582655034b-Abstract-Conference.html) | ICLR 2025 | LLM 推断 source/sink，CodeQL 执行污点分析，LLM 结合路径复审 | 补端点和路径复审已有直接先例 |
| [SemTaint](https://arxiv.org/html/2601.10865v1) | 2026-01-15，预印本 | 根据污点可达性按需修复调用关系，第三方候选摘要参与路径后再由 Agent 分析 | 按需补调用图和库摘要也已有直接先例；是最重要的方法对照 |
| [ARQ](https://arxiv.org/html/2608.20637v1) | 2026-08-21，预印本 | 成对程序与运行时 oracle 暴露查询错误，反馈修改并做累计回归 | 反例驱动改 QL 不能直接作为新贡献；其 C/C++ oracle 不可直接等价迁移到 Web 漏洞 |
| [LLM4PFA](https://arxiv.org/html/2506.10322v1) | 2025-06，预印本 | CFG 条件提取、LLM 语义推理和 SMT 转换、Z3 求解 | 加求解器做路径复审已有先例；约束翻译的正确性仍需验证 |
| [Artemis](https://tingdai.github.io/files/artemis_OOPSLA25.pdf) | OOPSLA 2025 | PHP SSRF 的 LLM source/sink 识别、静态传播与字符串路径条件剪枝 | 按漏洞类别建条件分析也已有先例；不能只用“路径敏感”包装创新 |
| [ABSENTIA](https://arxiv.org/html/2610.00977v1) | 2026-10-01，预印本 | 路由图组织审计、推断权限不变量并查找违反 | 业务语义和权限不变量审计也不是空白方向 |
| [APAS-Finder / ReSA](https://arxiv.org/html/2609.26529v1) | 2026-09-22，预印本 | 面向审批后对象重建的权限义务、模型核验与确定性分析 | “语义合同＋检查器”已有相关工作；其语义事实依赖人工核验，不能描述为自动 LLM 推断系统 |

SemTaint 的 §IV-E 以第三方调用的传播/净化判断过滤依赖路径，§V-B 记录了一例错误净化判断导致漏检；§V-F 也说明现有 sanitizer 过度近似在其处理范围之外。这给本项目提供了明确的问题入口，但“增加验证”本身仍需要具体算法和迁移实验。

相关的 QLCoder、CQLLM、QRS 已在规则生成研究中登记。RAG、编译反馈、执行反馈属于强基线组件，应保留与规则生成创新的边界。

## 3. 候选 A：带条件与不确定性的分析模型精化（优先）

### 3.1 研究对象

传统标签常把某个 API 直接归为 source、sink、传播函数或 sanitizer。实际语义可能依赖库版本、接收者类型、参数位置、配置、返回值分支和下游使用场景。

让 LLM 输出结构化模型事实：

```text
真实符号及源码锚点 + 库版本/配置
输入输出关系 + 目标 CWE/使用场景
生效条件 + 证据引用 + 尚未核实的前提
```

避免只生成 `isSafe=true`。先支持参数位置、常量配置和明确的成功返回分支等少量可检查条件。通用自然语言合同不能直接作为 CodeQL 可执行语义。

### 3.2 执行链路

```text
CodeQL 原生扫描 + 固定诊断查询；独立 Scout 并行
    ↓
定位模型缺口/冲突：端点、调用绑定、传播、保护条件
    ↓
LLM 读取局部源码、依赖实现、对应版本资料，提出条件化模型
    ↓
符号绑定与模板编译；CodeQL 检查模型前提与路径覆盖
    ↓
比较原生模型、候选模型、已核验模型的结果及依赖事实
    ↓
定向取证或修订模型，达到预算/收敛条件后停止
    ↓
统一复审；分别保留已核验、假设依赖、未决的候选
```

CodeQL 无告警不等于已发现分析断点。断点候选需要独立诊断查询、可疑操作目录或 Scout 提示；在实验中漏检由独立 oracle 判定。若 source 与 sink 均缺失，单靠已有污点路径无法保证发现；保留独立 Scout 和覆盖任务。

### 3.3 关键方法差异：不同模型错误具有不同后果

- 新增传播边可能增加可疑路径：可在候选分析中探索，但需要保留假设依赖，不把路径存在等同于真实漏洞。
- 新增净化/保护屏障可能删除真实漏洞：采纳条件应更严格。无法核验完整前提时，保留告警或未决状态。
- 原生 CodeQL 的可疑屏障也可以进入局部挑战分析；诊断视图绕过屏障只生成待查路径，不把所有屏障关闭后产生的结果都当漏洞。
- 路径携带所依赖的模型事实及作用域，冲突或失效时能定位受影响结果。事实改动后的缓存和版本记录是实现保障，单独不算方法创新。

研究重点是：**不确定模型如何影响路径结论、条件如何被检查、取证如何改变模型采纳决策**。双模型比较、普通 CEGAR、置信度阈值都不是新概念；需要说明本方法针对 LLM 语义事实的特殊错误及可测增益。

### 3.4 示例

某封装 `validate_path(p, strict)` 在 `strict=true` 且验证成功后，才满足特定路径遍历防护要求。

LLM 提出条件；CodeQL 绑定真实函数与被检查参数，检查调用配置、成功分支、实际使用值及校验后是否发生相关变换。仅存在同名校验调用不能删除全部路径；同一封装的其他配置继续按待查路径处理。

这个例子用于说明条件依赖，不代表任意路径校验可以被静态证明。符号链接、运行时目录状态、复杂规范化等超出当前静态模型时，应明确列为未决。

### 3.5 可以检验的研究假设

- H1：条件化事实比全局角色标签更能区分同一 API 的安全/不安全用法。
- H2：针对删路径模型的更严格核验，能降低真实漏洞被错误排除的比例。
- H3：依据结果依赖和模型分歧定向取证，在同预算下优于随机缺口处理或固定全量阅读。
- H4：模型能迁移到未见调用者、框架版本和配置组合；其增益不是记住开发样例。

这些都是待验证假设。核查源码锚点只证明引用存在；通过有限正反例只证明测试范围内行为；二者都不能自动证明模型普遍正确。

## 4. 候选 B：业务权限关系进入 CodeQL（潜力较高，成本较高）

LLM 从明确权限需求、可信测试与代码组织中提出“主体—动作—资源—条件”的权限合同。CodeQL 用固定检查模板绑定路由、对象身份、资源 ID、租户关系、校验条件及使用操作。

优先限制为两个模式：对象所有权检查、租户隔离。需要区分：

- 检查了对象 A，最终操作对象 B。
- 只校验登录，没有校验该资源的权限。
- 校验存在于一条分支，其他到达敏感操作的分支绕过。
- 校验后重新加载或修改了权限相关对象。

LLM 解释业务关系，CodeQL 检查程序中的关系与路径，反馈未覆盖位置。权限依据不足、动态调用不可解析或跨服务状态不可获得时保持未决。

ABSENTIA 已推断权限不变量；APAS-Finder 已处理特定审批重建场景。可研究的差异是跨 Web 框架的合同落地、对象绑定和分支覆盖自动化，但必须与二者任务边界逐项比较。仅将自然语言结论转存为 QL 文件不够。

风险：从漏洞实现本身推断“本来就应该这样”会产生循环论证；应区分外部声明的要求、源码支持的事实、推测的需求。没有明确业务需求时不能承诺自动判定任意业务漏洞。

## 5. 候选 C：CodeQL 路径的可检查反证（作为支撑模块）

CodeQL 提供控制/数据流事实，LLM 定位影响路径成立的外部语义，固定转换器生成受限约束，必要时交给 Z3。先限于布尔、整数比较、固定集合成员及部分身份关系。

只在约束抽取与转换的适用范围内排除路径；求解失败或语义缺失保留未决。SMT 得到 UNSAT 只说明提交的公式不可满足，不能弥补抽取遗漏或错误翻译；SAT 也不直接证明漏洞可利用。

LLM4PFA 和 Artemis 已有路径条件相关方法。推荐将其作为候选 A/B 的核验组件；单独增加求解器的创新支撑较弱，且 Python/JS 动态语义会增加实现成本。

## 6. 技术可行性和版本边界

- 官方提供 [Python 模型扩展](https://codeql.github.com/docs/codeql-language-guides/customizing-library-models-for-python/) 与 [JavaScript 模型扩展](https://codeql.github.com/docs/codeql-language-guides/customizing-library-models-for-javascript/)，可补 source/sink、type 和 summary；不支持的模型种类需要固定 QL 扩展。
- [partial flow 文档](https://codeql.github.com/docs/writing-codeql-queries/debugging-data-flow-queries-using-partial-flow/) 支持有界正向/反向探索。它是调试能力，不是自动漏检解释器；大量 source 和高探索半径可能很慢。
- 本地冻结库 Python `4.0.10`、JavaScript `2.4.0` 的 data-extension 声明已核查有 `summaryModel`，未见 `barrierModel/barrierGuardModel`。共享 dataflow 库可见 `FlowExplorationFwd/Rev`，各语言入口与自定义查询仍须实际编译验证。
- [2.25.4 更新记录](https://codeql.github.com/docs/codeql-overview/codeql-changelog/codeql-cli-2.25.4/)说明 Python/JS 的 barrier 数据扩展在该版本加入；历史对照 CLI 为 `2.23.5`。应选择旧版本兼容 QL 模板或独立升级实验臂，不能混入历史提升数字。
- 条件化合同并非都能表达为 YAML 模型。需要基于既有 CodeQL CFG/API graph/guard 能力做有限模板；优先复用成熟分析框架，避免重写整个分析器。

接入后仍可保留四阶段产品流程：协同精化放在发现阶段内部，最终审计结果进入语义修复；RAG 规则生成仍负责可复用规则的独立生成、验证与发布。

## 7. 最小研究验证方案

建议先做 12–20 个独立模型任务的开发试点，至少包含几种 API 条件机制和多个 Python/JS 项目；数量是资源规划，不能作为统计充分性的保证。预留未参与调试的项目/版本/条件组合，再决定扩大正式测试规模。

| 实验臂 | 用途 |
|---|---|
| 原生 CodeQL；当前并行双引擎 | 核查现有基础与额外复杂度是否值得 |
| LLM 全局 source/sink/summary 标签＋CodeQL | 接近 IRIS/SemTaint 相关机制的适配强基线，不能冒称原论文完整复现 |
| 条件化模型＋CodeQL | 测条件表达本身的增益 |
| 条件化模型＋分歧驱动取证＋严格屏障核验 | 测完整方法 |
| 人工核验模型＋CodeQL | 判断模型推断还是静态表达/分析能力构成上限 |

分量消融：去掉条件、去掉严格屏障核验、替换为随机取证、去掉模型依赖反馈；固定同模型、同 suite、同版本及预算，同时补同质量成本比较。

测试分层：

1. OWASP 新预留样本：一般检测效果与无回归检查。
2. 真实项目漏洞/修复对：未知框架包装、依赖和跨文件模型缺口；按项目与根因家族分组。
3. 独立条件对照：同 API 的版本/配置/返回分支/参数位置变化，单变量对比；不能只依赖生成模型自身提出的测试 oracle。
4. 权限合同方向另用 BAC-Bench 同任务材料与人工核验合同；不混入注入漏洞总体分数。

指标：根因级 P/R/F1、指定漏洞前后版本成对正确率、错误屏障造成的真漏洞排除率、模型适用条件准确性、未决/失败/预算耗尽率、完整端到端耗时与 token；模型原始路径和最终复审分别评分。

既有 OWASP48 和 RealVuln 已暴露，只作回归和开发诊断。选定 CodeQL 漏检集能测补充能力，不能代表通用召回；官方补丁仅为指定根因提供负例，不说明整个项目安全。模型事实“已核验”也不等于漏洞已证实可利用。

## 8. 推荐次序和停止条件

优先 A，先验证条件化传播/保护模型；B 在 A 有可用结构核验后，以所有权与租户隔离做独立试点；C 按遇到的具体核验缺口引入。

创新主张应是可测的方法差异：条件与不确定性如何进入分析、如何约束删路径决策、如何选择能改变结论的证据。LangGraph 编排、多 Agent、模型包、RAG 和缓存作为工程支撑。

若增加条件核验后，未见项目无法优于全局标签＋普通复审，或严格屏障核验只是把错误转成大量未决、成本明显上升，应收缩主张或调整方向。应先证实普通机制存在稳定失效，再用独立实验确认方法解决了该失效。

本次交付为研究方案：未新增付费模型调用，未运行 GUI/目标服务/漏洞利用，未修改生产审计链路。
