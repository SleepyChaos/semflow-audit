## 2. 从论文到可证伪实验

下面均为本项目拟实施的方案，不是原论文宣称的结论。

### R：证据绑定的规格生成

问题：编译/开发样例合格的规则是否能补充未知项目的分析能力？

- 基线 R0：固定 CodeQL 原生查询；R1：当前自由 QL 生成；R2：结构化规格与模板；R3：R2 加开发样例执行反馈。
- 增加项目 API 清单和实际调用位置绑定；同名遮蔽、不同参数位置、常量输入、合法 sanitizer 作为反例。
- 分开记录复用原查询、扩展框架模型、新检测器；只有 R0 漏检而新模型准确发现且独立验收通过的目标，才算新增覆盖。
- 开发用例可进入反馈；测试 oracle、测试项目修复和真值永不进入检索或提示。
- 首批沿用现有六类标准任务和三类框架任务作回归，新增 Flask `get/post` 缺口与真实框架包装 API 的开发/留出对例。不能用修正测试标签隐藏真实规则缺口。

### E：复审与主动发现分开评价

问题：按需取证是否改善真实告警裁决，是否错误排除真漏洞？

- E0：模型只获得固定告警位置附近上下文；E1：当前工具取证；E2：围绕缺失前提的结构化证据请求，例如来源可信度、sanitizer 语义、跨文件调用。
- 三组固定模型、输入起点、总 token/调用上限；工具组不能额外拿到答案或无限上下文。
- 复审报告 TP 保留率、FP 消除率、未决率、已裁决覆盖率；允许弃权，弃权不算排除误报。
- 主动发现单列：相对 CodeQL 新增、经根因核实的目标；位置不同和模型自报置信度都不足以证明新漏洞。
- 对“工具取证无收益”也接受结果；先检查上下文是否真的改变结论，再增加工具复杂度。

### S：质量约束下减少工作量

问题：减少重复分析与无关取证能否降低总成本，同时保持发现能力？

- S0：当前完整流程；S1：仅同快照内证据去重和已验证数据库复用；S2：基于未解决审计前提选择取证目标。
- 首轮不实现完整动态调用图修补，不以 LLM 自报低风险直接跳过审计。被预算跳过的范围必须可见。
- 分别报告提取、查询编译、查询执行、取证、模型、规则验证、报告时间；队列等待独立记录。
- 规则生成属于一次性投资，分别给出生成成本和复用 1/5/20 次时的摊销成本；不要把昂贵离线生成混成扫描加速。
- 比较顺序交替，固定并发，至少三次重复；冷/暖分组。重复同一漏洞衡量稳定性，不能扩大独立样本数。
- 首批小样本门槛：零个已知 TP 因优化丢失，并逐例复核输出差异；扩大真实数据后，再用配对置信区间评价非劣性。不能凭 20 对的点估计声称低于 1 个百分点的召回损失。
- 动态查询已有 BQRS 缓存串用历史，继续保留强制重算；未证明缓存键完整性与结果一致前不优化这一层。

| 自建规则正反例 | 现有标准与模拟框架集 | 规则回归和定位失效机制 | 必须与真实项目表分开；隐藏用例不可用于调参 |

首批总目标仍为 **20 个真实漏洞配对（目标 Python/JS 各 10）**。可运行性不足时保留失败清单和原因，不悄悄换成容易检出的样本。已有微样本用于工程回归，不能占用真实项目数量。

SastBench 本地结构检查发现 `finding_id` 自身形如 `commit:CWE:false_positive`，含答案。送入模型的输入必须只取白名单 `to_analyzer`，内部记录使用不含标签的随机 ID；`ground_truth`、`metadata.source`、原始 `finding_id`、补丁与裁决说明均留在评测器。仅“没有发送 ground_truth 字段”不足以证明无泄漏。

建议冻结清单至少包含：数据来源/版本/许可、repo、pre/post SHA、语言、目标 CWE、根因位置、oracle 状态、排除原因、开发或测试分组、源文件 hash。基准选择和排除在看到平台结果前确定；多源重复 CVE 和同一修复提交去重。

## 4. 本轮决策

1. **采用**：结构化规格与执行反馈、真实项目配对、独立复审实验、分阶段成本记录。
2. **优先试验**：与审计前提绑定的定向取证、同快照内证据去重、模型规格复用。
3. **暂缓**：完整 LLM 调用图修补、无实测支撑的复杂检索、将全部 Python/JS 语义转 SMT、缓存动态查询结果的激进提速。
4. **证据门槛**：源码实现、工程测试、真实模型结果、独立真值评价分别报告；任何一个环节尚未完成都不能用论文作者数字代替。

公开论文读取仅证明方法和材料存在。本轮没有新增性能分数，具体运行结果应另存独立报告并引用冻结实验清单。
