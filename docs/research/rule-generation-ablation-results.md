# RAG 规则生成改造：真实消融结果

日期：2026-10-03。结论：**受限规格＋已验证模板＋真实样例执行反馈值得继续；检索路由本身没有呈现一致提升，暂不替换默认生产链路。**

## 1. 实际完成范围

- 11 个实验组，162 次可比较生成请求；另保留 4 次提示词偏差请求，实际共 166 次、262 次模型调用。
- 固定实际响应模型 `deepseek-v4-1-flash-260910`，全部 thinking disabled；固定 Python / JavaScript CodeQL packs。
- 主组 6 种语义任务×3轮；补充 3 种模拟框架 API×3轮。重复次数用于测生成稳定性，不算独立漏洞数。
- 真正执行 CodeQL 编译、模型生成样例回归和隐藏样例检测；无 GUI 测试、无自动批准或发布。
- 普通测试 **78 passed、2 integration deselected**；另有真实动态查询缓存回归 **1 passed / 31.60s**。普通测试中的模型替身仅验证代码行为，不混入能力统计。

详细协议见 [消融协议](rule-generation-ablation-protocol.md)，机器可读指标见 [汇总 JSON](rule-generation-ablation-summary.json)。

## 2. 主消融矩阵

每组 18 次请求。生成通过表示结构、引用、样例语法及编译通过；端到端表示生成、生成样例真实回归、隐藏样例均通过。

| 组 | 路径 | 生成通过 | 隐藏样例通过 | 生成样例通过 | 端到端通过 | 生成阶段中位数 |
|---|---|---:|---:|---:|---:|---:|
| A | BM25＋日志＋自由 QL | 1/18 | 0/18 | 0/18 | 0/18 | 12.54s |
| B | 分路检索＋日志＋自由 QL | 4/18 | 2/18 | 1/18 | 1/18 | 12.87s |
| C | BM25＋完整候选反馈＋自由 QL | 12/18 | 7/18 | 7/18 | 7/18 | 18.46s |
| D | 分路检索＋完整候选反馈＋自由 QL | 11/18 | 8/18 | 6/18 | 6/18 | 19.70s |
| E | BM25＋受限规格＋官方模板 | 18/18 | 15/18 | 14/18 | 12/18 | 13.82s |
| F | 分路检索＋受限规格＋官方模板 | 18/18 | 15/18 | 12/18 | 9/18 | 13.23s |
| K（补充） | F＋真实生成样例执行反馈 | 18/18 | 15/18 | 18/18 | **15/18** | 50.72s |

### 可以得出的结论

1. **完整候选反馈有效。** A→C 的端到端成功从 0→7；B→D 从 1→6。旧链路只传日志、不传上一版完整规则的设计确实有问题。
2. **分路检索不能直接宣称提高准确率。** A→B 小幅改善，但 C→D 的端到端从 7→6，E→F 从 12→9。此次样本小，不能宣称统计显著；优先改善知识角色、完整 API 声明与任务绑定，不能把增加检索量作为解决方案。
3. **受限规格减少生成故障，但生成样例仍可能出错。** E/F 的编译率都是 100%；其端到端分别只有 66.7% / 50.0%。LLM 对来源语义、预期行号、反例的认识仍不稳定。
4. **真实生成样例反馈改善端到端。** F→K 从 9/18→15/18，同时中位阶段时间从 13.23s→50.72s。质量改善伴随模型/工具开销，不能宣传为速度同时提升。
5. **标准模板复用不算 AI 新增检测覆盖。** 无 AI 官方查询在隐藏样本上 5/6 任务通过；E/F/K 的隐藏通过率都对应这一能力。这里主要验证生成可靠性与验收机制。

### 剩余 Python XSS 失败

隐藏 Python XSS 样例使用 Flask `@app.get` 返回未转义用户输入；固定库的相关响应建模围绕 `route` / `add_url_rule`，该样例未被选定反射 XSS 查询检出。无 AI 官方查询同样失败。

这提示需要明确框架 API 覆盖，再补模型；不能靠生成样例反馈修复固定检测模板的覆盖缺口，也不能改隐藏样例来获得满分。

### 精确率／召回率的口径

- E/F/K 已完成全部 18 次隐藏检测；位置级 TP=21、FP=0、FN=3，精确率 100%、召回率 87.5%。这是小型人工构造样本的指标，不能写成现实项目“100%准确”。
- 自由组有工具执行/结果契约错误：A 的 1 个已编译查询执行失败；B 4 个里只有 2 个完成；C 12 个里 7 个完成；D 11 个里 8 个完成。
- B/C/D 在完成执行的子集上没有位置误报/漏报，但执行覆盖不足。**必须同时报 2/18、7/18、8/18 的请求级成功，不能只给子集 100% 精确率。**

## 3. 未建模框架 API 的补充实验

3 种不透明导入 API，危险参数在 0 / 1 / 2 位置。实现不提供给静态分析器，领域文档提供语义。每组 9 次请求，反例覆盖常量和仅流入元数据参数的用户输入。

| 组 | 路径 | 生成通过 | 隐藏通过 | 生成样例通过 | 端到端通过 | 中位阶段时间 |
|---|---|---:|---:|---:|---:|---:|
| H | 领域文档＋自由 QL＋完整反馈 | 1/9 | 0/9 | 0/9 | 0/9 | 13.33s |
| I | 领域文档＋FrameworkSpec＋sink 模板 | 9/9 | 9/9 | 3/9 | 3/9 | 11.88s |
| J | I 移除领域文档 | 0/9 | 0/9 | 0/9 | 0/9 | 3.56s |
| L（补充） | I＋真实生成样例执行反馈 | 8/9 | 8/9 | 8/9 | **8/9** | 53.45s |

- 官方无 AI 查询：0/3 任务，缺少对应 sink 模型。
- 人工指定正确 sink 的模板上界：3/3 任务通过。模板承载能力属于 CodeQL；AI 的贡献是从检索文档提炼模块、成员、参数索引，自动形成模型及样例。
- I 的 9 次完成检测共 TP=9、FP=0、FN=0；L 的 8 次完成检测 TP=8、FP=0、FN=0，剩余 1 次生成/回归失败保留在分母。
- J 的拒绝生成体现证据门槛：不能凭空生成无文档支持的 API。它不是已执行后“没有发现漏洞”。
- 当前语义提炼是小型合成 API 的证明，不能宣称超过人工建模或已经复现 IRIS/QLCoder 的现实 CVE 成绩。论文实验仍需加入无 AI 文档解析、人工模型、真实跨项目模型扩展对照。

## 4. 本次发现并修复的实际问题

1. **CodeQL 结果缓存串用**：相同 `audit/generated:generated.ql` 身份会复用上一条查询的 BQRS。动态执行增加 `--rerun`；两条不同查询同库执行的真实回归通过。缓存修正前的独立评估全部作废并重跑，没有重挑模型候选。
2. **抽取解释器路径**：相对 runtime PATH 在工具切换工作目录后失效，误用 3.14。改成绝对路径并以 3.11 重建评估数据库。
3. **候选与诊断丢失**：在元数据检查前保存完整候选，保留编译/契约诊断；模型无效/截断响应也保存为私有产物。真实样例失败使用实际开发样例日志。
4. **阶段提示词漂移**：补充实验准备时短暂改动 v3，检出 4 次偏差请求并原样保留、冻结原提示词补跑。现在模型绑定阶段时持久化提示词内容和 SHA，后续文件编辑不会影响该阶段。
5. **生成样例只做语法检查**：新增受控 `execute_dev`，执行结果差异与完整候选进入最多两次尝试的反馈环路，隐藏样例不进入反馈。
