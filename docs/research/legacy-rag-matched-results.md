# 新旧 RAG 规则方案：原测试集复测

日期：2026-10-04。协议见 [冻结协议及偏差说明](legacy-rag-matched-protocol.md)，机器可读结果见 [汇总 JSON](legacy-rag-matched-summary.json)。测试期间没有根据隐藏结果修改生成器、提示词或金标。

## 1. 结论

**在旧测试集、旧共同输出预算 6000 下，当前 v6 默认 auto 链路明显退化：旧最强 K 方案重新运行 15/18，当前 v6 为 1/18。** 双集合、真实 embedding、主动源码理解等机制已经接入，但当前组合没有证明规则生成效果改善。

此前 [开发案例报告](semantic-development-results.md) 的旧 v2 0/3、新 v6 3/3，是一个未建模来源案例的结果；它不能代表本次六类任务，也不能替代与旧最强 K 的比较。这两个实验的任务和基线不同，原始结果均保留。

| 本次组别 | 通过编译的请求 | 开发正反例通过 | 完成隐藏执行 | 端到端通过 |
|---|---:|---:|---:|---:|
| 旧 K：v3 受限规格＋官方模板＋执行反馈，重新运行 | 18/18 | 18/18 | 18/18 | **15/18（83.3%）** |
| 新 v6：默认 auto 检索，共同预算 6000 | 1/18 | 1/18 | 1/18 | **1/18（5.6%）** |
| 新 v6：strict hybrid 首轮偏差实验，共同预算 6000 | 1/18 | 1/18 | 1/18 | **1/18（5.6%）** |

编译与开发检查按请求计：存在一个成功候选即计通过，不是所有候选通过率。端到端要求成功生成、开发检查和隐藏正反例全部通过；生成失败仍进入 18 次请求的分母。

这里是 **6 个独立语义任务，每个重复 3 轮**，不是 18 个独立漏洞，更不是项目级准确率。没有依据用这组小样本推算跨项目性能或统计显著性。

旧 Python XSS 的三轮均能生成、编译、通过开发样例，但在旧隐藏 Flask `@app.get` 场景漏检；这个既有框架建模缺口保持原样，没有替换测试代码。新方案目前大量失败发生在隐藏检查之前，无法据此判断其潜在检测逻辑是否更好。

旧 K 的实际隐藏位置统计为 TP=21、FP=0、FN=3，条件精确率 100%、召回率 87.5%，包含重复轮次。新 auto 仅一条规则执行隐藏检查，TP=1、FP=0、FN=0；strict hybrid 也仅一条，TP=2、FP=0、FN=0。**不能把新方案这一条成功规则的条件 P/R 宣传为总体 100% 准确。** 执行覆盖率只有 1/18。

## 4. 对照条件与限制

- 沿用 Python/JavaScript × eval/SQL/XSS 的原 requirement、purpose、strategy 与原隐藏位置评分器；隐藏源码/变体/标签的 SHA256 全部与旧数据一致。
- 请求模型 `deepseek-v4.1-flash`，实际返回 `deepseek-v4-1-flash-260910`；temperature 0、thinking disabled；输出预算 6000、最多两个候选，24 次实际模型请求、100000 tokens、300 秒阶段预算、90 秒请求 timeout。
- **产品当前默认输出预算是 8000。本次为公平沿用旧 6000，未测完整默认 8000 配置。** 新组使用默认 auto 检索和 v6 主生成路径，称“默认链路在共同预算下”，不能称全量默认配置成绩。
- CodeQL CLI 2.23.5；Python 库 4.0.10、JavaScript 库 2.4.0；前后核对提示词、冻结语料、向量及隐藏数据身份。
- 旧 K 使用旧任务/轮次当时的冻结检索结果；新 v6 固定当前公共库 180 个文档的 allowlist，含历史公共条目及本批新增材料。后续资料入库不影响本次召回范围。
- 为适配当前必需源码契约，每类任务建一个公开普通处理函数开发项目，移除标签。两组共用同一个实际静态扫描基线；旧链路维持不主动读源码，新链路可以读取开发源码。隐藏别名、行偏移、安全反例和位置金标不供生成器读取。
- **这是整条方案的比较。** 语料、读取能力、生成约束和验证步骤均不同；无法把退化单独归因于 embedding 或双库，也无法证明关闭其中一项即可恢复。
- 两个 case Worker，同一数据库串行使用，查询 `--rerun`。首次旧 K/strict hybrid 每轮随机组序；auto 是随后运行的新组，复用已完成的全部 18 个旧 K 对照。缓存、顺序及旧检索回放限制严格速度比较。
- 首轮脚本使用 strict hybrid，与产品默认 auto 不符；完整保留负面成绩和偏差文件，随后追加 18 次真实 auto 请求，未改提示词或隐藏测试。旧控制记录仅复制引用，**共 54 次新生成请求、95 次实际模型调用**，没有把复制记录重复算入测试量。
- 研究账号禁用登录；测试阶段隔离、规则未批准或发布。没有进行 GUI 测试，也没有混入真实用户上传项目。

## 5. 失败原因与证据

### 5.1 默认 auto 的 17 次失败

| 失败阶段/类型 | 请求数 | 当前解释 |
|---|---:|---|
| 重复源码取证停滞 | 9 | 模型反复请求同文件同窗口，服务端防重复门提前终止，未进入生成 |
| 上下文预算超限 | 5 | 知识记录、出处/验证元数据及候选反馈装配后超过 40000 字符 |
| 两个候选编译/契约/开发检查未通过 | 2 | 观察到无效 CodeQL 类型 API 与生成策略契约不匹配 |
| 关键语义证据不足 | 1 | 语义就绪门阻断；需进一步区分合理弃权和解释流程错误 |

strict hybrid 的 17 次失败为：上下文 8 次、重复取证 7 次、筛选后没有可用向量材料 2 次。auto 去掉了这两个强制向量阻断，但整体仍然 1/18，因此问题不止是检索模式配置。

### 5.2 上下文工程没有达到设计目标

保存的材料尺寸表显示：JavaScript XSS 的知识对象格式化 JSON 为 **40895 字符**，其中正文仅 16943；eval 为 **51086**，正文仅 19914。仅知识对象已可超过 40000 字符生成上下文门，尚未加上目标、源码解释、告警和反馈。XSS 中一个 Code injection 范例正文 918 字符，整个对象却达 13105 字符。

这说明出处和验证元数据进入模型上下文的体积过大。保留完整产物是必要的，但给模型的视图应保留关键原文和简短身份引用。当前实现直接携带完整对象；较小材料在重试加入完整候选/诊断后也可能超限。扩大输出预算不能直接修复这个独立字符门。

### 5.3 主动源码工具缺少有效的进度反馈

首轮 Python XSS 记录中，模型连续两次要求读取 `app.py` 1–5 行，理由分别是确认完整来源和确认处理函数/防护；实际窗口相同。防重复机制确实阻止了无限循环，但流程没有让模型有效复用已读结果、明确缺失事实并进入 ready。auto 中相同类别占 9/18，是优先修复的流程缺口。

### 5.4 新路径丢失了旧路径最有价值的生成约束

旧 K 走 `generate_from_spec`：LLM 产出受限 DetectorSpec，服务端选择固定官方 QL 模板。v6 主路径重新自由生成 QL，规格路径仅留作实验开关。增加背景知识后，仍出现 API 猜测：

- JavaScript SQL 第一轮两稿分别对泛化节点使用不支持的 `getACall()`、`getMember(string)`、`getAMember(string)`。
- Python eval 第三轮先发生策略契约不匹配，后一稿使用不支持的 `Flow::CallNode.getFunc()`、`Function.getAReference()`、`Assign.getASource()`。

因此当前改造同时增加了材料/取证开销，并取消默认受限输出的可靠性。它不是在旧 K 上仅替换一个更强 RAG 模块。

### 5.5 角色路由和有效范例覆盖仍有缺口

当前确定性家族路由包含 CodeInjection、SQL、Path、Command，XSS 会走通用选择；观察到 XSS 召回 Code injection/Stored XSS 等不完全对应的范例。

JavaScript SQL 的严格过滤结果没有可用索引范例：历史范例向量身份过期，新固定版本范例的官方开发验证标记失败并被排除；参考 API 文档本身有有效向量。auto 可退回 BM25 继续，但不会自动补齐范例质量。应分别核实编译、测试环境和真实预期不匹配，不能把官方测试失败直接解释为规则语义错误。

| 指标 | 旧 K | 新 v6 auto | 新 v6 strict hybrid |
|---|---:|---:|---:|
| 生成链路时间中位数 | 38.46 秒 | 7.60 秒 | 9.18 秒 |
| 含隐藏评价时间中位数 | 50.71 秒 | 7.60 秒 | 9.18 秒 |
| 实际模型调用 | 22 | 37 | 36 |
| 输入 tokens | 126953 | 132852 | 113473 |
| 输出 tokens | 17143 | 29636 | 26575 |

**新组的较短中位数来自早期失败，不能称速度提升。** auto 唯一成功的 JavaScript SQL 生成/验证链路耗时 110.78 秒，再加隐藏执行 10.97 秒，共 121.75 秒。新链路含原项目单规则验证，旧检索又使用回放；这个单例同样不能当严格同成本速度因果结论。

## 7. 下一步改进优先级

本次仅比较和诊断，没有在看到结果后边改边重新计分。建议下一批按以下顺序实施，冻结本次结果为回归基线：

1. **恢复受限生成主路径。** 保留 v6 三类输入，让源码理解/RAG 辅助选择经过编译的检测模板和类型化规格；现成模板不足时再做受控 source/sink/model 扩展，自由 QL 单列实验。目标先恢复旧六类任务至少 15/18，官方复用与新增覆盖分别计。
2. **压缩模型视图并修正取证循环。** 全文出处/测试资产放不可变产物，模型只拿必要 API/规则原文、短身份、源码事实和当前差分诊断；逐轮重装上下文，不能截断关键路径。已读窗口作为最新工具观察，重复请求反馈明确进度/缺口，再以有限预算纠正，不直接无限重试。目标消除当前已定位的预算溢出和重复停滞。
3. **补齐角色与质量门。** 新增 Reflected/Stored XSS 路由；检查每类任务可用 reference/example 及索引身份；官方范例编译与环境/测试结果分列，先修复资料覆盖再比较 hybrid/BM25。目标让材料准备失败可以提前诊断且有明确补充方向。

恢复后，分别消融受限输出、源码理解、双集合、向量检索和反馈，禁止一次同时替换后宣称某一项有效。旧测试集是回归门；继续使用未建模 API 和独立真实项目测试泛化，避免针对这六类任务拟合。
