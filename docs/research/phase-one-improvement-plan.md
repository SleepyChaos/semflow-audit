## M1：模型可靠性与调用可观测性

### 原因与现状

- 默认 `AI_MAX_OUTPUT_TOKENS=6000`；本轮Python遮蔽复审和JS原型污染修复各有一次不完整输出。已知是完成状态不满足契约，但当前没有保存该次finish_reason/思考token细分，**不能仅凭总token断定唯一原因**。
- `CompatibleModel` 已正确拒绝不完整响应，并设置SDK `max_retries=0`；因此本项重点是观测与受控恢复，不是重新实现已有拒绝机制。
- 当前 `calls/input_tokens/output_tokens` 是阶段聚合，缺少单次请求耗时、实际模型与失败类别，无法可靠比较配置。

### 目标

保留“失败不等于安全”的语义；使请求成本、耗时、预算和失败原因可追溯。在固定输入上判断调整预算是否减少失败，避免无限提高预算或无限重试。

### 工作拆分

| ID | 修改内容 | 交付/标注 |
|---|---|---|
| M1.1 | 增加独立调用记录，关联stage、purpose、attempt、prompt/schema版本、请求模型、响应模型、预算、耗时、finish_reason、token细分与结构化error_code | 已实现并验证；未返回usage记录unknown，不填0假装免费；不保存密钥/请求头/默认完整代码 |
| M1.2 | 配置按review/repair/rule区分预算与超时，并冻结每次stage的有效配置快照；保留全局默认兼容 | 已实现并验证；同阶段重试用显式覆盖配置并记录差异，不静默换模型 |
| M1.3 | 输出截断允许最多一次显式恢复；上调预算必须受阶段总调用、总token、总时长上限约束 | 已实现并验证；从完整原输入重新生成，不拼接半段JSON，不合并两个不完整补丁 |
| M1.4 | 区分length、timeout、provider_error、schema_invalid、evidence_invalid等；网络错误与结构纠错用不同策略 | 已实现并验证；认证/不支持参数等配置错误直接失败；证据伪造不自动补成真实证据 |
| M1.5 | 可选思考模式仅在该provider/model完成能力验证后启用；不向所有兼容接口统一发送特殊参数 | 条件增强；当前不假定用户端点支持哪些模式，也不先规定必须关闭思考 |

修改范围：`adapters/ai/provider.py`、`core/audit_config.py`、调用记录持久化及迁移、阶段repository/API输出；通用调用策略留在适配器，图节点只消费结果。M2的结构纠错与M1的截断恢复共用总预算，不能形成两个独立循环。

### 验收

1. 重放stop/length/缺usage/timeout/provider异常：每次尝试有记录；原失败保留；usage未知与零值有区别；不完整响应不得写成成功结论。
2. 真实模型使用相同样本与同一prompt，先固定默认6000作为对照，再固定一个候选配置。各轮记录所有尝试，比较失败率、端到端p50/p95、token和完成后的正确性；**本轮基线不回填重跑成绩**。
3. 原两个失败输入各三轮：目标是每轮在总预算内完成，且独立标签/oracle正确。若仍失败，交付必须明确报告失败；不能为了“全绿”放宽结构和证据校验。
4. 性能边界：只有候选配置减少失败且未降低正确性，才建议作为新默认；总耗时或token明显上升必须列出代价，不预承诺固定提速比例。

## M2：分离锚点评价、候选评价与新增漏洞

### 原因与现状

- `ReviewResponse.findings` 同时表达已有候选复审与新发现。没有静态候选的良性锚点也通过“补充候选”保存，产生pending实体并标为new_location。
- `shadowed_json.js` 第1轮因补充发现缺少真实file/line失败；另外两轮虽然正确排除，却创建了AI候选。这会干扰漏洞数量、增量收益和后续修复选择。
- JS同名eval样本存在独立XSS，说明目标CWE排除和文件其他发现可以同时成立；单个supported/excluded不能表达全部范围。

### 目标与契约

| 对象 | 必须指向 | 允许结论/字段 | 对漏洞数量的影响 |
|---|---|---|---|
| anchor_assessment | 当前stage的anchor_id | reviewed/excluded/insufficient、理由、实际证据；明确被评价的weakness | 不创建Candidate，不算新增漏洞 |
| candidate_assessment | 当前stage的candidate_id | supported/excluded/insufficient/pending、理由、实际证据 | 更新模型建议，不替代人的Decision |
| new_finding | 当前范围内真实主位置 | CWE或unknown、描述、来源、related_target、真实file/line及已取得源码证据 | 创建待确认候选；new_location仅表示位置，不证明新根因 |

锚点的reviewed表示完成检查但没有可确认漏洞结论；excluded必须说明排除哪个目标操作/CWE；证据不足用insufficient。`weakness=unknown`不允许被当作已判明类别参与CWE准确率统计。

### 工作拆分

| ID | 修改内容 | 交付/标注 |
|---|---|---|
| M2.1 | 将最终响应拆为上述三类数组；新增严格位置结构；action=tool/final的互斥规则保持 | 已实现并验证；review.v2 prompt/schema，不覆盖历史v1 |
| M2.2 | 锚点评价独立持久化；候选记录保存CWE、来源和模型建议；人工状态仍独立 | 已实现并验证；无静态告警的正常锚点可完成复审，不需要制造漏洞 |
| M2.3 | 保存前一次性验证全部对象的ID归属、范围、证据引用和主位置；事务提交，避免半个成功结果 | 已实现并验证；未知/遗漏对象标记未评估，不能自动excluded |
| M2.4 | 仅格式或缺字段错误允许一次明确反馈纠错；不自动补造位置、不批准跨任务证据 | 已实现并验证；反馈包含受限契约错误，重新校验完整响应；预算由M1统一控制 |
| M2.5 | 报告/API区分已评估锚点、待确认新发现、模型建议与人工决定；按CWE评价 | 已实现并验证；同名eval可excluded，同时单独报告XSS supported |
| M2.6 | Alembic向前迁移及v1读取兼容；历史字段缺失记legacy/unknown | 已实现并验证；不凭标题自动猜历史CWE，不修改原始历史/已有确认 |

修改范围：`contracts/stages.py`按职责拆分、`services/review.py`拆出校验/保存职责、`workflows/review.py`有限反馈分支、`prompts/review.v2.txt`、`persistence/stage_models.py`及迁移、报告/API；GUI仅增列后续验收，不运行GUI测试。

### 验收

- 良性同名函数+JSON输出：得到锚点excluded且新增Candidate=0；合法XSS发现仍可单独创建候选。
- 直接eval外部输入、常量eval、同名函数、跨CWE组合、缺字段、未评估、伪造证据、跨任务ID、越界位置各设独立代码/API测试。
- 事务内任一对象无效时，不写入部分新增候选；结构纠错至多一次，失败保留原因。
- 同一输入v1与v2固定预算各三轮：比较结构失败、候选数量误增和目标CWE结论；不把“成功返回空数组”算正确排除。
- pending/insufficient/模型supported仍不得自动进入修复；人工确认门保持。未评估锚点在报告中可见。

## M3：RAG知识与规则独立验收

### 原因与现状

- 检索器已有Haystack BM25和可选pgvector融合能力；本轮没有embedding配置，实际是BM25。问题主要是知识范围与评估设计，**不是完全没有RAG实现**。
- 当前两个种子知识文档，固定字符切块可能拆开API、完整QL示例及前提。生成的eval规则与知识模板近似。
- 三条规则编译/自生成样本通过，但独立8例表现说明它们只是名字匹配锚点；若当漏洞检测器评分，P=0.5、R=0.75。

### 目标

先建立规则用途、可信知识与独立测试，再比较检索方案。优先测量“现有CodeQL覆盖缺口能否被补上”，而不是提高模板复写通过率。

### 工作拆分

| ID | 修改内容 | 交付/标注 |
|---|---|---|
| M3.1 | 增加purpose：review_anchor / vulnerability_detector / framework_model；purpose与生成strategy（model/extend/new_query）分别保存 | 已实现并验证；锚点覆盖、漏洞P/R、框架建模单测分别评价 |
| M3.2 | 创建知识清单与导入管线：来源、许可、语言、框架、CWE、CodeQL依赖版本、hash、更新时间、可信级别 | 已实现并验证；优先固定版本官方API/查询源码与合法框架文档，项目自维护知识明确标注 |
| M3.3 | 按章节、API签名、完整示例及限制一起切块；版本/语言过滤、索引去重、检索上下文去重 | 已实现并验证；复用现有Haystack/pgvector，不自研检索引擎 |
| M3.4 | 在BM25之上启用已验证的embedding，再比较向量/融合；重排仅在融合基线确有不足后引入 | 条件增强；当前凭据不等于已提供embedding服务，缺配置保持真实BM25标签 |
| M3.5 | 输出coverage_gap、purpose、知识引用与限制；执行编译反馈、人工样本门、独立holdout、发布门 | 已实现并验证；knowledge引用必须匹配真实检索条目，拒绝未知固定版本API |
| M3.6 | 验收结果拆成compile/generated_fixture/independent_holdout三层；绑定query/modules/dependencies与数据集版本hash | 已实现并验证；只有自生成样本通过时标未独立评估；模块或依赖变化使旧验收失效 |

知识初批目标：不少于20个有来源和固定版本标注的条目，涵盖Python/JS常见source、sink、sanitizer和框架建模；每条完整性优先于数量。试验需求至少12项，覆盖动态执行、SQL注入、XSS及自定义框架source/sink；各自准备含别名、遮蔽、净化、跨文件包装器的独立正反例。知识库不得包含测试项目修复答案或目标位置金标。

修改范围：`adapters/retrieval/knowledge.py`拆出导入/切块/索引职责、`persistence/knowledge_models.py`及迁移、`contracts`与`prompts/rule.v2.txt`、`services/rules.py`、CodeQL验证适配器、规则/API报告。框架建模变化仍放在固定版本QL模块内，不扩成自研静态分析器。

### 验收与实验

1. 无RAG仅作为隔离研究基线；生产生成仍要求有效来源引用。BM25、向量、融合使用同一知识版本、模型、预算、需求与holdout。编译反馈有/无作为第二轮消融，避免首轮组合过多。
2. 检索评价Recall@k/MRR、引用命中与版本正确性；生成评价编译率、所有尝试通过率、反馈次数、耗时/token；漏洞规则额外评价独立P/R及相对CodeQL基线新增TP/新增FP。
3. 最小功能门：语言/owner/版本隔离、不存在引用拒绝、反例误命中、别名漏检、hash变更失效、未评估规则标识、人工发布门，都必须通过代码/API测试。
4. 准备的12个独立需求至少各三轮；失败纳入分母。检索方案若不改善独立结果，报告无增益并保留更简单配置；不为完成计划预设“混合一定更好”。
5. 发布验收按purpose和数据集预先定义：复审锚点必须显式展示限制；漏洞检测器独立例中不得命中已标定的安全反例；框架模型必须在source/sink集成规则上检验。小集通过只是发布回归门，不宣称总体精度100%。

## 阶段完成与标注规范

状态统一使用：`计划待实施 → 实施中 → 代码/API验证通过 → 真实模型对照完成 → 可验收`，条件增强允许`等待服务配置`；不把未跑测试标成通过。

- 第一交付：M1调用记录、受控恢复、配置对照；数据能解释失败后再进入M2。
- 第二交付：M2版本化契约、迁移与报告；良性锚点不产生新增候选，真实漏洞证据门有效。
- 第三交付：M3规则purpose、知识清单、独立例及检索对照；先证明功能正确，再决定是否切换默认检索。
- 每次交付报告原因、修改文件、测试、已知限制、回滚方法；数据库迁移与prompt/配置变更分开注明。
- 保存2026-10-03原始基线；新增结果使用新版本、输入hash和配置快照。CLI评估完成后补充GUI清单供用户手动验收。
