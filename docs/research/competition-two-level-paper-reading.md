## 2. SemTaint：怎么写分析过程介入

### 2.1 为什么适合

它让 Agent 补端点、未解析调用关系与第三方流摘要，并将事实交给 CodeQL；不是单次查询内部的实时 LLM 回调。PDF 第 5 页图 1 展示各阶段和事实产物，适合观察“静态分析输出什么问题、Agent 返回什么、结果再次进入哪里”。

### 2.2 正文结构

以下为阅读版 PDF 的章节编号与中文概括；HTML 使用罗马数字，个别图号不同。

| 章节 | 组织作用 |
|---|---|
| 1 引言 | 给出分析缺口和贡献 |
| 2 动机案例 | 用实际代码展示静态分析为何中断 |
| 3 总体方案 | 展示模块、数据及协作流程 |
| 4 核心方法 | 定义污点事实、端点推断、调用解析、库摘要与执行接口 |
| 5 评价 | 设置数据与对照，研究检出、定向推理、消融、未知漏洞及有效性威胁 |
| 6 相关研究 | 说明和已有方法的关系 |
| 7 总结 | 收束方法与结果 |

### 2.3 针对本项目的写作建议

以下是拟研究路线的写作设计，不是论文原文或当前已完成能力：

1. **问题定义**：原生污点传播对哪些表示转换/保护条件缺少表达；模型错误如何改变漏报与误报。
2. **动机案例**：一个陌生封装或“先检查、后转换”的案例，画出原始分析和期望分析的区别。
3. **语义表示**：有限状态、转换条件、保护作用域、未决事实及源码绑定。定义清楚 LLM 输出的对象。
4. **协同算法**：固定诊断查询 → 待查需求 → LLM 候选模型 → 绑定核验 → 状态分析 → 下一轮。
5. **CodeQL 落地**：外部事实桥接、StateConfigSig、附加流步骤、状态相关 guard/屏障，以及旧状态边的处理。
6. **验证**：人工模型上限、普通传播/净化摘要、条件化模型与消融；未见项目和条件组合验证。
7. **局限**：动态调用、运行时环境、语义证据不足、状态数量和预算耗尽。

论文或创新章节要交付具体模型定义、查询接口、算法步骤和反例，而不仅是一张 LangGraph 流程图。相关实验应解释“改动哪一类分析关系带来了收益”。

先读第 3 节和图 1，再读 §4.3.2 的定向调用解析、§4.5 的摘要处理、§4.6 的外部事实接口和 §5.4 的消融；最后阅读附录的 Agent 走查。

创新边界：SemTaint 已有按需调用图修复和外部事实迭代。本项目的状态语义/保护失效设计需要进一步差异核查与实验，不能把其已有机制换名作为原创。

## 3. IRIS：怎么写端到端审计框架

### 3.1 为什么适合

它组织候选 API 提取、LLM 规格推断、CodeQL 分析及上下文告警复审。PDF 第 4 页图 3 把每个阶段的输入和输出放在图中，适合学习可解释的链路描述。它仍改变了端点规格，因此不是纯粹并行运行两个工具。

### 3.2 正文结构

| 章节 | 组织作用 |
|---|---|
| 1 引言 | 提出问题、思路与贡献 |
| 2 动机案例 | 解释缺失规格和复审需求 |
| 3 框架 | 先定义问题，再说明提取、推断、检测、复审与指标 |
| 4 数据集 | 专门交代真实项目、构建与标签核验 |
| 5 实验 | 评价已知/未知漏洞、规格质量和组件消融 |
| 6 相关研究 | 定位框架与既有方法 |
| 7 总结及局限 | 解释结论和边界 |

### 3.3 针对本项目的写作建议

以下组织的是 SemFlow 的现有系统与拟补证据，不认为 IRIS 包含修复、RAG 或我们的独立 Scout：

1. **需求与范围**：目标用户、支持语言、项目输入、发现/确认/修复/规则输出及预算约束。
2. **框架总览**：按“候选来源—证据复审—人工确认—下游产物”组织；区分 CodeQL 与独立 Scout 的职责。
3. **阶段合同**：不可变源码快照、候选 ID、证据引用、任务状态、失败/未决状态和重试规则。
4. **发现与复审**：覆盖任务、粗筛、合流、去重提议、证据门控、未知前提及人工决定。
5. **语义辅助修复**：项目/流程/修改点理解、受限取证、候选 diff、测试反馈；报告已做验证的真实边界。
6. **RAG 规则生成**：知识与范例双集合、实际源码输入、查询检查、正反例与单规则执行、发布门。
7. **评测协议**：三个能力分别评价，数据准入/隔离、统一裁决、强基线、失败与成本记录。
8. **实证与讨论**：准确率、召回、成对正确率、速度和 token；报告未决和跨项目限制。

先看第 3 节和图 3，再看第 4 节数据构建、第 5 节实验和附录 A 的输入/提示/QL 实现说明。借鉴其问题—模块—实验的对应关系；无需为竞赛强行声称发布新基准。

边界：IRIS 以 Java 检测为主，本项目当前以 Python/JS 为主；其论文数字不与我方 OWASP 抽样数字直接做提升比较。它没有证明 SemFlow 的业务语义修复或 RAG 生成正确性。

## 4. 两个层级如何进入同一份竞赛作品报告

| 原稿章节 | 可以写入的内容 | 应有证据 |
|---|---|---|
| 作品概述 | 用户痛点、双引擎及三个能力方向；区分已实现与计划 | 当前支持范围与完整流程 |
| 设计与实现 | 先讲系统架构，再设独立小节解释分析中段协同 | 源码模块、阶段合同；协同原型完成后补模型与查询细节 |
| 测试与分析 | 框架能力测试和核心协同方法测试分别报告 | 固定版本、独立样本、基线/消融、耗时/成本及失败 |
| 创新与特色 | 系统层的工程整合与方法层的条件/状态机制分别说明 | 实现与因果消融；设计候选明确标注 |
| 竞品分析 | 功能边界表＋可比任务上的效果表 | 不同语言/数据集/作者自报分层 |
| 总结 | 当前交付、局限与下一阶段目标 | 和前文能力状态一致 |

建议将框架层作为当前作品的主体，将中段协同作为正在深化的方法路线。其实现与独立验证完成后，再把对应内容从设计目标改为已实现创新。

这两个层级可以组成一份完整报告。若后续分别发表，两篇产出必须有不同的研究问题、主要贡献和新增实验，并披露共同系统基础，不能重复包装同一批结果。

## 5. 可用的暂定标题与优先阅读顺序

- 方法层暂定：**面向条件语义与保护失效的 LLM–CodeQL 协同代码审计方法**。

标题是本项目写作候选，不代表已经达到发表条件。当前修复以语义辅助为目标，标题与正文应避免宣称已证明业务行为完全一致。

推荐先花一轮阅读理解 IRIS 的第 3–5 节，确定作品报告的系统叙事；再读 SemTaint 的第 3–5 节，确定核心方法需要补交什么定义、实现和消融证据。
