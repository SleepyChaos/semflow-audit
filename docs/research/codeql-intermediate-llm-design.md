# 在 CodeQL 分析中间介入 LLM：语义状态与分轮查询设计

日期：2026-10-08。状态：详细设计建议，未实现或验证检测效果。前置研究：[创新边界](codeql-llm-interaction-research.md)。

## 1. 可以介入哪一层

CodeQL 先提取源码形成数据库，再编译和执行 QL 查询。调用关系、数据流和污点传播等许多分析由 QL 库关系定义、由求值器计算，并不都是提取数据库时永久写入的字段。查询内部实际执行次序由编译器优化，不能把概念上的分析阶段视为可暂停的固定流水线。

本方案保留源码提取事实，通过显式的多轮查询改变分析关系：

```text
源码 → 一次提取数据库 D
         ↓
固定诊断查询 Qd(D, M_t) → 语义需求 W_t
         ↓
LLM 局部理解 → 候选事实 H_t
         ↓
固定绑定/验证查询 Qv(D, H_t) → 有效模型事实 V_t
         ↓
固定状态分析查询 Qa(D, M_t ∪ V_t)
         ↓
新待查需求 → 下一轮；达到停止条件 → 最终路径与 SARIF
```

这里的介入位置是**数据流传播和保护条件的定义/精化**，发生在最终告警生成之前。单次查询完成后才能注入下一轮事实；不是单次 CLI 求值中实时调用 HTTP，也不是从求值器内部检查点恢复。

官方公开接口提供外部关系和数据扩展，没有公开的“执行某谓词时调用 LLM”标准回调。若坚持每传播一条边就同步询问 LLM，需要自行实现求值层或更换支持语义 oracle 的分析框架，工程规模与当前复用成熟框架的要求不符。

## 2. 三种介入点及优先级

| 层 | 让 LLM 解决的问题 | 对 CodeQL 分析的实际影响 | 选择 |
|---|---|---|---|
| 调用绑定 | 动态调用可能进入哪个真实函数/回调 | 自定义查询的跨函数流连接；具体形式取决于语言库入口 | 配套能力，SemTaint 已有直接先例 |
| 转换语义 | 陌生 API 如何传播数据、改变表示或安全属性 | 带状态的附加流步骤与有限状态转换 | 优先试点 |
| 保护语义 | 校验保护哪个值、何种状态和哪些分支 | 状态相关屏障或 guard；在 sink 前保留/消除特定风险状态 | 与转换语义一起试点 |

无需假定所有原生查询自动受影响。模型只有被查询导入并使用时才生效；先改一个选定 CWE 的查询配置或受控适配查询，原生 suite 保持独立对照。

## 3. 核心：LLM 提出语义转换，CodeQL 传播状态

普通污点模型容易只表达“传播”或“截断”。状态模型可记录有限语义属性，例如某个值仍受外部控制、目前具有哪类编码、哪种校验在当前位置成立。

LLM 对陌生 API 提出结构化转换：

```text
真实 API、输入槽位、输出槽位
调用条件、输入状态、输出状态
可能失效的保护属性
对应源码/版本资料、未决前提
```

CodeQL 负责绑定实际节点、检查可表达条件、应用固定转换模板、沿数据流传播状态。LLM 不逐行执行程序，也不直接给每条路径贴最终安全标签。

### 3.1 表示与校验的示例

```python
p = request.args["file"]
if validate_relative_path(p):
    q = decode_path(p)
    return read_file(q)
```

假设经核查 `validate_relative_path` 检查的是当前字符串表示，而 `decode_path` 可以改变路径分段，则“原表示通过校验”不能直接推广到解码后的值。需要检查最终表示是否重新满足所需路径约束。

可用有限状态记录：外部可控、当前表示的校验已成立、变换后需重新校验、语义未决。解码使有关校验事实失效，sink 在仍缺少所需保护时产生候选。

并非任何解码都造成漏洞：实际转换实现、validator 的保证、绝对路径处理及其他保护都必须核查；运行时文件系统条件超出模型时保持未决。本例展示“保护会失效”的机制，不给目标程序预设金标。

### 3.2 场景相关编码的示例

同一字符串经过 HTML 文本编码，可在指定 HTML 文本上下文满足部分保护要求；在脚本、URL 或其他上下文中的要求应单独建模。模型需要记录处理所针对的上下文，sink 检查需要的属性，避免全局 sanitizer 直接删除所有后续流。

试点可选一个可独立标注的表示转换机制，不同时实现全部 Web 编码语义。

## 4. 外部事实如何进入查询

本机 CLI `2.23.5` 的帮助已确认支持：

```text
codeql query run analysis.ql --database=<同一数据库>
  --external=<外部谓词名>=<本轮事实.csv>
  --output=<本轮结果.bqrs>
```

命令为接口示意，不是已执行的实验。结果可由 `bqrs decode` 解码；最终告警需要配置解释/导出步骤。CLI 支持该参数不表示现有 `run_query` 适配器已接入，本项目目前仍主要使用 `database analyze`。

固定 QL 桥接逻辑把 CSV 中的事实加入 `isAdditionalFlowStep` 或状态相关 guard/屏障。事实变化可以复用查询程序；是否复用编译结果和内部计算缓存需测试，不承诺只计算新增边。

官方机制参考：[query run](https://docs.github.com/en/code-security/reference/code-scanning/codeql/codeql-cli-manual/query-run)、[external 注解](https://codeql.github.com/docs/ql-language-reference/annotations/)。SemTaint §IV-F 已利用外部谓词 CSV，因此外部事实接口本身不算新贡献。

## 5. 状态分析接口已存在

CodeQL 官方提供 `DataFlow::StateConfigSig` 和 `GlobalWithState`，接口包括：

```text
isSource(node, state)
isAdditionalFlowStep(node1, state1, node2, state2)
isBarrier(node, state)
isSink(node, state)
```

这些是接口示意，不是完整可编译查询。[官方 flow-state 教程](https://codeql.github.com/docs/codeql-language-guides/using-flow-labels-for-precise-data-flow-analysis/)说明状态传播和状态相关屏障；[JS 接口](https://codeql.github.com/codeql-standard-libraries/javascript/codeql/dataflow/DataFlow.qll/predicate.DataFlow%24Configs%24StateConfigSig%24isAdditionalFlowStep.1.html)给出状态转换签名。

本地固定库已有真实用例：

- Python `4.0.10/semmle/python/security/dataflow/NoSqlInjectionQuery.qll`：字符串→字典状态转换，以及旧状态的屏障处理。
- JS `2.4.0/semmle/javascript/security/dataflow/PrototypePollutingAssignmentQuery.qll`：状态转换和状态相关 barrier/guard。

新增转换边不会自动替换原有边：若旧状态仍能通过默认流边到达输出，会同时保留两条语义路径。保护相关状态的消除必须由经过核验的屏障/guard 配合实现；不能用附加边的存在假定旧状态已经消失。这是原型必须检查的具体风险。

状态类型采用人工定义的有限集合，LLM 选择关系和转换参数。先限于少量属性，避免任意自然语言状态、无限模型 ID 和笛卡尔积导致查询成本失控。复杂业务权限的对象身份与合同可用独立关系表，不能全部塞进流状态。

## 6. 待查需求 W_t 如何形成

待查列表可以包括：

- source 附近或 sink 反向有界探索中的未建模调用。
- Agent 指出的真实可疑操作缺少 source、sink 或传播关系。
- 保护条件已经出现，但校验值、使用值或状态对应关系不明确。
- 候选模型与已核验模型产生不同路径结论。

每项只携带实际符号、局部源码引用、输入状态、下游要求、未知前提和必要资料。共享证据持久化引用，下一轮只注入新增事实和失败原因，避免完整历史反复堆入上下文。

没有告警不能直接推导“发生漏检”；partial flow 不能保证发现所有缺口。source/sink 都缺失、尚未分析的文件或复杂动态关系仍需 Scout 和覆盖记录兜底。

## 7. 绑定与核验的边界

事实以源码快照、相对路径、完整位置、节点种类和输入输出槽位绑定。LLM 只能引用已导出的候选标识，桥接查询检查唯一对应；未找到、匹配多个或快照变化均不采纳为已核验事实。跨轮不要假定内部 QL entity ID 可在其他数据库稳定复用。

符号存在、位置匹配与模式条件成立能自动核查；外部 API 的完整功能语义并不因此获得证明。复杂事实仍需独立资料、开发正反例或人工核验。证据不足保持假设状态，尤其不能据此删掉真漏洞路径。

每轮模型与结果冻结保存。新增传播事实、删除/修改保护事实可能产生非单调结果，不能简单合并各轮 SARIF；最终模型需重新求值，旧结果保留为历史。预算耗尽明确输出尚未解决的需求。

## 8. 初始验证与创新主张

先固定一个语言、一个 CWE 和一种表示/保护失效机制。验证：

1. 固定诊断查询是否能产生正确的语义需求。
2. 外部事实的增删是否确实改变目标查询关系和路径。
3. 状态转换、旧状态屏障及分支 guard 是否正确。
4. 人工模型能否区分独立安全/不安全对，再换 LLM 推断模型。
5. 跨调用者、配置、版本能否迁移，以及成本是否可接受。

消融至少包括原生 CodeQL、现有并行＋复审、普通传播/净化摘要、人工状态模型、LLM 状态模型，以及移除失效转换/条件核验/定向取证。正式样本与开发样本隔离。

可能的方法贡献是：**LLM 识别有条件的语义转换与保护失效，CodeQL 在路径中传播和检查这些状态，分析结果按具体语义需求反馈下一轮理解。**

Flow-state、CSV、迭代调用图和 LangGraph 都是已有组件；能否形成论文创新，要由与 SemTaint 等强基线的方法差异及未见项目实验决定。本次没有生产改造、付费模型调用或能力测试。
