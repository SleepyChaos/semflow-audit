# 当前项目论文可行性与研究聚焦评估

评估日期：2026-10-04；代码基线：`2b1519b`。本次为研究判断与下一步建议，没有新增能力实验，也没有将候选研究贡献视为已完成创新。依据为现有源码、[第一轮消融](rule-generation-ablation-results.md)、[第二阶段结果](phase-two-results.md)及下文一手论文。定向检索不能证明全球首创。

**总体判断：工程和实验基础已形成，方法论文尚缺明确的方法差异及真实泛化证据。** 可以开始论文问题定义、系统实现、实验协议和失败分析的写作；当前结果不足以支持“综合审计能力优于现有方法”的结论。推荐用一个核心方法串起规则生成、审计效果和成本三个评价维度。

| 产出形式 | 当前可行性判断 | 最关键的补充 |
|---|---|---|
| 毕业设计、工程型学位论文 | 已有较好的系统与实验载体；是否满足要求仍取决于学校标准 | 核实真实数据、完成可复现对照、明确工程贡献和研究贡献 |
| 工具展示或实证研究论文 | 有发展基础，尚需补证据 | 可复用工具/数据、真实用户任务或跨项目失效分析；不能只展示 GUI |
| 方法型会议/期刊论文 | 有条件可行，目前尚未就绪 | 区别于既有规格生成与反馈验证的方法、强基线、独立测试、可信标签 |
| 高竞争研究主会论文 | 当前证据不足，不宜预估录用概率 | 具有一般性的研究发现或方法突破，以及充分跨项目、跨模型验证 |

**1. 已有结果支撑什么**

- 87 项普通回归与真实四阶段集成证明工程链路具备测试基础；不证明检测准确率。
- 第一轮 162 次可比较请求来自 6 种标准任务和 3 种模拟 API 的组合重复；不能写成 162 个独立漏洞。完整反馈与受限规格有改善信号，但标准模板检出能力主要来自原生 CodeQL。
- Flask 模型扩展将构造样例从 1 TP/5 FN 变为 6 TP/0 FN，同时增加 1 FP。两种受限生成配置各 3/3 编译通过，但独立样例全通过均为 0/3。这是值得研究的“验证通过但语义不正确”实例。
- 7 条独立告警中，固定上下文与新版复审均三轮判断正确；固定上下文中位时间 4.74 秒，新版 5.28 秒。新版优于旧主动取证，尚未优于简单强基线，且去重单独使用未改善 JSON 误判。
- 19 对完整源码已收集，4 个仓库已有扫描结果，但根因和独立 oracle 尚未完成。材料数量不能替代已验证漏洞数量。
- 所有主要真实模型实验仍依赖一个模型。模型特定效应、顺序和负载影响尚未排除。

**3. 推荐的核心问题与研究边界**

建议题目方向：**面向框架语义缺口的证据约束静态分析模型生成与验证**。

核心问题：在不给出目标漏洞补丁或答案的情况下，如何把框架文档和项目调用证据转换为具有明确适用条件的分析模型，补充真实漏洞覆盖，并控制新增误报及验证成本？

推荐执行链：项目/API 与版本识别 → 检索实际语义证据 → 生成条件化规格 → 静态绑定与冲突检查 → 开发反例验证 → 编译为固定分析模型 → CodeQL 扫描 → 按缺失前提复审。独立测试集只由评测器读取。

第一篇优先聚焦一门语言、2–3 类框架语义缺口，再用另一门语言检验迁移。平台继续支持 Python/JS，不要求论文同时证明全部语言、CWE 和自动修复能力。修复链路可作为独立安全/功能验证的辅助，不作为这一篇的第四主线。

**4. 三项候选贡献及深入方式**

| 候选贡献 | 要解决的具体问题 | 尚需实现或验证 | 对应指标 |
|---|---|---|---|
| C1：绑定项目证据和适用条件的语义规格 | 文档中出现 API 名称，不代表模型适用于当前接收器、版本、参数与响应场景 | 定义统一规格及判定规则，将包版本、符号身份、参数角色、配置/返回上下文、事实来源和未决条件绑定；跨框架采用同一机制 | 规格事实正确率、错误证据拒绝、域外覆盖、真实新增 TP 和新增 FP |
| C2：针对语义边界的反例验证 | 编译成功和模型自造测试容易共同遗漏前提 | 围绕每项条件形成正反对例；使用运行时观察、独立测试或人工核实标签；失败反馈修正规格条件，并测试未见组合 | 编译后语义失败率、反例发现错误的比例、独立端到端成功率、跨项目迁移 |
| C3：按未决条件分配取证预算 | 无差别工具循环增加耗时，也可能引入误判 | 显式记录已支持/已反驳/未知前提，定义取证动作和停止/弃权条件；将通用检索和结构化条件选择对照 | TP 保留、FP 排除、未决率、风险随裁决覆盖率变化、时间/token/调用预算曲线 |

三项均为研究候选。C1/C2 是核心方法；C3 可先作为成本与有效性研究。若第三项没有超越固定上下文基线，就保留负结果与工程实现，不强行写成第三个算法创新。学术贡献可以是“方法＋可信基准＋实证发现”，无需硬凑三项算法。

具体例子：`get/post` 只是路由入口事实；输出为 HTML、JSON、纯文本还是被自定义 response/provider 改写，是另一组事实。不能把“返回 dict”全局当成 XSS sanitizer。应验证在当前框架版本、响应构造与后续处理条件下的输出语义；缺失条件保留未决。

反例分两类：①语义保持变换（别名、包装、跨文件移动）应保持目标检测；②改变一个安全前提（转义、参数化、输出上下文变化）应按经过核实的语义改变结果。变换关系必须先验证适用前提，不能用字符串替换自动制造金标。动态测试只能提供已覆盖行为的证据，不构成所有路径安全的形式证明。

**5. 当前实现特别需要澄清的六点**

1. `flask_spec.py` 的证据校验目前主要是引用文本含指定符号；尚未证明引用语义蕴含所生成条件，也未完成项目 API 清单约束。把引用 UUID 改成“可核验事实与适用条件”才有更强研究意义。
2. 当前 Flask 规格只在 Flask/Blueprint、get/post 这几个预定义选择中生成。简单表驱动方法可能取得同样结果，必须加入无 LLM 的解析/映射基线，不能仅比较自由 QL 弱基线。
3. BM25 本身可以构成 RAG，无 embedding 不等于“没有真正 RAG”。现有实验没有证明分路检索稳定提升。先测证据检索与版本匹配；检索正确后仍失败时，应研究规格/验证而非继续扩大向量库。
4. 无文档时被契约拒绝，只能说明拒绝门槛有效；不足以证明 RAG 提高了语义理解。缺失、错误、过期文档试验需保持相同校验规则，并分别测支持范围与条件成功率。
5. 当前缺口基于固定 python-all 4.0.10。正式研究保留此可复现基线，同时增加论文实验时冻结的新版兼容 CLI/packs 对照。如果新版已支持某接口，该例保留为历史回归，不能当作最新工具新增覆盖证据。本次未验证新版是否已经覆盖。
6. 新版 review v3 主要靠提示词描述取证策略，还不是经过独立评价的条件选择算法。C3 需要可观察的状态与决策、基线及消融。

**6. 建议实验设计**

| 研究问题 | 对照设计 | 关键真值与分母 |
|---|---|---|
| RQ1：生成模型能否补语义缺口？ | 固定/新版 CodeQL、无 LLM 文档解析、人工模型、自由 QL、当前受限规格、C1/C2 | 全部预先纳入的独立需求；拒绝、预算耗尽、工具失败均报告；正确规格与真实检出分开 |
| RQ2：何种验证真正降低语义错误？ | 仅编译、自生成测试、独立开发正反例、针对条件的反例；另比较随机变异 | 所有配置使用相同最终留出集；验证器不接触留出标签；测试/模型预算对齐 |
| RQ3：真实审计是否改善？ | CodeQL、语言适配的 Semgrep/Bandit、同模型直接审计、模型扩展、扩展＋复审 | 根因级匹配；复审只评价已有告警，主动发现另列；所有额外告警需裁决或列未知 |
| RQ4：收益是否值得成本？ | 固定上下文、现有工具循环、定向取证；同预算与质量约束两种比较 | 端到端时间、失败成本、实际 token、未决率；离线生成和后续复用成本分列 |

规则生成按增量组件消融：移除版本/项目绑定、移除条件语义、移除独立反例、替换为通用测试生成。RAG 单列正确资料、错误版本、相似错误 API、缺失资料；测检索 Recall@k、引用事实准确性和端到端结果。给定正确证据的生成实验与完整检索实验分开，有助于定位瓶颈。

QLCoder 输入包含已知 CVE/修复信息，IRIS 的主要实验为 Java，SemTaint 为 JS。只有输入、语言、工具与预算可比时才直接跑原方法；适配版本需明确写“机制复现/适配”，不能拿对方论文数字做我方排行榜。未知漏洞审计中不提供目标补丁；补丁驱动规则学习另设任务，并在未见项目测试迁移。

材料按用途管理：现有 19 对先全部做根因核实和可运行性记录，用于开发试点；正式目标沿用总计划 60–100 对、至少 10 仓库，按项目/家族分组。规则侧争取约 20 个独立 API/规格任务，覆盖多个框架，另构造近似安全反例；这些数量是资源规划，不是发表门槛。复审样本数需根据试点误排率和目标置信区间确定，不能凭几轮重复宣称零漏报。

优先补全样本 oracle：漏洞版本能触发指定安全问题，官方修复版阻断同一路径；同时核对正常行为。官方修复版只对指定根因作为负例，不假设整个项目安全。无需为了本轮实验自动生成修复。确实无法执行的样本采用记录充分的人工根因标注，并与运行时验证样本分层报告。

至少加入第二个独立模型系列，以区分方法效应与模型特定提示词效应。固定配置，交替/随机实验顺序；重复运行只估计随机性，统计推断按独立任务或仓库聚类。报告配对差值与置信区间，避免将重复输出当新增样本。已有规模不足以证明非常小的召回损失界限。

**7. 先解决的实验可信度问题**

- 已查看并据此调试的 Flask 隐藏用例转为开发回归。历史成绩保留其当时的协议；后续必须重新冻结从未用于调参的项目/语义组合，才能称最终留出成绩。
- 文档、补丁、CVE 描述和数据 ID 可能泄露答案。外部知识仅用允许的 API 资料与无答案内容；评价器持有根因、补丁和标签。SastBench 原 ID 带标签的风险沿用总计划过滤。
- 分别报告选定缺口集与更广泛项目集。预选 CodeQL 漏检样本适合测补充能力，但不能代表通用总体召回。
- 在现有静态扩展误报未解决时，不能用 AI 后处理正确掩盖生成规则不正确；分别给原始规则质量和最终流水线质量。
- 单个 HTTP 响应观察只能支撑限定威胁模型中的标签。JSON/纯文本不等于在所有浏览器、代理、前端消费链中永远安全。
- 第三方许可与复现材料需核实；优先发布原创用例、索引、脚本、版本/hash 与允许再分发的资料。模型版本和不可控服务变化列为复现限制。

**8. 下一步决策顺序与停止条件**

| 顺序 | 交付 | 继续深入的依据 |
|---|---|---|
| P0：核实研究对象 | 19 对根因/适用性清单、固定与新版原生能力、失效分类；建立新的留出边界 | 在多个项目发现可由统一机制处理的缺口；若只是旧版本接口缺失，调整问题定义 |
| P1：最小方法原型 | 条件化规格与独立开发反例，先覆盖 2–3 种语义机制；无 LLM 对照同时实现 | 在未见项目优于当前模板及简单解析，收益来自条件而非硬编码答案 |
| P2：真实基准和消融 | 扩大独立任务、仓库与模型；完整报告失败、未决和成本 | 核心收益跨项目存在、错误没有转移为更严重漏报、置信区间支持主张 |
| P3：成本优化与论文 | 显式条件取证策略、同质量成本比较、复现包与研究威胁 | 简单基线已足够时保持简单；无增益时发表诚实实证结论 |

若 P1/P2 未能超过无 LLM 模型映射或固定上下文，不继续增加代理数量以追求正结果。可转为“LLM 增强静态分析的语义验证失效与评测研究”，但仍需多个框架、真实案例、可复现协议和具有解释力的失效分类。负结果有研究潜力，不自动保证可发表。

本次建议不替换已有总计划的工程承诺；它调整论文优先级：**先确认真实缺口与真值，再研究规格适用条件和独立验证，最后在同等质量下评价取证与复用成本。**
