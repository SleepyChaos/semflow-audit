# 综合代码审计平台：竞品与论文实验方案

版本 v1，2026-10-03（北京时间）。依据最早“AI 增强传统静态审计”的方向、旧项目 RAG/增量锚点的问题，以及当前四阶段实现制定。实际已运行项目见 benchmark-results.md；本页未执行的内容是实验计划。

## 1. 研究主线与能力边界

建议主线：**证据约束的混合审计及可验证反馈**。平台整合本身是工程成果；论文要验证机制带来的收益。

| 拟定贡献 | 操作机制 | 当前具备 | 研究还需补齐 |
|---|---|---|---|
| 版本与项目约束的 RAG 规则合成 | 按锁定 pack/API/确认缺陷检索；编译反馈；独立正反例验收 | 文档版本/digest/引用、固定依赖、编译与人工例批准、发布门槛 | 项目 API 模型抽取、独立留出集、知识质量分层 |
| 证据预算约束的语义复审与补充发现 | 真实快照取证、有限工具循环、允许弃权、人工确认 | 取证工具、预算、引用检查、候选与判断历史 | 跨过程调用图、可行性/根因裁决、可靠新增漏洞统计 |
| 共享证据与双 oracle 的审计—修复—规则反馈 | 共同根因证据；隔离修复；安全与功能独立验证；反馈迁移 | diff、隔离测试、冻结规则复扫、报告和可人工生成规则 | 通用 exploit 注册、自动受控知识回流、跨项目迁移实验 |

前两项现名需收紧：“RAG 生成 CodeQL”已有 QLCoder 等先行工作；“精准”应由结果证明。第三项也不能仅叫普通闭环；已有 JIT 修复复扫研究。详细近邻、引文与日期见 papers-and-innovations.md。三个方向可作为同一个方法的三个可消融机制，不必强行包装为三个独立原创。

研究范围先固定 Python 与 JavaScript。TS 可扫描，但当前通用修复验证器不做 tsc/JSX 构建；单列支持边界，不纳入自动正确修复主榜。只包含有可靠真值的注入、路径穿越、原型污染/ReDoS 等类别；授权/业务逻辑漏洞先用案例研究。

## 2. 对照组与公平约束

| 组别 | 配置 | 用途 |
|---|---|---|
| B0 | 固定版本 CodeQL security-extended | 必选静态基线，与平台使用相同查询包 |
| B1 | Bandit 1.9.4 默认检查，Python | 轻量 AST 静态对照，已经在微型样本实跑 |
| B2 | Semgrep CE + 有明确授权且固定 commit 的规则集 | 可选结构/污点静态对照；引擎和规则许可分开记录 |
| B3 | 阿里 Open Code Review 固定 commit | 主要 LLM 审查对照；同模型/预算/源码访问权限，缺乏支持语言时单列 |
| B4 | 同模型一次性项目/告警上下文，无工具，无 RAG | 判断主动取证收益；不能将截断失败伪装为无漏洞 |
| M1 | CodeQL + 受约束 AI 复审/补充发现 | 验证语义取证机制 |
| M2 | M1 + RAG 补充规则 | 规则增益；规则生成成本和后续复用成本分别计 |
| M3 | M2 + 共享证据修复及验证反馈 | 综合组；正确修复与留出项目规则迁移分别衡量 |

QLCoder/IRIS/QLPro 是方法近邻，原实验主要 Java，不能未移植就直接放进 Python/JS 执行排行榜。优先复现其核心消融思路，另表记录官方语言、数据和原报告结果。

固定：机器、CPU/内存、并发、CLI/pack、模型实际版本、temperature、prompt hash、知识 manifest、工具预算、上下文预算和超时。LLM 对照同模型、同 token/call 上限；不同模型做独立附表。不同工具的能力不硬凑一致：报告默认规则与人工精调两个结果，精调仅使用开发集。

## 3. 数据分层与收集状态

- **层 A：机制微样本**。当前 12 个 Python/JS 正反例覆盖 CWE-094/078/089；3 类提供的修复候选用于双 oracle 验证；8 文档/8 问题检索样本。可重复、可解释，不作为论文真实项目主结论。
- **层 B：真实漏洞配对**。OpenSSF 已收集 223 项元数据及 3 项 JS 单文件 pre/post。Vul4Py 已收集 100 项 Python 修复提交索引。正式实验应取完整仓库快照、依赖与 oracle；单文件探索结果不能代替完整项目召回。
- **层 C：复审标签**。AACR 全量 2,145 条，当前语言子集 714 条（151 Python /141 JS /422 TS）。安全子集需人工标注；不能把正确审查评论等同可利用漏洞。
- **层 D：独立修复 oracle**。2026 execution-calibrated patching 复制包已下载，例源未执行；逐项审阅后适配隔离运行。Vul4Py 需要补完整环境与测试，当前仅索引。
- **层 E：规则留出集**。自建包装函数、跨文件传递、常量/sanitizer、参数顺序、无关危险 API 等变体。优先由另一名标注者编写，不能使用生成模型自己的正反例作为唯一真值。

路径、许可、版本与下载状态见 competitors-and-materials.md 及 artifacts/research-materials/manifest.json。论文 PDF 及其状态见 artifacts/papers/manifest.json。大型源代码、论文和运行产物保持本地，不随 Git 提交。

## 4. 正式实验的选样与切分

建议先做可行性批次：每种语言 10 个真实漏洞配对，至少 4 个 CWE；稳定后扩到每种语言 30–50 个配对，至少 10 个仓库。数量是目标，不预先承诺当前已可执行。

1. 固定 benchmark revision，筛支持语言、完整快照、可复现 oracle 和许可明确条目。先公布所有候选与排除理由，避免只留下 CodeQL 能命中的条目。
2. 按仓库与 CVE 家族划开发/验证/测试，建议约 50%/20%/30%；样本不足时做按项目交叉验证，最终测试从未用于改 prompt/规则。关联 fork/同根因变体也归同组。
3. 真实安全对照使用官方修复版本，并额外核查目标根因；不宣称整个修复后项目绝对安全。每个条目保留目标文件/位置/CWE/根因及 oracle。
4. 检索库中移除测试项目代码、同 CVE 描述/patch、近重复答案和 oracle。通用 CodeQL API 可保留。记录知识 cutoff 与每个 chunk SHA；避免旧 CVE 已见于模型训练的未知污染，单列时间留出和未公开变体结果。
5. 两位标注者盲审，第三方裁决分歧；报告一致率与裁决记录。未标注的额外告警进入待判断队列，不自动作为 FP。

## 5. 审计准确率与复审实验执行链

完整快照 → 上传/建库 → 固定 CodeQL 扫描 → 保存所有告警 → 同预算运行各 AI 组 → 按真实证据人工裁决 → 根因去重 → 汇总。

匹配单位为漏洞实例：项目/快照 + 根因 + CWE + 相关位置。行号只用于定位，不以另一行自动认定新增实例。静态与 AI 重叠、同漏洞多条流、重复复审只计一次。

指标：

- Precision=TP/(TP+FP)，Recall=TP/(TP+FN)，F1；分母为零记 NA，按 CWE 宏平均与总体微平均同时报。
- 配对双正确率：漏洞版检出且修复版不再报告同根因，两者均满足才算一对正确。
- 复审：原 TP 保留率、原 FP 排除率、弃权率与自动判定覆盖率。弃权不是排除；人工确认耗时记入成本。
- 补充发现：静态基线遗漏的、独立裁决确认根因数量；报告每新增 TP 的调用/token/人工成本。
- 工具失败、超时、抽取不完整分别列数量与覆盖率；同时给意向测试集结果和成功子集结果。不得删除失败项来制造高准确率。

AACR 输入是带上下文的评论真假判断，另作“复审正确性”榜：接受/拒绝/弃权、balanced accuracy、真评论保留、错误评论拒绝。先做安全子集和全子集两张表，不以其标签计算漏洞召回。

## 6. 修复准确率执行链

确认根因/证据 → 冻结范围 → 模型生成 patch → 应用到隔离副本 → 语法/构建 → 功能 oracle → 安全 oracle → 完整冻结规则复扫 → 盲审 → diff 验收。

先校准 oracle：漏洞版原功能通过、目标安全测试失败；官方修复版功能与安全都通过。若条件不成立，该条目的 oracle 尚未合格，应报告排除理由。

主指标是 **安全且保持原功能的正确修复率**，不是语法通过率或告警下降率。分别报告 patch 可应用、构建、功能、安全、联合通过、人工语义接受、其他规则回归和超时。top-1 为主，若给多次尝试则报告 pass@k 与总预算，不能把挑选后的最好补丁称为一次成功。

原有测试、依赖/配置锁文件、认证授权分支等不在默认补丁范围。若确需改测试或依赖，新增明确实验组并独立批准；不能删安全检查来获得零告警。没有可执行 oracle 的业务漏洞单列“人工案例”，不混入已验证修复率。

## 7. RAG 与规则生成实验

固定 20 个以上规则需求，每个至少 5 个留出正例、5 个近似良性负例；分语言/CWE/框架包装类型。先做 8 项微型检索测试，随后用真实项目抽取的规则需求扩展。

对照：无检索 / 通用文档 BM25 / 文档+项目知识 BM25 / 相同知识混合检索。保持模型、prompt、编译反馈次数与预算一致。embedding 模型变化必须重建索引，不混用向量。

记录：Recall@k、MRR、来源/版本有效率、过期 API 检索率；生成解析率、编译率、独立例检测 precision/recall、良性误报率、人工样例批准率、发布率、总时间/token。编译失败也保留在生成任务分母中。RAG 检索命中不证明最终查询正确。

查询策略分“数据流模型补全”“原规则扩展”“新查询”；纯 sink 锚点规则单独标记，不能作为高精度漏洞检测。独立例不能由同轮模型生成，也不能被检索。

## 8. 消融、性能与统计

必做消融：

1. 无知识 vs 通用 RAG vs 版本/项目约束知识。
2. 一次性上下文 vs 有限主动取证，保持相同调用/token 上限。
3. 无证据引用校验 vs 校验/弃权机制（只在隔离实验，不发布未经证实规则）。
4. 仅语法/复扫 vs 功能+安全双 oracle。
5. 不反馈 vs 人工确认后反馈；只在未知项目评价迁移。

性能各重复至少 3 次，记录中位数/范围；正式模型实验建议 5 次随机种子/独立调用。分别计 API 排队、抽取、查询、AI取证、patch生成、验证、规则生成与复用扫描。真正冷启动要新环境/空查询缓存；未清 OS 缓存只能写“首轮观测”。Docker启动与模型网路时间计入端到端，网络可缓存但各组一致。

报告样本量、失败率、每项目结果、95% 按项目 bootstrap 区间。配对二元结果可用 McNemar；时间用配对分布比较。三轮同一确定性样本用于稳定性，不扩大独立样本量。

## 9. 执行批次与验收产物

| 批次 | 工作 | 完成判据 |
|---|---|---|
| P0 已做 | 普通测试、真实四链路、微型审计/验证/RAG、Bandit、真实JS单文件探索 | 原始结果、hash、可重复CLI、边界说明 |
| P1 | 配置真实模型，适配20个完整项目与oracle，标注AACR安全子集 | 所有样本与依赖固定，官方pre/post双oracle通过 |
| P2 | CodeQL/Bandit/Semgrep/阿里与M1–M3同预算运行 | 失败保留、盲审和根因去重完成 |
| P3 | 规则留出与知识/取证/验证/反馈消融 | 测试知识无泄漏，模型调用与引用日志完整 |
| P4 | 扩到60–100真实配对、统计与论文 | 每项目结果、区间、反例与局限、复现清单齐全 |

每次运行至少留：run_id、dataset/case/revision、language/CWE/root_cause、tool/rules/model/prompt/knowledge版本、状态、候选/证据引用、人工裁决、patch hash、oracle结果、各阶段时间、调用/token与费用。

验收时优先看失败和边界案例：过时 API、良性危险调用、跨文件包装、同根因不同位置、源码伪指令、证据不足、修复功能回归。若收益只来自更多 token、模型更强或调参接触测试集，应收回方法收益结论。
