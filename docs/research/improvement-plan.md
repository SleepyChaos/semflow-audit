# 真实模型测试后的改进计划

日期：2026-10-03。依据：`live-model-results.md`、既有 `benchmark-results.md`，以及保存的不可变阶段、证据、补丁和测试日志。本文件保留最初改进目标；最新完成状态与仍待实施范围见下方交付记录。

前三项的具体执行拆分、原因、目标、依赖及验收见 [第一阶段改进计划](phase-one-improvement-plan.md)。M1/M2/M3核心机制现已实现，代码/API与真实模型校准完成，见[实施记录](phase-one-implementation.md)及[测试结果](phase-one-test-results.md)。向量消融、完整框架验证、成熟符号解析、竞品大规模实验与增量身份仍待实施；规则检测质量尚未达到目标。

## 实施顺序

1. 先补P0可观测性和结果语义，冻结本轮基线；不先改架构或更换模型。
2. 扩充规则独立测试集，再比较检索方案。没有独立规则检测指标时不宣称“RAG显著增强”。
3. 增强成熟解析器/框架证据，开展跨文件与真实CVE测试，然后做竞品与消融。
4. 数据、失败率、成本和修复oracle稳定后，做增量身份与论文主实验。

## 三个论文创新点的收敛建议

1. **检索与执行反馈约束的CodeQL规则生成**：来源可追溯、版本固定、编译修正、独立样本验证，而不是“用了向量数据库”。比较无RAG、BM25、混合检索、加入编译反馈及独立holdout。
2. **静态证据驱动的主动语义复审**：以CodeQL路径和只读取证工具为证据，区分确认、排除和不足；比较纯LLM、仅解释静态告警、主动补证三组。尚未证明“精准”，应把它写为待验证假设。
3. **证据约束修复与双重独立验收闭环**：确认后的根因→有限范围补丁→安全oracle与功能oracle→复扫→人工接受。比较仅生成diff、仅复扫、双oracle闭环的正确修复率与回归率。比单纯“综合平台”更可测量，但需通过文献对照论证增量贡献，不能声称首创。

## 明确保留的边界

没有向量检索配置就报告BM25；没有完成分析就报告失败/未知；没有独立oracle就不计修复正确；锚点规则不自动证明漏洞；重复三次仅衡量稳定性，不增加独立样本数。GUI验收另见 `docs/acceptance-checklist.md`，本轮未进行GUI测试。
