## 1. 已有能力和缺口

- 已有持久化 PostgreSQL + pgvector、Haystack BM25、向量余弦检索及 RRF 融合，不需要再部署一套向量数据库。
- 同一知识表现已通过 corpus 字段区分 reference/rule_example，旧混合文档保留 unclassified，不仅靠提示词贴标签。
- 两集合独立预过滤/召回，按操作/CWE分配 API 与范例角色；仍无独立重排模型。接口、数据库迁移和完整范例依赖取回均已实现。
- 本次标准 `/models` 查询返回 404。依据官方支持文档与真实调用确认可用模型，而非将 404 解释为没有向量模型。
- 同一现有 `/api/plan/v3` 网关实测支持 `doubao-embedding-vision`：OpenAI `/embeddings` 返回 `doubao-embedding-vision-251215`、2048 维；两条独立文本批量结果通过数量、索引、有限非零和差异检查。
- `/embeddings/multimodal` 也能返回 1024 维；本项目先使用已适配的文本 `/embeddings`，两个端点产生的向量不混用。

集成烟测脚本：[embedding_smoke.py](../scripts/benchmarks/embedding_smoke.py)。只读凭据，结果不含密钥或向量。索引操作仅允许与已安装公开 MIT CodeQL 查询包原文、SHA256 完全一致的共享条目；上传项目和其他知识不在本次批量范围。实际结果见本地 `artifacts/research/embedding-smoke-2026-10-04.json`，不提交审计产物。

本次实际完成 28 条公共规则、28 个块的向量入库。Python/JavaScript 各运行 vector 与 hybrid，4/4 检索烟测通过；版本与共享访问范围均通过检查，两类查询在向量检索首位分别命中 CodeInjection 与 SqlInjection。4 次检索耗时约 0.289–0.364 秒，仅描述本次小库调用，不外推为大规模性能。相关普通测试 20 项通过。

## 2. 两个逻辑集合

两个集合使用同一数据库与 embedding 配置，通过集合字段、所有者、版本过滤实现独立检索。不要仅在提示词中给混合检索结果贴标签。

| 集合 | 内容 | 提供给生成器的作用 | 质量门槛 |
|---|---|---|---|
| reference | QL 语法、固定版本的 CodeQL API、source/sink/summary 建模、框架数据来源和参数语义、漏洞机制与边界、已核实的错误解决说明 | 回答应该分析什么、如何使用当前版本 API、哪些事实仍未知 | 来源、许可、语言/API/框架版本、原文证据；未知项不补造 |
| rule_example | 完整 `.ql`、必需 `.qll` 依赖、用途/适用范围、source/sink/sanitizer 角色、依赖锁、验证记录及可公开的开发正反例 | 提供可复用结构、已有能力和扩展方式 | 依赖可恢复；编译状态和验证状态分列；官方查询不冒充对新任务验证通过 |

reference 内按“漏洞原理、CodeQL API、框架 API、诊断”分类型，不另拆四套数据库。rule_example 的代码块保持完整，检索到片段后按文档/依赖关系取回必要原文。现有混合教学文档应分为两个有共同来源关联的记录，不能靠标题猜测类别。

项目源码和审计证据由本次任务工具提供，不混入共享背景库。用户上传知识保持租户隔离；不得因为属于 rule_example 就升级为可信来源。

## 3. 生成执行链路

### 3.1 必需输入：RAG 知识、源码、漏洞描述

用户确定：正式规则生成必须同时提供这三类素材。默认 v6 已加载实际证据正文并支持有限主动取证；历史 v2/v3/v4/v5 保留旧协议。三类材料分别保存和引用，源码和漏洞事实不能由背景知识或模型自生成样例替代；以下契约已在首版实现，跨框架泛化继续验证。

| 素材 | 必需内容 | 来源与完整性要求 |
|---|---|---|
| RAG 知识 | 与目标匹配的 CodeQL API/建模知识和可用规则范例；引用固定版本、适用范围及依赖 | 两集合独立召回，记录片段 ID、来源、版本、digest；缺少某类证据明确补检索/待补充，不填造 |
| 源码 | 漏洞所在函数/模块原文，以及判断输入来源、关键传播、汇点和防护所需的相关代码 | 本次不可变项目快照；绑定文件、行范围、源码 hash/证据 ID；读取正文，不只传路径或 ID；外部框架语义由对应版本文档补充 |
| 漏洞描述 | 漏洞类型、位置、输入可控性、触发条件、关键路径、防护情况、根因、确认状态和原基线覆盖情况 | 来自本次审计确认记录/明确任务描述，事实与假设分列；CWE 或遗漏原因未知时明确未知；模型描述不自动成为漏洞真值 |

另附生成配置：语言、实际固定依赖、用途/策略、基线结果与版本、执行预算。不能把整份项目源码和全部扫描告警默认塞入模型；围绕目标组装并保留原文引用。

**材料准备与就绪检查**：从目标漏洞记录加载描述和关联证据正文 → 初始定位相关函数与 source/sink → 通过范围受控的 `read_source`、`search_source`、`callers` 按需补源码 → 明确待核实 API/建模问题并检索两集合 → 校验三类材料 → 冻结生成输入。工具调用应复用 AI 复审的证据适配器；调用线索只是线索，仍要读相关定义/调用代码。

- 原始证据先保存在产物中；上下文去重、预算化，关键路径、参数位置和防护条件保留原文，概要不能替代这些事实。预算不足时保留待补项，不能静默截掉关键证据。
- 只允许读取当前用户、当前审计及匹配快照的源码；工具读取范围、次数和总上下文设预算，不允许任意磁盘/网络读取或执行项目指令。
- 三类材料任一缺失时不得进入正式规则生成，状态为待补材料；关键漏洞条件不清楚时返回补证据/待确认，不生成声称已确认漏洞的检测规则。源码中的注释和字符串均作为不可信数据处理。
- 无人工确认的任务描述可以用于提出待验证规则，但没有已确认遗漏目标时，不得获得“已验证补漏”状态。正式补漏验证仍按第 7 节确认根因。

### 3.2 从材料准备到验证发布

1. 加载三类输入并准备证据：规范化漏洞描述，读取并按需补充相关源码；语言、CWE、框架、source/sink、预期路径、覆盖缺口中未知项保持未知。
2. 从实际锁定依赖确定 CodeQL API 版本；按语言、版本、集合、所有者预过滤。
3. reference 召回：BM25 保留 API/符号精确匹配，embedding 支持语义召回，RRF 融合。
4. rule_example 独立召回：除相关性外核对分析类型、API 版本和依赖完整性，优先可复用结构。
5. 上下文装配与就绪检查：RAG 两类分别预留份额，例如知识 3 条、范例 2 条作为起始实验配置；与真实源码、结构化漏洞描述及生成配置一起组装，按需补齐依赖。预算不足时说明省略项及原文引用，不截断半个查询或关键漏洞路径。三类必需素材齐备后冻结输入。
6. 输出受限分析规格，优先复用已有查询/补 API 模型，再决定生成新查询；生成器引用来源、版本和 digest。
7. 确定性模板或受约束生成，先通过规则静态检查，再执行开发正反例与有限诊断反馈。
8. 在原项目同一源码/数据库快照上单独执行新规则，按第 7 节核实是否发现原基线遗漏的已确认漏洞；保存原始 SARIF、诊断和根因对比。
9. 独立留出测试与人工发布，保持现有规则验收流程；知识检索不拥有发布权限。原项目补漏成功与独立泛化通过分开记录。

重排暂空，RRF 是排名融合，不能称为 reranker。预留适配器即可，不使用聊天模型模拟重排成绩。后续有实际 reranker 时，在相同冻结集合上独立消融。

## 4. 上下文与索引约束

- 原始文档保持不可变，结构化标签和摘要只用于检索；关键 API、条件及代码使用原文。
- 记录集合、来源、语言、库/框架版本、角色、许可、验证级别、依赖关系、原文 hash。
- 索引配置已包含请求模型、固定返回版本、维度、端点协议及预处理版本。同名模型更换版本需重新索引；过期向量排除，API 单列当前与过期索引数量。
- 两集合可共用一次查询 embedding，避免重复网络调用；准确符号检索不能被相近语义取代。
- 当前 BM25 候选上限 1000 条，扩库前必须解决候选截断和索引策略；目前 pgvector 持久化检索存在，不等于已部署大规模 ANN 索引。
- 没有匹配版本/API 证据时弃权或请求补充；向量相似度不能证明某个函数或 sanitizer 存在。

## 6. 高质量知识与范例扩充工作包（首批完成，持续扩充）

用户新增要求：检索方式改造之外，还必须主动寻找、核验和补充高质量资料与规则范例。初始 28 条片段为历史起点；本次新增 40 主题、28 含依赖与官方开发测试的完整范例，并记录固定源码版本、全部验证及排除状态。数量达标不代表高质量知识覆盖已经充分。

### 6.1 目标与优先来源

| 材料 | 优先来源与范围 | 入库单位及要求 |
|---|---|---|
| QL 与 CodeQL API | 官方写查询指南、Python/JS 语言库文档、固定依赖包源码的定义和注释 | 单个主题/API 原文；含完整签名、返回类型、可用版本、调用关系和引用 |
| 污点建模知识 | 官方模块化数据流、source/sink/summary/barrier、PathGraph 和框架建模说明 | 可定位到原始资料的知识卡；区分数据流与污点传播，不把模型猜测作为事实 |
| 框架语义 | 优先覆盖试验已暴露缺口的 Flask，以及实际目标中的 Django、Express 和数据库/模板/命令执行 API；以官方版本文档和框架实现为准 | 输入来源、成员、参数位置、返回值/调用语义、安全 API 条件；有缺口就标注未知 |
| 完整规则范例 | 固定版本官方 `github/codeql` 查询、关联 `.qll`、公开的官方开发测试与预期结果 | 查询包单元：规则＋实际依赖＋用途解释＋可恢复开发样例；保留现有查询 ID 与来源身份 |
| 漏洞机制与反例 | CWE 官方定义及相关官方框架安全文档，必要时采用可核实的漏洞公告 | 漏洞触发前提、安全边界、防护适用条件及常见误报；背景机制不能代替实际项目证据 |
| 修正记录 | 本平台真实编译/开发执行失败中，经固定版本工具重现并修正的案例 | 诊断＋版本＋最小失败例＋验证通过的修正；排除密钥、私有源码和隐藏测试，人工核验后才入库 |

论文用于确定方法和评价，不直接转为权威 API 知识。第三方文章、社区规则和模型生成说明只作为候选，必须核实原始出处、许可和当前固定版本，不能自动晋升为可信材料。

### 6.2 覆盖矩阵与首批目标

- 以语言（Python/JS）、漏洞（代码/命令/SQL 注入、XSS、路径遍历、反序列化、SSRF）、分析角色（source/sink/summary/barrier）和固定版本建立覆盖矩阵；不要求每个 CWE 适用于每个语言/框架。
- 首批目标：至少 30 个独立 reference 主题，以及至少 20 个完整 rule_example 单元。数字是待验收目标，不是已采集数量；切片、重复版本和同一内容改标题不能重复计数。
- 优先补齐模块化数据流、节点类型转换、框架 API 位置和依赖恢复，解决已观察到的生成失败。随后才按目标漏洞覆盖扩量。
- 不自动把 sanitizer 的描述转成 barrier。范例必须说明为何能阻断指定攻击、适用参数和上下文；证据不足则禁止生成放宽条件。

### 6.3 采集、核验与发布流程

1. 建材料清单：URL/仓库路径、commit/包版本、许可、采集时间、正文 hash、语言/CWE/角色、所属集合和用途。
2. 下载允许使用的官方原文或从固定本地包提取；保留不可变原文，避免只存二次摘要。资料有版本冲突时分别入库并显式关联。
3. reference 人工核对 API 和语义，检查版本映射；无法映射到当前依赖的资料标为不适用，不参与默认规则生成。
4. rule_example 恢复 `.ql` 和实际 `.qll` 依赖，在固定 CodeQL 环境编译，并运行独立于留出集的开发正反例。记录编译、执行、路径语义三种状态，失败样例保留为诊断材料，不进入优先范例。
5. 去重、完整性与许可检查，核对租户范围。可信来源字段由采集/核验流程设置，用户上传接口不得自行声明“官方已验证”。
6. 生成双集合索引，记录模型返回版本和索引身份；检查跨租户、跨语言/版本检索，分别发布材料版本。

### 6.4 如何证明资料扩充有用

- 先固定独立检索需求，标注应召回的 API/规则和依赖，检查 Recall@k、符号精确命中、版本正确率、依赖完整率。不能由生成模型自行给检索结果打正确标签。
- 冻结旧材料版本，对比“旧资料”与“扩充资料”，再比较单集合/双集合及 BM25/向量/混合；固定生成模型、提示词、预算、任务与规则验证器。
- 报告独立留出上的端到端规则通过率、FP/FN、弃权率、耗时和 token；检索提升与生成提升分别统计。小样本结果说明范围，不将资料数量当作增益指标。
- 基准源码、漏洞补丁、金标、隐藏测试和评价脚本不纳入共享背景库；同源官方规则/测试若用于 RAG 开发，则不能再充当证明泛化的独立留出。

### 6.5 交付物与完成条件

- 来源/许可/版本清单、两集合内容清单、覆盖缺口表、可恢复范例包、逐条验证记录和冻结库版本。
- 覆盖矩阵达到首批目标，范例依赖可恢复；所有未核实、失败、排除和版本不兼容条目可追溯。
- 完成旧/新材料和检索方式的独立消融，决定保留的材料与默认策略；若没有质量增益，继续按失败类别补资料，而非盲目扩库。

## 7. 生成规则的两道验收门槛（新增设计，待实施）

用户要求：生成后首先通过静态检查，其次使用单条规则在原项目复测，确认能否识别原来没有发现的漏洞。这是规则检测能力验收；此前暂缓的是修复补丁的新增利用复测，两者分别执行各自计划。

### 7.1 第一道：规则静态检查

- 校验规则输出契约、用途、元数据、命名空间、允许的模块路径、固定依赖及 API 版本；缺失或冲突直接失败。
- 使用固定 CodeQL CLI 和锁定依赖进行真实 `query compile --check-only`；语法、类型、导入或 API 解析错误必须修正后再执行。
- 静态通过只表示规则可编译，不能表示能检测漏洞。保留已有开发正反例及独立样本验收，避免锚点查询或“见到危险函数就报警”冒充漏洞检测器。

现有 `prepare_query`、`compile_query` 和规则生成图已提供其中基础检查。新增工作重点是把下一道原项目验证作为显式节点和持久化验收状态，不能以当前样例执行结果代替。

### 7.2 第二道：原项目单规则补漏复测

1. **确定验证目标**：优先选择 AI 取证后人工确认、但原 CodeQL 基线遗漏的漏洞。记录漏洞根因、source/sink、关键路径和确认依据；只有模型建议或函数关键词时，目标仍是待确认，不能自动作为真值。
2. **冻结基线**：绑定原审计 ID、源码 hash、数据库身份/提取配置、CLI/查询包版本，以及当时启用的全部补充规则和原始 SARIF。验证原扫描完成且覆盖了相关文件；扫描失败或抽取缺失不能称为规则漏检。
3. **先核实漏检**：按根因、相关 source/sink/路径匹配原基线，而非按查询 ID 或告警行号。若原基线已有同根因告警，记为已有覆盖；不算新增检测。
4. **单独执行**：复用匹配的原 CodeQL 数据库，在独立输出目录仅运行新规则的一个入口 `.ql`，包含其必要 `.qll` 和固定依赖。不混跑整个默认查询包。若是 API 模型扩展，使用引用该模型的对应单条检测查询作入口。
5. **核对目标命中**：保留完整 SARIF、数据流证据、执行日志和耗时，核实新命中是否属于预先确认的遗漏根因。路径或位置变化不能自动算另一个漏洞。
6. **分开处理其他告警**：重复根因去重；额外告警标为待核实、确认 TP 或确认 FP，不因为“新出现”就全部计为新增漏洞。检查已有安全反例，误报情况和目标补漏状态分别记录。
7. **给出结论**：目标检测成功、目标未命中、已有覆盖、证据待确认、执行失败、超时/快照不匹配分别持久化。成功的严格条件为“有效基线未覆盖＋新单规则成功执行并命中同一已确认根因”。

无已确认遗漏目标的通用规则，仍运行原项目单规则并报告结果，但标记补漏效果 `not_evaluated`，不能把零告警当作正确，也不能宣称已验证补漏。此类规则可按已有通用样例/独立验收流程发布，但不得获得“已验证新增漏洞覆盖”标记；明确以补漏为目标的规则，目标复测未通过则保持待改进状态。

### 7.3 图编排、反馈与验收产物

拟定执行顺序：`漏洞描述与初始源码证据 → 有限源码读取 → 双集合 RAG → 三类素材就绪检查 → 生成 → 契约/静态编译 → 开发正反例 → 原项目单规则复测 → 根因与基线比对 → 独立验收 → 人工发布`。人工样例批准及目标确认保留现有权限边界；自动节点不代替人工确认漏洞。

- 编译、开发执行和已知原项目目标未命中可进入共享预算内的有限反馈，复用已有最多两次候选尝试，避免再叠加无限重试循环。每次保留规则 hash、诊断和执行结果。
- 原项目证据是该次生成的开发上下文，命中原目标只证明该项目补漏。独立留出真值/补丁不能反馈给模型；原项目重试成功不得作为独立泛化成绩。
- 产物：基线与快照身份、目标确认记录、规则/模块/依赖 hash、静态诊断、新规则原始 SARIF、目标匹配依据、额外告警裁决、耗时、最终状态。
- 规则、模块、依赖、目标、源码、提取配置或基线变更时使该次验收失效，禁止沿用旧“补漏通过”。恢复任务需校验产物身份后才复用数据库。
- 新增指标：已确认遗漏目标的检出率、重复告警比例、额外 TP/FP/未决数量和单规则耗时。没有完整漏洞金标时不据此宣称项目总体 recall。

实施验收须覆盖：编译失败阻断复测；原基线已覆盖不计增益；同根因不同位置去重；确实遗漏的目标单规则命中；目标未命中；额外误报/未决不计 TP；扫描失败或源码/数据库不匹配不伪装安全；重试及恢复保持原始产物和预算。以上为待实现要求，目前原项目单规则验证节点尚未接入正式生成流程。
