# 多页面审计工作台设计

日期：2026-10-11
状态：页面布局与 V2 风格已获用户认可；本稿更新了独立副本要求，待书面审阅；尚未改动产品界面代码

## 目标与已确认方向

用途：视频演示，同时支持真实的本地审计操作。
已确认：采用多页面工作台，将总览、审计任务、规则库、知识库分开。四个审计阶段放在左侧列表中，可自由切换，不采用顺序向导。
成功标准：观众能看懂四阶段关系，操作者能立即找到当前结果、待办和下一步；数据含义准确，功能入口明显。
已确认采用 V2 示意图：浅灰侧栏、黑白主体、少量橙色强调、平面分隔线和克制的工具界面。

## 范围

重整现有 React / TanStack Router / Query 前端，复用当前后端接口与阶段组件。
实现真实任务导航、状态说明、规则和知识管理；保留既有证据、历史及人工判断流程。
本次不新增模型或扫描引擎，不加入没有数据支撑的统计图，不改动密钥、已有本地启动配置或用户文件。

## 页面与导航

固定左侧导航分组：工作台（总览、审计任务）；当前审计（项目名称、语言，以及 CodeQL 审计、AI 复审、修复与报告、RAG 规则四项）；管理（规则库、知识库）。没有选中任务时当前审计组给出选择任务入口，不能使用虚构任务。侧栏底部提供执行环境入口。
公共顶栏显示当前页面、简洁的环境状态及“新建审计”。环境详情以侧边面板展开。
刷新页面和浏览器前进/后退后保留任务与阶段，使用 URL 而非仅存于组件状态。

路由：
- `/`：总览。
- `/audits`：审计任务。
- `/audits/new`：新建审计。
- `/audits/$auditId`：任务详情，查询参数 `stage` 为 `scan`、`review`、`repair`、`rules`。
- `/rules`：规则库，查询参数 `ruleId` 可定位具体版本。
- `/knowledge`：知识库，可按语言和材料类型过滤。

### 总览

标题为“审计总览”，副标题简述上传、复核、修复、规则沉淀的关系。
第一屏显示真实的任务数、扫描执行中的任务数、待人工确认候选数、已发布规则数。
每项明确统计范围：当前接口返回的本地任务或规则。候选统计需实际读取候选接口，未加载完成时显示“统计中”，请求失败显示“无法统计”，不显示假零。
第二行重点显示可继续处理的任务：待复核、待人工判断、规则待验收/发布等，并提供直达对应任务阶段的按钮。
第三行显示最近任务；空数据库展示新建审计入口与简短流程，不展示虚构任务。
默认不放装饰性走势图，保证录屏有明确的信息重点。

### 审计任务列表与新建审计

任务列表提供名称搜索、语言与执行状态过滤；点击任务名称进入独立详情。
列为项目、语言、扫描状态、静态告警、AI 候选、人工确认、创建时间、继续处理。
“静态告警”含 CodeQL 基线及所选自定义规则的扫描结果；AI 候选包括未确认与已判断候选；“人工确认”按候选身份计算，避免重复历史记录计数。
候选数据读取失败或尚未读取显示对应占位，不将未知记为零。
任务列表无需在每次列表刷新时重复加载所有证据与阶段日志；候选请求按任务缓存并限制并发，详情使用相同查询缓存。

新建审计为单独页面：上传 ZIP、名称、语言、可选已发布规则，说明 ZIP 大小限制及最多四个规则版本。
提交后立即进入新任务详情，显示排队与扫描进度。上传失败保留填写内容并显示错误。

### 任务详情与四阶段

第一屏固定项目名称、语言、快照标识、执行状态，以及下一步操作区。
扫描完成只表示扫描执行完成，文案不能暗示全部安全或整个审计已经结束。
四个阶段在左侧当前审计分组中纵向排列，使用普通菜单高亮所选项，右侧展示相应内容。它们具有业务依赖，但导航不强制顺序，不采用横向步骤条、箭头串联或逐步解锁菜单。操作按钮依据真实前提决定是否可执行，菜单允许随时查看各阶段。
各阶段分别显示未开始、进行中、待人工处理、已完成、失败等真实状态，不能用“曾有一次执行完成”代表全部验收完成。
推荐下一步依据当前结果派生；用户仍可主动切换阶段，生成规则不强制先修复。
重跑、取消、恢复等操作沿用后端约束；执行历史保持可访问。

双引擎扫描：CodeQL 与 Agent 分开展示执行结果，明确区分静态告警与 AI 假设；覆盖详情和日志按需展开。
AI 复核：展示候选列表与证据详情；来源、模型建议、人工状态分开标注。未知建议保留未知，不能由前端自行改成 supported。
复核卡片将复选框和标题放在同一行，提供清晰选中态与说明；证据选择、判断理由和提交动作靠近。
人工确认仍需要现有证据与理由验证。原始候选及历次判断不删除、不静默合并。
修复与报告：先显示报告导出入口，再显示已确认候选的修复选择；未确认时给出返回 AI 复核的入口。Diff、语法验证与复扫结果分开展示。
RAG 规则：明确区分生成条件、编译结果、样本验收、独立测试、项目根因确认和发布状态。

### 规则库与生成交互

规则库集中展示全部规则，按语言、用途和状态过滤；展示来源项目、版本、生成策略与验证摘要。
可查看查询、关联模型模块和检索依据，下载查询，并访问来源任务的规则阶段。
生成入口需选择来源审计任务，再进入该任务的规则表单，不创建没有快照关联的规则。
已发布规则提供新建审计的使用入口；规则发布、停用及重跑继续使用真实接口。

规则生成表单分成三个明确分组：
1. 规则目标：用途、已确认候选或明确需求、源码范围。
2. 检索与生成：知识材料就绪提示、策略及说明。
3. 验收配置：独立测试集，说明缺少独立集时可生成但暂不能发布。

保留现有用途与默认值，用户明确选择“漏洞检测规则”时再提交该用途；不将复审锚点默认解释为漏洞证明。
高级策略以“自动选择、补充框架模型、扩展查询、新查询”说明，保留相应真实参数。
缺少 reference / rule_example 时显示材料类型、所需语言库版本与“前往知识库”入口；前端只能依据已获数据提示，服务端仍是最终校验依据。
运行失败展示简短中文原因与解决入口，原始错误可展开。`materials_missing` 不能被误标为模型调用失败。
生成后的规则显示验收清单，缺少的条件明确写出来；样本批准、根因确认、发布分别由用户执行。
前端不自动批准样本、不自动确认漏洞、不伪造模型或测试结果。

### 知识库

知识导入成为可见主操作，不再藏在任务页折叠项内。
提供语言过滤、参考知识/完整规则范例分类、来源、材料版本、分块与索引状态。
导入表单保留标题、来源、正文、语言、语言库版本、材料类别、许可证字段；明确不会自动抓取填写的 URL。
区分材料已保存、向量索引就绪、索引失败以及当前检索方式。BM25 不因未向量化被误报成不可用。
规则阶段进入知识库时保留来源任务链接，补齐材料后可返回原任务。

## 视觉与录屏布局

桌面主要目标为 1920×1080 和 1366×768；小屏保持基础可操作，不横向挤压主按钮。
浅暖灰侧栏约 224px（#F4F3F0）、近白主体（#FCFCFB）、炭黑文字与主按钮、少量橙色（#D66A38）用于选中项和提示。细灰分隔线、小圆角、平面布局，减少阴影和独立大统计卡片。成功、待办、失败除颜色外同时标注文字和图标。
全局中文命名，工程术语保留必要的 CodeQL、AI、RAG、CWE、SARIF 并补简短说明。
页面标题约 28–32px，正文约 14–16px，按钮和复选框提供明显点击区域。
主结果与下一步操作位于任务第一屏；代码和证据可使用双栏，窄屏转为上下布局。
长表单分组，次要参数及原始 JSON 放入“高级设置”或“执行详情”。错误摘要与未满足条件必须直接可见。
每屏有明确主按钮，次要动作采用较弱样式。按钮禁用时附近展示具体原因。
加载、失败、空数据有独立界面；请求失败不伪装成空列表。
默认展示真实结果，不加入演示用假数据或自动确认模式。

## 实现边界与数据

保留现有 api/audits.ts 和 api/stages.ts 接口，页面与阶段组件按职责组合。
为任务摘要、候选计数与推荐动作建立独立的派生展示逻辑，避免在多个页面各自解释同一状态。
当前只把取得的候选、阶段和规则记录作为事实来源；缺失、未知和失败必须可辨认。
以 auditId、stageId、ruleId 定位真实持久化记录，轮询仅用于活动任务；查询缓存支持跨页面更新。
扩展公共壳层、任务路由、总览、规则库及知识库；调整阶段表单和卡片的布局与提示。
不更改后端授权、验收边界、不可变历史、隔离修复或扫描行为。
手写文件按 AGENTS.md 保持职责清晰，通常 150–300 行，大组件拆成具名模块。

## 验收与验证

构建与 TypeScript 检查通过；对修改文件进行格式/静态检查，不运行会改写全仓的命令。
有意义的前端交互测试验证路由直达与刷新、AI 候选与静态零结果并存、禁用原因、材料缺失跳转、规则验收门槛与错误状态。
使用当前真实 XSS 任务验证：静态扫描基线零结果时 AI 候选仍可见；人工确认与规则发布使用已有真实记录。
演示已发布规则的正例与反例真实回扫结果，明确正例命中、反例零结果，不扩大解释为普遍检测准确率。
确认报告下载、修复选择、规则生成、样本批准、根因确认和发布入口可达；验证可以优先使用已有记录或只读界面，避免无理由再次发起付费模型调用。
实际浏览器检查 1920×1080 与 1366×768，截取总览、任务详情、规则库、知识库图供用户核对。
主流程无浏览器异常、按钮无遮挡、无关键横向溢出；键盘操作与控件标签可用。


## 独立代码副本与运行隔离

用户要求：复制代码后在独立目录改造，不能直接修改原项目。
新目录为 `D:\semflow-audit-ui`，原目录为 `D:\semflow-audit`。
已复制当前源码（包括原目录已有未提交修改）、独立 Git 历史、本地配置和测试上传包；源码与原目录逐文件哈希比对一致。
新副本的 Git 工作分支为 `codex/workbench-redesign`；后续改动、构建产物、日志与设计文档只写入新目录。
虚拟环境、node_modules、工具安装目录、缓存及原审计运行产物未作为源码复制；后续为新副本准备依赖与运行路径。

运行配置拟采用：
- 新前端 `127.0.0.1:5174`，新 API `127.0.0.1:8001`。
- 独立 Compose 项目 `semflow-audit-ui`，独立 PostgreSQL 与 Redis 容器及持久化卷。
- PostgreSQL 主机端口优先 15440，Redis 端口优先 16380；实施时实际检查可绑定性，存在冲突则在新配置内改用空闲端口。
- 新工作进程连接新数据库、队列与新 artifacts 目录，API 代理指向新 API。
- 新数据库初始化独立工作台与流程数据；不会因为复制代码自动获得原库任务，页面空状态必须可用。
- 演示需要的材料和测试包使用真实资料及副本内文件准备；验收通过实际记录，不复制图片里的统计值。
- CodeQL 使用现有固定版本；运行产物、规则包缓存与数据库路径指向新副本。依赖安装避免沿用含旧绝对路径的虚拟环境。
- 新启动/停止入口只管理新副本的服务；不能对原版的进程、容器或数据执行停止、迁移、清理等操作。
- 原目录的源文件、配置、数据库和启动端口保留；验收核对原版前端/API仍可访问。
