## 2. 双引擎代码审计

### 目标与完整材料

验证CodeQL与Scout联合发现、统一复核能否提高有效漏洞发现并控制误报，覆盖项目级发现和专项准确性两种用途。

| 测试意图 → 材料类型 | 完整测试对象 | 固定要求 |
| --- | --- | --- |
| 漏洞发现准确性、业务语义覆盖 → 项目测试 | RealVuln论文v1.0全部26个Python项目及796项标签 | 使用论文对应的项目提交、标签和官方评分器；保留676正标签与120误报陷阱 |
| 准确性、误报控制、类别覆盖 → 专项测试集测试 | OWASP BenchmarkPython全部1230例 | 保留452正/778负的原始分布和全部14类，不重新平衡为小样本 |

RealVuln以[论文v1](https://arxiv.org/abs/2604.13764)的完整清单为准，不用本地其他版本的项目数量替换论文26项目范围。作者材料版本不同，必须单独命名评估，不能声明完成论文同榜测试。

OWASP源码固定为`f1291485808b66e20ddb6b01b10dc71b3df8c8ba`，全部任务由[expectedresults-0.1.csv](../../benchmark-data/raw/discovery/owasp-python/source/BenchmarkPython-f1291485808b66e20ddb6b01b10dc71b3df8c8ba/expectedresults-0.1.csv)登记。**历史48例只是已执行子集，本方案目标明确为1230/1230例。** 全项目源码、公共依赖和模板完整保留；可以分批调用模型，但须覆盖全部任务，不能只评分被选中的文件。

### 执行方法与对照

1. 冻结完整源码和任务清单，隔离标签、历史裁决、评分答案及源码中的显式答案标记；必要的中性清理保留代码语义和行号映射。
2. 对全部26个项目和完整OWASP项目执行CodeQL单引擎、Scout单引擎、双引擎＋Review三组评估，保存复核前并集。OWASP另运行Bandit，作为轻量外部静态对照。
3. RealVuln主表使用作者官方位置/CWE匹配与`strict_micro F3`，补充P/R/F1和按项目、CWE统计；内部根因裁决另表，不能替代作者分母。
4. OWASP按固定的精确文件＋目标CWE适配器计分，报告全1230例混淆矩阵及14类结果；此口径称本地适配评分，不冒称OWASP官方scorecard。目标类别外告警另行核验。
5. 保留漏检、误报、复核误删、重复告警、证据不足和扫描失败明细。失败或未评估的负例不能默认算TN；有效覆盖率与评分值同时报告。

预算按项目规模预先制定，并在可比组间固定；对照拥有相同源码权限。已用于开发的样本登记暴露状态，全量结果不得称全部为未见样本成绩。

## 3. 代码修复

分类：**代码修复 → 修复安全有效性、正常功能保持 → 专项测试集测试**。

### 目标与完整材料

使用[PatchEval](https://arxiv.org/abs/2511.11019)验证Repair2的补丁是否既消除漏洞又保持正常功能。完整范围包括1000项CVE任务及其中230项带安全PoC与功能测试的动态沙箱任务；Python、JavaScript和Go全部纳入。

1000项任务全部生成并保存候选补丁，按作者等价性协议评估；其中230项还须执行动态验证。其余770项不能凭等价性判断写成动态安全修复成功，两类指标各自统计。来源：[本地任务元数据](../../benchmark-data/raw/repair/evaluator_only/patcheval-dataset.json)、[论文PDF](../../benchmark-data/papers/repair/patcheval-2511.11019v1.pdf)。

### 执行方法与对照

1. 冻结1000项任务身份、目标提交、漏洞位置与参考补丁；取得作者完整230项沙箱清单、镜像和测试。动态任务校准须满足：原版功能通过/安全失败，参考补丁两项均通过。
2. 对全部任务比较“同模型直接修复”和“Repair2”。采用论文给定漏洞位置的输入口径，两组提供相同描述、目标文件和业务合同；参考补丁及最终评分答案仅供评测器使用。
3. 主表比较首候选；Repair2预算内最多3候选另表。生成阶段仅使用允许的开发反馈，最终隐藏测试不回送模型；不与论文不同反馈轮数混算。
4. 全部230项在独立沙箱执行补丁应用、功能测试和安全PoC。必须确认检查实际执行，跳过、缺失或没有有效测试不能算通过，补丁不得修改评分测试。
5. 全部1000项按作者固定的判断模型/Prompt及等价性标准评分，记录判断器身份；等价性仅为补充指标。统计无补丁、应用失败、安全失败、功能失败、联合通过与未评估，报告语言/CWE分布和耗时成本。

Go运行与验证能力、完整源码/镜像、评分器和判断器均属于全量执行前置条件。环境不可用的任务保留在原清单，不能删掉后把剩余任务称作全量。

### 论文对照与预期效果

作者PDF第9页Table 3，给定漏洞位置、单次补丁，动态分母230，包含三种语言：

| 作者配置 | 安全＋功能联合通过 | 联合通过率 |
| --- | ---: | ---: |
| GPT-4.1 | 43/230 | 18.70% |
| Gemini 2.5 Pro | 52/230 | 22.61% |
| DeepSeek R1 | 44/230 | 19.13% |
| SWE-Agent＋Gemini 2.5 | 53/230 | 23.04% |

来源：[作者表核对](../../benchmark-data/experiments/paper-baseline-alignment.md)。预期Repair2较同模型直接修复提高联合通过率、减少破坏正常功能的补丁，并使失败原因可追溯。不将自建模块成绩推广为真实CVE全量成绩，不预设超过作者最佳模型。

### 完成条件

1000项任务两组均有生成与等价性评估结果，230项全部取得校准及动态执行收据，三种语言无范围缺失；首候选与预算内结果分表。动态联合通过率使用230为完整分母，等价性分母为1000；环境异常与未评估数同时列出，不以可运行子集代替完整范围。

## 4. 规则生成

分类：**规则生成 → 生成可执行性、CWE覆盖与检测准确性 → 专项测试集测试**。

### 目标与完整材料

使用[CQLLM](https://doi.org/10.3390/app16010517)验证Rule8生成Python CodeQL漏洞检测规则的能力。完整测试分为两套材料，分别评分：

| 材料 | 全量要求 | 评价用途 |
| --- | --- | --- |
| 作者五字段需求＋Python_CWE_Bench | 固定作者需求表的全部行，配套覆盖54类CWE的完整源码/数据库 | 真实QL生成、编译、执行和CWE覆盖 |
| 作者代码生成测试集 | 完整375条固定test样本；不混入3004条train与375条validation | 按作者协议计算BLEU-4、ROUGE-1/2/L及生成耗时，作为辅助质量表 |

五字段为CWE-id、Query_id、Name、Vul-type、Description。[已保存的作者CSV](../../benchmark-data/raw/rules/cqllm-slice-9e2abe0/最终版prompt.csv)在提交`9e2abe086b7b2cc55fa22c0fc9305e972b16157f`有298行、265个不同Query_id、53个不同CWE-id。**这298行全部纳入，不抽6项；54类是论文目标数据库范围，不等于CSV类别数量。** 完整材料须核对作者实验脚本和需求表是否一致；若另有论文对应输入清单，须完整登记并单列版本，不能用现有文件冒充已对齐。

论文Table 4中的321/298是各配置的输出QL数，不直接视为相同独立任务数。用原始行号＋内容哈希保留重复需求，报告条目数、不同Query_id数与输出去重数；3754是训练/验证/测试总量，不作为生成测试分母。来源：[论文PDF](../../benchmark-data/papers/rules/cqllm-applsci2026.pdf)、[作者材料说明](../../benchmark-data/raw/rules/cqllm-slice-9e2abe0/README.md)。

### 执行方法与对照

1. 冻结完整需求清单、375条官方test划分和54类数据库。用途指定为`vulnerability_detector`；工作台默认`review_anchor`不替代本项检测器测试。
2. 两套材料均比较“同模型直接生成”和“Rule8＋双库检索”。输入、模型、初始输出次数和预算保持一致；直接生成使用独立实验入口。参考QL、对应测试答案及其等价拷贝从检索库隔离。
3. 对每条需求的新QL执行编译与实际运行，记录成功/失败、输出位置及命中的CWE；不把旧候选重跑当新生成。375条test按作者代码生成评分器独立评分，不与需求表相加成为独立漏洞数量。
4. 在完整54类数据库上统计QL执行成功率、CWE覆盖率、告警量和QL重复率。增加全数据库可核对的漏洞位置及安全反例，统计实际目标命中与误报；本项目补充标签明确标为派生，不冒称论文原有金标。
5. 首候选结果为主表，开发反馈后结果另表；最终反例不回送模型。告警量不能直接称TP，编译/执行成功不等于检测正确。通过验收的规则另做批准、发布和再用检查，记录规则版本。

作者完整测试划分或数据库不能取得时，保留全量目标与缺失项，不能临时随机切分、缩为SQL/路径任务后声明论文完整测试。这里只借用论文完整测试材料评估本平台，不要求新增微调训练，不声称复现作者微调系统。

## 5. 统一执行、验收与归档

三个模块统一遵循“冻结完整清单与环境→校准材料→全量同输入对照→独立评分→报告归档”。校准只验证评测环境，不能减少正式范围；失败的模型输出属于评测结果，未启动的任务、未准备的材料属于执行缺口，两者分列。

| 必须登记的信息 | 用途 |
| --- | --- |
| 改进版本、Git提交、工作树内容哈希、实际模块/Prompt哈希 | 确认每份结果对应哪个实现，不能只写“当前版本”或“v8” |
| 基准版本、完整任务清单哈希、项目提交、标签/评分器哈希、暴露标记 | 固定测试对象和分母，防止不同数据版本混用 |
| OS、运行时/锁文件、CodeQL CLI与查询包、沙箱镜像digest、模型真实ID/参数、检索库版本、预算 | 固定环境和对照权限，保留差异说明；不归档密钥 |
| run ID、逐任务状态、阶段产物引用、耗时/成本、报告ID与SHA-256 | 支撑复查，保存失败和未评估项，禁止覆盖原始执行历史 |

最终交付为一个总测试报告，三个模块分别列全量清单、论文作者对照、本轮同输入对照、主要指标及失败分析。每套数据须报告“计划数、已执行数、成功数、失败数、未评估数”，不得只报成功子集。

**测试完成不要求模型全部答对；要求全量协议实际执行、每项结果可追溯、缺口如实披露。** 模型无输出、错误补丁或坏QL记失败；材料缺失、环境未就绪、任务未执行时，不得标记全量验收完成。性能是否达到预期另作结论。

按照[现有归档规约](README.md)，按项目功能改进版本与测试批次建立新的不可覆盖归档。旧版本对照仍绑定旧实现身份；真实目标源码、数据库及审计产物保存在本地忽略目录，文档仅引用必要收据，不提交凭据或真实上传项目。
