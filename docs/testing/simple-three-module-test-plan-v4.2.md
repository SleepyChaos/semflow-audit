# 项目完整测试方案

日期：2026-10-11。文档版本：v4.2。本文定义三个模块完成测试所需的全部范围、方法、对照和验收条件，不作为测试进度报告。每模块最多两篇论文，目前各选一篇；代码审计另使用OWASP公开测试项目。

## 1. 测试范围与统一约定

| 模块 | 基准与项目来源 | 必须覆盖的全量范围 | 主要指标 |
| --- | --- | --- | --- |
| 双引擎代码审计 | RealVuln论文v1.0 | 全部26个Python项目，676个漏洞标签＋120个误报陷阱，共796项标签、18个CWE家族 | 论文口径P/R/F1/F3、漏检与误报 |
| 双引擎代码审计 | OWASP BenchmarkPython 0.1 | 全部1230例，452正例＋778负例，14个类别 | TP/FP/TN/FN、P/R/F1、类别表现 |
| 代码修复 | PatchEval论文v1 | 全部1000项CVE任务；其中全部230项动态沙箱任务覆盖Python、JavaScript、Go | 230项安全＋功能联合通过率；1000项补丁等价性另表 |
| 规则生成 | QLCoder，ICLR 2026正式论文 | 全部176项Java CVE任务，覆盖42类CWE；每项使用漏洞版与修复版配对源码 | 查询可执行率、漏洞命中率、修复版区分率、三条件联合成功率 |

**全量是完成要求，分批只是执行方式。** 接入校准、抽样调试和历史小集都不能替代上述范围。各基准保持独立分母，不汇总为一个项目“总准确率”。

测试对象为无账号本地工作台的三个模块，配置采用Scout7/Review9/Repair2/Rule8作为设计起点；正式执行时冻结实际代码、Prompt、环境与预算，不能用模块名称代替版本身份。分类统一为“功能→测试意图→材料类型”，沿用[测试分类表](../../benchmark-data/test-programs/classification-draft-v2.md)。已取得的成绩另见[历史结果附录](project-test-status-appendix.md)，不写入本方案的预期结果或完成状态。

### Agent名称与职责

本方案将现有模型与受控工作流组成的功能角色统一标识为以下四个Agent。它们通过模型进行判断或生成，在工作流约束下取得工具结果并依据反馈推进任务；这些名称是文档中的角色标识，对应现有服务与工作流实现。

| 功能项 | Agent名称 | 职责与重点验证 |
| --- | --- | --- |
| 双引擎代码审计 | ScoutAgent | 独立发现漏洞候选，按需读取、搜索源码和调用线索；验证发现准确性、漏检、覆盖和证据定位 |
| 双引擎代码审计 | ReviewAgent | 对CodeQL与ScoutAgent的候选统一取证复核，给出支持、排除或未确定的建议；验证误报减少、正确发现保留和证据一致性 |
| 代码修复 | RepairAgent | 理解已确认问题及业务约束，生成补丁并依据验证失败进行有限修订；验证安全与功能联合通过及候选预算 |
| 规则生成 | RuleGeneratorAgent | 基于检索知识和漏洞材料生成QL，并依据编译及开发执行反馈进行有限修订；验证全模块的可执行、漏洞命中和修复版区分 |

CodeQL是静态分析引擎；RAG检索、补丁验证、QL编译执行及评分由工具或评测器完成。人工确认、批准与发布是独立流程步骤。检索与验证结果进入对应Agent的上下文，最终成功以实际执行收据判定。

Agent名称与配置版本分别登记。设计起点中的Scout7、Review9、Repair2、Rule8分别指ScoutAgent的`scout.v7`、ReviewAgent的`review.v9`、RepairAgent的`repair.v2`、RuleGeneratorAgent的`rule.v8`配置；正式执行冻结实际采用的Prompt、代码、模型、工具和预算，不把角色名称当作版本身份。

## 2. 双引擎代码审计

### 目标与完整材料

验证CodeQL与ScoutAgent联合发现、ReviewAgent统一复核能否提高有效漏洞发现并控制误报，覆盖项目级发现和专项准确性两种用途。

| 测试意图 → 材料类型 | 完整测试对象 | 固定要求 |
| --- | --- | --- |
| 漏洞发现准确性、业务语义覆盖 → 项目测试 | RealVuln论文v1.0全部26个Python项目及796项标签 | 使用论文对应的项目提交、标签和官方评分器；保留676正标签与120误报陷阱 |
| 准确性、误报控制、类别覆盖 → 专项测试集测试 | OWASP BenchmarkPython全部1230例 | 保留452正/778负的原始分布和全部14类，不重新平衡为小样本 |

RealVuln以[论文v1](https://arxiv.org/abs/2604.13764)的完整清单为准，不用本地其他版本的项目数量替换论文26项目范围。作者材料版本不同，必须单独命名评估，不能声明完成论文同榜测试。

OWASP源码固定为`f1291485808b66e20ddb6b01b10dc71b3df8c8ba`，全部任务由[expectedresults-0.1.csv](../../benchmark-data/raw/discovery/owasp-python/source/BenchmarkPython-f1291485808b66e20ddb6b01b10dc71b3df8c8ba/expectedresults-0.1.csv)登记。**历史48例只是已执行子集，本方案目标明确为1230/1230例。** 全项目源码、公共依赖和模板完整保留；可以分批调用模型，但须覆盖全部任务，不能只评分被选中的文件。

### 执行方法与对照

1. 冻结完整源码和任务清单，隔离标签、历史裁决、评分答案及源码中的显式答案标记；必要的中性清理保留代码语义和行号映射。
2. 对全部26个项目和完整OWASP项目执行CodeQL单引擎、ScoutAgent单引擎、双引擎＋ReviewAgent三组评估，保存复核前并集。OWASP另运行Bandit，作为轻量外部静态对照。
3. RealVuln主表使用作者官方位置/CWE匹配与`strict_micro F3`，补充P/R/F1和按项目、CWE统计；内部根因裁决另表，不能替代作者分母。
4. OWASP按固定的精确文件＋目标CWE适配器计分，报告全1230例混淆矩阵及14类结果；此口径称本地适配评分，不冒称OWASP官方scorecard。目标类别外告警另行核验。
5. 保留漏检、误报、复核误删、重复告警、证据不足和扫描失败明细。失败或未评估的负例不能默认算TN；有效覆盖率与评分值同时报告。

预算按项目规模预先制定，并在可比组间固定；对照拥有相同源码权限。已用于开发的样本登记暴露状态，全量结果不得称全部为未见样本成绩。

### 完成条件

26个项目、796项标签和OWASP1230例全部纳入固定清单，每组均完成全范围执行与评分；有逐项目/逐例结果、完整对照表、14类专项结果及失败说明。缺少论文对应源码、类别或只完成部分样本时，不能标记本模块全量测试完成。

## 3. 代码修复

分类：**代码修复 → 修复安全有效性、正常功能保持 → 专项测试集测试**。

### 目标与完整材料

使用[PatchEval](https://arxiv.org/abs/2511.11019)验证RepairAgent的补丁是否既消除漏洞又保持正常功能。完整范围包括1000项CVE任务及其中230项带安全PoC与功能测试的动态沙箱任务；Python、JavaScript和Go全部纳入。

1000项任务全部生成并保存候选补丁，按作者等价性协议评估；其中230项还须执行动态验证。其余770项不能凭等价性判断写成动态安全修复成功，两类指标各自统计。来源：[本地任务元数据](../../benchmark-data/raw/repair/evaluator_only/patcheval-dataset.json)、[论文PDF](../../benchmark-data/papers/repair/patcheval-2511.11019v1.pdf)。

### 执行方法与对照

1. 冻结1000项任务身份、目标提交、漏洞位置与参考补丁；取得作者完整230项沙箱清单、镜像和测试。动态任务校准须满足：原版功能通过/安全失败，参考补丁两项均通过。
2. 对全部任务比较“同模型直接修复”和“RepairAgent”。采用论文给定漏洞位置的输入口径，两组提供相同描述、目标文件和业务合同；参考补丁及最终评分答案仅供评测器使用。
3. 主表比较首候选；RepairAgent预算内最多3候选另表。生成阶段仅使用允许的开发反馈，最终隐藏测试不回送模型；不与论文不同反馈轮数混算。
4. 全部230项在独立沙箱执行补丁应用、功能测试和安全PoC。必须确认检查实际执行，跳过、缺失或没有有效测试不能算通过，补丁不得修改评分测试。
5. 全部1000项按作者固定的判断模型/Prompt及等价性标准评分，记录判断器身份；等价性仅为补充指标。统计无补丁、应用失败、安全失败、功能失败、联合通过与未评估，报告语言/CWE分布和耗时成本。

Go运行与验证能力、完整源码/镜像、评分器和判断器均属于全量执行前置条件。环境不可用的任务保留在原清单，不能删掉后把剩余任务称作全量。

### 论文对照与预期效果

作者PDF第9页Table 3，给定漏洞位置、单次补丁，动态分母230，包含三种语言：

| 作者配置 | 安全＋功能联合通过 | 联合通过率 |
| --- | ---: | ---: |
| GPT-4.1 | 43/230 | 18.70% |
| Gemini 2.5 Pro | 52/230 | 22.61% |
| DeepSeek R1 | 44/230 | 19.13% |
| SWE-Agent＋Gemini 2.5 | 53/230 | 23.04% |

来源：[作者表核对](../../benchmark-data/experiments/paper-baseline-alignment.md)。预期RepairAgent较同模型直接修复提高联合通过率、减少破坏正常功能的补丁，并使失败原因可追溯。不将自建模块成绩推广为真实CVE全量成绩，不预设超过作者最佳模型。

### 完成条件

1000项任务两组均有生成与等价性评估结果，230项全部取得校准及动态执行收据，三种语言无范围缺失；首候选与预算内结果分表。动态联合通过率使用230为完整分母，等价性分母为1000；环境异常与未评估数同时列出，不以可运行子集代替完整范围。

## 4. 规则生成

分类：**规则生成 → 查询可执行性、漏洞命中与修复版本区分 → 专项测试集测试**。

### 目标与完整材料

采用[QLCoder: A Query Synthesizer for Static Analysis of Security Vulnerabilities](https://proceedings.iclr.cc/paper_files/paper/2026/hash/2adf01ab15adde8820622f7f24bd516b-Abstract-Conference.html)作为本模块的唯一论文基准，评价规则生成模块的整体效果。检索属于生成过程的一部分，不另设独立RAG测试基准。

**全量目标为论文正式评测的176项Java CVE，覆盖42类CWE，其中111项为旧CVE、65项为2025年新增CVE。** 每项冻结CVE描述、漏洞提交、修复提交、与安全修复相关的Diff，以及两版本的CodeQL数据库和修复位置映射；不选少量Python任务替代，不用20项消融子集代替176项完整评估。

论文采用CWE-Bench-Java及其扩展材料。完整任务ID以论文正式结果清单逐项核对，不能将作者仓库更大的候选池直接当成已评分的176项。论文正文/附录的数量差异须记录核对依据，不能自行补项或删项。

来源：[正式论文PDF](../../benchmark-data/papers/rules/qlcoder-iclr2026.pdf)、[作者项目说明](../../benchmark-data/raw/rules/qlcoder-b879ac2/README.md)、[本地作者代码版本收据](../../benchmark-data/raw/rules/source-metadata/qlcoder-commit.json)。作者代码材料起点为`b879ac2c90aac7fcc0b2e73caf117c2a12bf20e9`；执行前核对其清单、评分器与正式论文的一致性，冻结实际采用版本。

### 执行方法与对照

1. 建立完整176项任务清单，准备Java运行环境、CodeQL Java查询包、两版本数据库和修复位置映射。CodeQL使用论文的2.22.2；若采用其他版本，单列版本差异，不能直接宣称同榜提升。Java语言接入及规则验证能力属于正式执行前置条件，须真实可用，不能仅在清单中写支持。
2. 对全部176项比较“同模型基础生成”和“RuleGeneratorAgent”两组。基础生成通过独立实验入口；采用相同模型、源码权限、工具与输出预算，明确两组生成配置。用途指定为`vulnerability_detector`，不以默认`review_anchor`替代漏洞检测规则。
3. 遵循论文的已知CVE规则合成场景：两组均可读取CVE说明、漏洞版、修复版和相关安全修复Diff，并接收配对执行反馈。任务对应的已生成答案QL及其等价拷贝从测试输入和检索库隔离，通用官方查询、文档和API资料按冻结规则使用。
4. 保存首次候选结果及预算内最终结果。论文对齐的预算内评估最多10个候选验证回合；每回合记录真实模型调用、QL及反馈。模块内自动重试计入总调用预算；若实际产品预算无法对齐，单列其成绩，不与作者53.4%直接计算提升。
5. 每个新生成QL依次执行“编译与运行→漏洞版目标路径匹配→修复版对应路径检查”，保存两版本结果和命中证据。评分器、补丁位置映射及目标数据库不可被生成器改写；旧QL重跑不算新生成。

论文允许修复信息和配对反馈用于合成，因此本项是给定CVE的规则生成效果测试。跨项目泛化与独立隐藏样本验收另列工程检查，不把同一配对任务的训练反馈称为隐藏验收。

### 指标与成功标准

| 指标 | 判定方式 |
| --- | --- |
| 可执行 | QL在两版本数据库上编译、运行完成，无执行错误；空结果不自动算失败，也不自动算检测成功 |
| 漏洞命中 | 漏洞版本至少有一条路径经过对应安全修复区域，按作者映射匹配 |
| 修复版区分 | 修复版本不再报告经过对应修复区域的同一漏洞路径；不要求整个项目所有告警都为空 |
| 联合成功 | 主指标；同一候选QL同时满足以上三项，完整分母为176 |
| 辅助指标 | 作者口径的路径Precision/Recall/F1、按CWE结果、迭代次数、模型调用、耗时和成本 |

失败、无QL、编译错误、只命中漏洞版但修复版仍命中、超时和未评估逐项记录，不从完整分母删除。作者路径精确率以修复区域相交作为匹配依据，不等同于所有告警均经独立人工裁决；其他路径与疑似误报另行登记。

### 论文对照与预期效果

正式论文PDF第8页Table 1，176项全量规则合成，Claude Code Agent＋Claude Sonnet 4，最多10轮：

| 作者配置 | 联合成功 | 成功率 | 平均路径Precision |
| --- | ---: | ---: | ---: |
| QLCoder | 94/176 | 53.4% | 0.631 |

第9页Table 4另有**20项消融**：完整QLCoder成功率55%，去Doc/Ref为20%，仅Claude Code为10%。这些数值仅作小集方法参考，不作为176项全量直接对照。作者Table 2的130项共享集也保持独立分母。来源：[作者表核对](../../benchmark-data/experiments/paper-baseline-alignment.md)。

预期RuleGeneratorAgent较同模型基础生成提高三条件联合成功率，减少无效API及修复版本误报，并保留可复查证据。只有任务、允许输入、评分和预算一致时才报告与作者的差值；不预设必须超过53.4%，也不将模块整体收益单独归因于RAG。

### 完成条件

176项全部纳入两组真实生成、配对执行和评分，每项有候选QL或真实生成失败记录，覆盖全部42类CWE；首次候选与预算内结果分表，报告完整分母、失败原因和环境缺口。Java未接入、缺任一版本源码/数据库、只完成20项或只重跑旧规则，均不能标记本模块全量测试完成。合格规则另做批准、发布和再用检查，保留其规则版本。

## 5. 统一执行、验收与归档

三个模块统一遵循“冻结完整清单与环境→校准材料→全量同输入对照→独立评分→报告归档”。校准只验证评测环境，不能减少正式范围；失败的模型输出属于评测结果，未启动的任务、未准备的材料属于执行缺口，两者分列。

| 必须登记的信息 | 用途 |
| --- | --- |
| 改进版本、Git提交、工作树内容哈希、实际模块/Prompt哈希 | 确认每份结果对应哪个实现，不能只写“当前版本”或“v8” |
| 基准版本、完整任务清单哈希、项目提交、标签/评分器哈希、暴露标记 | 固定测试对象和分母，防止不同数据版本混用 |
| OS、运行时/锁文件、CodeQL CLI与查询包、沙箱镜像digest、模型真实ID/参数、检索库版本、预算 | 固定环境和对照权限，保留差异说明；不归档密钥 |
| run ID、逐任务状态、阶段产物引用、耗时/成本、报告ID与SHA-256 | 支撑复查，保存失败和未评估项，禁止覆盖原始执行历史 |
