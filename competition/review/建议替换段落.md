# 建议替换段落

这些文字以当前 SemFlow Audit 实现与仓库实验记录为依据，可用于下一轮修订；原始 Word 尚未修改。比赛品牌可继续使用“智码盾”，但需在首次出现时说明对应的参赛实现版本。

## 摘要替换建议

针对静态代码审计覆盖受规则限制、大模型审计结论难以复核等问题，本项目设计并实现了一套结合 CodeQL 与大语言模型的代码审计平台。平台支持 Python、JavaScript 项目 ZIP 上传，按漏洞发现、证据复审、辅助修复和规则生成四个阶段组织流程。CodeQL 与独立 LLM Scout 并行提出候选，Review 通过源码和工具证据复核，再由审计人员记录确认、排除或证据不足的决定。修复模块生成可下载补丁并展示所选验证结果；规则模块结合参考资料与规则范例，经过编译、正反例执行、独立验收和人工发布形成可复用规则。在仓库记录的 OWASP Python 预留 48 例实验中，平台按精确文件与目标 CWE 案例匹配取得 90.00% 精确率、75.00% 召回率和 81.82% F1，CodeQL 默认套件相应结果为 81.82%、37.50% 和 51.43%。该结果仅适用于本次样本与配置，不代表完整基准或真实项目逐条漏洞准确率。作品特色在于将自动分析、证据追溯、人工确认与分阶段验收结合，形成可审阅的审计闭环。

## 架构与流程替换建议

平台前端采用 React、TypeScript 和 Vite，后端采用 FastAPI；PostgreSQL 保存审计、阶段、证据、候选、人工决定、修复和规则版本，Celery/Redis 负责异步任务，LangGraph 组织阶段流程与恢复。源码快照、原始 SARIF、补丁及执行材料作为产物文件保存，阶段之间通过持久化 ID 与产物引用关联。CodeQL 和修复验证容器的运行边界单独配置；模型通过配置的服务接入。

漏洞发现阶段并行执行 CodeQL 和独立 Scout，合流后形成待审候选。复审阶段按候选读取源码、检索依赖并引用静态证据，保留支持、排除、待决和证据不足等自动研判结果；人工决定独立记录理由与证据，模型支持不自动视为已确认漏洞。辅助修复只针对人工确认的缺陷生成候选补丁，执行所选语法或项目测试及目标复扫，并显示未验证范围。规则生成从参考资料与规则范例中检索材料，按用途生成候选，经过编译、开发正反例、项目复跑、样例审批和独立验收；符合发布条件后由用户显式发布，供后续审计选用。

## 规则与修复边界替换建议

知识检索采用 Haystack BM25，并在配置实际向量模型后支持 pgvector 融合；当前未接入重排序模型。规则用途分为复审锚点、漏洞检测器和框架模型。当前较稳定的类型化检测规格覆盖 Python/JavaScript 的 eval、SQL 和反射 XSS；其他策略保留为实验性草稿。规则编译成功只说明其通过相应编译检查，不直接证明检测正确或具有跨项目泛化能力，正式发布仍受正反例、独立验收与人工确认约束。

修复模块以最小变更为原则生成候选，提供 syntax、python_pytest、javascript_test 等验证方案，默认执行语法检查，并可配置目标复扫。验证结果与未覆盖范围一并记录，所选检查通过不等于业务语义等价。审计人员复核证据和补丁后决定是否接受，下载 Diff 手动应用，原始审计快照保持可追溯。

## 测试章节替换建议

本节分别评价漏洞发现与规则生成，不用一个模块的结果证明其他模块可靠。漏洞发现采用预先冻结的 OWASP Python 48 个案例，含 24 个正例、24 个反例与 14 类目标 CWE，以精确文件和目标 CWE 的案例命中计分。在仓库记录的同样本比较中，平台选定配置 Scout v7/Review v9 获得 TP=18、FP=2、TN=22、FN=6；CodeQL 默认套件获得 TP=9、FP=2、TN=22、FN=15。平台扩大了本批目标正例覆盖，但仍存在漏报，不把未完成候选视为安全，不把所有 supported 输出计作真实漏洞。

本实验不是 OWASP 官方全量 scorecard，平衡抽样的精确率不能直接推广到低漏洞率仓库。平台与竞品的预算、输入和输出适配不同，不能据单次结果宣称严格等预算优势。平台 AI 墙钟与 CodeQL 扫描组成和为 472.40 秒，CodeQL 扫描为 11.72 秒；该组成和不包含上传排队，也不等于 GUI 双分支从启动到结束的实测总耗时。

规则生成实验采用六类 Python/JavaScript 任务各三轮，共 18 个请求。Rule v8 的编译、开发执行与可评估生成均为 18/18，端到端独立验收为 15/18（83.33%）。该结果说明本批任务的工程稳定性，不能称为所有 Python 规则可用率 100%，也不能证明向量检索单独带来准确率提升。功能验收应另列实际执行记录；未做 GUI、利用执行或跨项目验证的部分明确标注未执行。

## 创新与特色替换建议

本项目的特色首先是独立双源候选发现与证据复审：保留 CodeQL 的结构化结果，同时让 Scout 在受限范围内独立检查源码，再将候选与可追溯证据关联，辅助人工判断。其次是将未决状态与执行历史纳入流程：任务隔离、不可变输入、失败记录和人工决定使结论可以追溯与复核。第三是将规则生成分为草稿、编译、开发执行、独立验收与发布等状态，降低把模型生成内容直接用于正式审计的风险。这些是当前可展示的工程设计，检测效果与效率仍应通过同配置、同样本的独立实验评估。

## 背景与竞品措辞替换建议

随着软件依赖和业务调用关系日益复杂，代码审计不仅需要发现常见缺陷，还需要辨别输入来源、传播路径和安全前提。静态分析依赖已有规则与 API 建模，大模型分析则可能出现证据不足或语义误判。本项目尝试将两类分析与人工确认结合，以提高结论的可审阅性。具体漏洞统计与经济损失数字在获得对应的一手来源前不用于论证。

竞品分析分别介绍传统静态工具、专用 LLM 审计框架与通用编码智能体，并标明各项结果的样本、语言、模型和研究版本。文献数据用于说明研究背景，本项目实测数据用于评价本批配置，两者不直接组成跨平台准确率排名。对尚未复现的功能、成本和大规模性能不作全面优劣结论。
