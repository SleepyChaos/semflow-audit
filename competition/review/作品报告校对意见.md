## 审阅结论与范围

报告的“静态分析结合大模型、辅助修复、规则沉淀”方向与项目总体目标相符，但实现章节大量沿用旧版结构，且把设计目标、模型推断、编译通过写成了已完成能力或已证实效果。以当前 SemFlow Audit 作为参赛版本时，需要重写实现与测试章节，并同步替换架构图、ER 图和旧界面截图。

本次检查了完整正文、表格、尾注及 40 页本地渲染，结合实际路由、工作流、模型、适配器、前端入口和仓库实验记录复核。没有重新运行付费模型实验、GUI 验收或历史 Java/C 靶场实验；已有实验数字属于仓库记录，不冒充本轮独立复现。

定位采用“章节＋原文关键句＋P 段落编号”，P 编号来自本次 OOXML 顺序提取，含表格单元格。物理页码包含封面、填写说明、目录，正文印刷页码通常为物理页码减 3；不同 Word/WPS 环境分页可能变化，以原文关键句为主要定位依据。

结论分三类：**实现不一致**有当前代码直接反证；**待补证据**缺少本轮可追溯材料，不等于历史结果虚假；**文字/格式问题**可直接纠正。附件的填写说明只作为提交模板核对依据，不自动执行其操作要求。

### 12. 摘要中的三项成绩不能作为当前版本的已验证成绩【待补证据】

位置：摘要/P42，物理页 4。

“检出量提高 57.9%”“CASTLE 召回约 88%”“Python 规则可用率 100%”分别依赖旧 Java 实验、10 个 C 文件、53 条规则评估；当前仓库未找到足够材料将这三组数据绑定到当前默认版本。应提供 commit、模型、提示版本、源码哈希、工具版本、套件、输入、完整输出、标注与计分记录，或改用下述已记录的有限实验。

### 13. 30/19 与“新增 18 个漏洞类型”的口径不一致【待补证据/表述问题】

位置：3.1/P168–169，物理页 24。

`(30−19)/19≈57.9%` 算术正确，净增数量为 11。若增强结果另有 18 个新增实例，需说明交集 12 个及 7 个基线独有结果的处理，不一定矛盾，但目前没有集合账本。实例数、独立根因数、CWE 类别数不能混写为“漏洞类型”。告警增加也不自动等于召回提升。

建议：增加逐条人工确认记录与集合关系；“显著”需要明确统计依据。当前不能把不同模式产生的原始告警直接计成真实漏洞。

### 14. CASTLE 小样本无法代表整个基准，精确率需补混淆矩阵【待补证据/方法问题】

位置：3.2/P174–223、表 4-1，物理页 24–25。

列出的 10 个文件都属 CWE-125，含 9 个标注为有漏洞、1 个安全对照。“单例漏报”若按案例计分可对应 TP=8、FN=1、Recall=88.89%；按相同案例级口径，FP 至多 1，Precision 最低为 8/9，无法同时得到约 66%。若 66% 是逐条告警精确率，则可能存在多个误报，但须另列告警分母、重复合并及匹配规则，不能与案例召回混用。

官方 CASTLE 有 250 个 C 微程序、25 类 CWE。全量公开 CodeQL 成绩与顺序抽取的 10 个同类样本不构成同样本公平比较；需要在同 10 个文件上运行相同 CodeQL 基线。建议称为“CWE-125 小样本可行性实验”，不要写“证明总体基准性能”或“彻底排除幻觉”。[官方数据集](https://github.com/CASTLE-Benchmark/CASTLE-Benchmark)

### 15. 53 条规则的自评分不能直接称为“100% 可用”【待补证据/指标问题】

位置：3.3/P225、图 4-4，物理页 26。

49/53≈92.5% 成立，但“质量分”“可用”“高度可用”缺少评估者、量表、阈值、编译/执行记录及独立正反例。C#、C++ 不在当前产品语言范围内。由 49 条全部可用、另外 4 条可用率 50% 可推得总体可用数 51/53≈96.23%；90.6% 若指另一“高度可用”阈值，必须明确分母与阈值。按已显示的分组均值加权约 95.96，95.9 是否受原始精度影响需原始分数核对，不能直接认定造假或强行改数。

建议：分开统计结构有效、编译成功、开发执行、独立验收、原项目确认及发布；未知 CWE 不能计作明确覆盖类别。官方范例编译通过与模型生成新规则可用也应分别统计。

### 18. 竞品表应区分文献自报、第三方复测与本项目实测【方法问题】

### 19. RepoAudit 引用混淆最大/平均值，且时间换算错误【确定问题】

位置：5/P356，物理页 35。

“80 分钟（13 小时以上）”明显错误。实证研究 v2 表 XII 中，Sonnet 3.5 配置输入/输出最大约 2.255 亿/3808 万，平均约 3263 万/499 万；平均费用 $172.77，最大耗时 312.87 分钟。GPT-5.4 配置最大耗时 894.63 分钟。论文正文跨配置概括了超过 800 分钟，报告不能把一个配置的费用和另一配置的最长时间拼成同一行。建议直接按固定模型引用表 XII。[实证研究 v2](https://arxiv.org/html/2601.19239v2)

### 20. SFDR 必须限定语言、模型和研究版本【表述问题】

位置：5/P357–365。

文中的 59.55% 是受控 C/C++ 集的合并召回；IRIS 97.80% 与 LLMDFA 100% 对应特定模型的 Java 真实项目抽样。Codex 9.09%/Claude Code 74.07% 属于 C/C++ 设置，不能概括全部真实项目。SFDR 是已抽样告警中的误报比例，与负例分母的 FPR 不同。论文 v2 使用 Codex 筛查并作抽样人工验证，不能将其全部表述为“所有报告经人工复核”。给表格补充限定，禁止与本项目 FPR 直接求差。[实证研究 v2](https://arxiv.org/html/2601.19239v2)

### 21. QLPro 被过度简化，Antiproof 缺少可定位依据【引用问题】

QLPro 的原论文将其定位为 LLM 与静态分析集成的自动漏洞发现框架，并报告 Java 项目检测结果，不能说它“仅聚焦规则生成、功能单一”。“没有修复”与“没有审计上下文”要分开核验，缺少证据时删除后者。Antiproof 的计算开销和大规模性能判断需补完整论文或官方仓库、版本、实验条件，本轮不把无出处结论写成事实。[QLPro 原论文](https://arxiv.org/abs/2506.23644)
