日期：2026-11-02。结论来自源码、10-14 正式 F 回执与保存请求核对；本轮没有新模型调用、扫描或利用测试。

后续状态：本文记录修复前诊断；同日随后已在本地实现有效不足的受限补证和历史保留，详见[补证机制与修复](../../design/audit-mechanisms/evidence-feedback.md)。以下历史成绩、原始失效路径及未执行的四组重放保持原含义。

## DVGA 回答了什么

**DVGA 暴露了通用流程中的缺口：有效的 `insufficient` 尚未驱动自动、候选级的补证闭环。项目已经有证据读取和前提校验，不能说整个项目完全没有实现复审或补证能力。**

还要区分“证据在库里”和“证据在该次模型请求中”。对 `dvga-021`，中间件及视图封装证据在该阶段更早的请求中已经出现，最终这个批次却没有带入。不能据此说模型看到了这些正文仍忽略；能直接证实的是宿主没有将已取得的相关证据组织到这个未决目标中，也没有在它声明缺失后继续补证。

单例足以证实这条失效路径存在；不能用单例推断全部候选都如此，或补证之后一定成为 TP。

## 哪些已经实现，哪些仍缺少

| 机制 | 实际状态与边界 |
| --- | --- |
| Scout/Review 按需读取 | 已有 `read_source/search_source/callers` 与多步工具循环，本例确实执行过两次读取 |
| 初始相关源码供给 | 已有目标预读、bootstrap/import 启发式和控制上下文；每批从目标材料重建，没有因此自动带入全阶段所有相关页 |
| 三前提与引用校验 | 已有属性一致、源码引用、前提状态与 supported 门控；不是对所有文字推导是否成立的独立逻辑证明 |
| 无效/漏答候选恢复 | 已有一次有界恢复，保留历史与失败状态 |
| 有效 insufficient 的反馈 | 尚无通用调度：接受该评估后即作为 reviewed，恢复路径不再选中它 |
| 缺失前提定向检索 | 工具选择主要由模型提出；尚无宿主把缺失事实转成取证任务、检索同快照已有页并重新判断的完整策略 |

直接代码依据：

- [冻结的unified_review.py](../../artifacts/research/realvuln/20261014-ablation/implementation/system/backend/app/services/unified_review.py#L128)：模型返回 final 后直接 `return save_batch(...)`；只有保存抛出校验错误才带反馈继续，并不因为有效 insufficient 再开一轮。
- [review_recovery.py](../../system/backend/app/services/review_recovery.py#L8)：`reviewed` 收集所有 recommendations，未按 supported/insufficient 区分；已有有效评估者不会进入未评估恢复。
- [review_pool.py](../../system/backend/app/services/review_pool.py#L213)：按当前批次候选取得材料，构造独立上下文。
- [review_tools.py](../../system/backend/app/services/review_tools.py#L57)：执行模型提出的工具，并刷新来源窗口；没有在每次新 imports 出现后自动规划整个缺失控制链。
- [discovery_context.py](../../system/backend/app/services/discovery_context.py#L212)：三项状态和源码引用的门控，语义蕴含并非普遍自动验证。

`local_control_context.missing_modules=[]` 只表示该启发式选中的模块没有登记缺页，不能解释为“所有中间件均已核查”。另一个通用风险是任意复用读取会使下一轮强制 final；它并非本次 DVGA 的触发原因，需另做回归后再决定修改。

诊断时、后续修复前，上述循环、恢复与工具模块同10-14冻结实现逐字节一致；当时 `discovery_context.py` 的差异是导航索引缓存，不能视为已经修复这个闭环缺口。

## 全量诊断：研究对象不止一个案例

本轮先验证审阅包2429个文件，再读取正式 F 的26个项目、1094个候选：

| 观察项 | 数量 | 可以说明什么 |
| --- | ---: | --- |
| supported / insufficient / excluded / unknown | 709 / 264 / 78 / 43 | 状态不同，阶段 completed 不代表全部安全条件已决 |
| 存在 insufficient 的项目 | 22/26 | 未决问题跨项目存在，未证明这些都是错误弃权 |
| 涉及输入或业务策略前提缺失 | 220/264 | 首要研究对象；缺失项来自模型声明 |
| 涉及防护前提缺失 | 159/264 | 与上一行重叠，不能相加 |
| 涉及操作前提缺失 | 24/264 | 需要核对真实调用/绑定等事实 |
| 所在批次有工具读取的 insufficient | 104/264 | 做过读取仍可能未决，不证明工具读取服务于该候选 |
| 曾进入未评估恢复，最终 insufficient | 47/264 | 是先前漏答/拒收的恢复记录，不是有效 insufficient 的后续闭环 |

三项目保存请求的补充核查：验证1060个文件哈希，找到33个被接受的 insufficient 评估事件，其中13个的缺失前提文本提及可识别源码文件，8个涉及更早请求已经出现而当前未提供的页；32个在非强制 final、仍有后续调用位置时结束。

另有4个事件的缺失前提文字提及当前已提供的完整文件。这只是检索提示：**文件可见并不等于所需业务事实已经存在，不能将这4个记作已确认的推理错误。** 这也是为什么全量自动统计与人工前提裁决必须分别保留。三项目是所选案例，不能把其比例外推到26项目或其他数据集。

## 互补发现：先排除计分和范围混杂

独立 A/B 命中交集80，静态独有26，Scout独有309，双方均未命中261。309个Scout独有金标中：

- 34个的位置附近有其他CWE的静态输出，应先检查是否为分类、邻近不同根因或匹配容差造成的差异。
- 275个附近没有静态输出，仍需核对运行规则与提取范围，不能直接归为复杂语义理解。

此处“附近”严格使用冻结官方匹配器的位置/替代位置与±10行规则，仅放宽CWE，不是按人类根因重新裁决。本轮没有将任意一例自动标为“规则没有覆盖”或“语义创新已证明”。

复审的收益也要同时看损失：历史 C→F precision从31.37%到49.17%，recall从61.54%到52.37%；金标保留353、丢失63、新增1。分类变化与贪心匹配有影响，不能把这63个全部归因于错误复审，也不能只把 precision上升当成推理已经更正确。
