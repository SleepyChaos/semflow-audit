# Repair3 生产修复滚动改进与固定小测（2026-10-16）

当前状态：R13 原四例统一实现验证、R14/R15 开发验收已结束。按用户最新要求以性能为主，仅保留必要正确性冒烟。100 项全量测试保持暂停，未上传原始审计产物或源码到代码仓库。

## 结论边界

已修复生产链路的工具协议、重复取证、文档冗余、可写窗口丢失、真实 provider 冻结策略接入及复审证据未回接等问题。原 Repair2 的 SemanticRepair/LangGraph 图继续使用，新 API 阶段默认版本化为 Repair3；不是只修改基准提示词。现有生产默认入口、真实适配器（Mock HTTP）、隔离应用、冻结恢复、实际证据及验收作用域均有行为回归。

不以更快报错、更多候选、语法通过或模型自评通过作为有效修复。原固定四例各轮结果仍有质量波动，不能将某一轮速度或某些样本的最佳结果拼成系统成绩。原安全基准依赖上游新增 API 名称时保留未通过，独立公共行为探针另列，不回流隐藏测试给模型。

## 性能优先补充（用户最新范围）

性能分为完成时延、调用/token开销、重复工作和可继续执行性，不能只看失败返回得快。没有用户指定的硬 SLA，以下仅给出小样本观察，不以任意阈值宣称生产全面达标。

原三例同口径比较：旧 v4b 合计19次调用、128.37秒、142,927输入token；R13合计30次调用、129.68秒、362,131输入token。时延增加约1.02%，调用增加57.9%，输入增加153.4%。旧版两例未产出有效候选，R13三例均完成实际功能验证，工作量不同；既不能把额外工作全部归为浪费，也不能宣称总体资源效率已经改善。

R13四例单个生产修复阶段16.42–80.58秒，模型单请求超时、取证/候选次数和重复停滞均有界；样本中没有小时级卡住。独立基准依赖安装46–146秒另列，不计为模型阶段。发现阶段此前两例的123→94调用、569.05→513.22秒是不同阶段的结果，不能当作修复提速证据。

本次只修两处可核实的浪费：

1. R15在46.32秒、8调用后因上下文失败，不能算成功提速。其第二候选载荷60,439字符，实际源码18,825字符；相同失败解释在feedback与checks重复发送。原失败载荷离线重建与原始指标完全一致，去重后58,476字符，减少1,963字符(3.25%)，满足冻结源码扩展规则；诊断全文仍在failure_feedback.summary，原始检查收据不变。没有放大硬上限，也未截断源码。
2. 显式选择验收套件时改为语法→已选真实测试→独立语义复审。明确执行失败的候选直接进入原有限重试，避免先付费复审失败代码。两个小例均两候选收敛，模型复审由2次减为1次；最终通过候选仍须独立复审，基线两轮缓存和每候选两轮执行保留。这是确定性的调用节省；不直接换算成真实模型总耗时百分比。

R14/R15为已接触样本上的公开RFC开发验收，输入包含显式选定的7项要求，与R13原始标题输入不同，不能合并为原基准成绩。R14新增异常漏导入导致NameError；R15为上述上下文失败。失败记录保留。本次不再扩展安全测试集。

载荷证据：artifacts/research/repair3-production-tests/retry-packing-performance.json。针对性冒烟：performance-smoke-permitted.xml；真实执行：performance-real-v4.xml。同目录保存最终一个难例的独立性能检查，不覆盖R15记录。

### 最新性能冒烟的真实结果

最终一个难例通过现有生产RepairService/LangGraph执行，阶段 adeb4fdd-06ad-48f8-aa96-b153ed5b95c6，75.47秒、13次真实模型调用、151,205输入/9,517输出token。两次候选迭代：首次实际NameError被执行反馈定位；第二次通过所选7项验收及独立语义复审。只调用一次独立复审，未复审明确失败候选。正常基线两轮复用，每候选两轮执行。没有小时级等待、重复读取停滞或上下文限额失败。

R15的46.32秒是失败，不能把最新75.47秒与它相比称时延下降；最终输入验收要求也不同于R13原始基准，不合并原评分。单次开发样本说明链路可在分钟量级完成有实际验收的修复，不证明全量P95、并发吞吐或整体token性价比达标。按本次性能优先范围收尾，不追加大规模安全回归；全量仍暂停。

结果与实现摘要：artifacts/research/repair3-production-tests/final-performance-one-case/performance-summary.json 和 implementation-hashes.json；原始调用/检查记录保留于 artifacts/runs/adeb4fdd-06ad-48f8-aa96-b153ed5b95c6。

## 系统改动及生产适配

1. 工具参数契约、完整行分页、实际 EOF 与累计已读/未读区间；错误请求有界纠正，重复停滞停止。临时工具猜测不作为最终支持事实。
2. README/配置按需读；修复诉求和用户已选验收预期作为独立请求证据，实际行为必须由源码支持；验收套件验证所属、目标覆盖和哈希，不向模型传执行测试代码。
3. 理解与应用使用同一组授权可写文件。可写内容恰好为实际已读区间并集；不丢失大文件已读正文，不因小文件而赋予未读行写权限。精确旧文本、原快照和失败历史保留。
4. progress 下保留真实 token/call 用量，有限图按进展执行；bounded 保留操作者总限额。真实 provider 冻结 40,000 字符优选/80,000 默认硬上限，只有源码增长可推动扩展，非源码开销仍受约束，旧阶段不追溯扩权。有限调用预留从工具/候选计划计算，避免独立12次阈值截断合法进展。字符限额不是计费 token 或模型容量声明。
5. 将模型解释当作可纠正假设；不能扩大原确认诉求。解释错误回到重新理解，明确候选冲突复用已有评估，未知不伪装为通过。
6. 从改动 Python 函数追踪两层语法调用位置，每个位置提供实际源码，要求逐项保持/授权改变/冲突/未知判断且引用自身证据。最多8个窗口、遗漏显式报告；不宣称完整解析动态派发。
7. 复审读到的调用点经审计所属、摘要和原文重验证后进入下一次理解；仅在已授权文件内补全实际已读可写窗口，解决“复审看到了但生成器没看到”的衔接问题。
8. 未能成功应用候选记为修复失败；不因保存了 needs_review 记录或阶段 completed 就算安全通过。

生产设计与限制：[repair3-progress.md](../../design/repair3-progress.md)。repair_semantics.py 约432行，已按职责把窗口、需求、取证、预算和调用影响拆至模块；留下同一图节点的编排与历史保存，未机械拆散。

## 公共接口开发探针（不替代原分数）

- JWCrypto：同一公共 JWE 探针下，漏洞版把攻击者 p2c 带到昂贵 KDF，官方修复与R8候选均在 KDF 前拒绝，正常加解密保留。观察器主动停止高成本计算。
- Flask-CORS：漏洞版错误允许大小写不同路径；官方修复与R12候选拒绝，正常路径和大小写不敏感请求头保留。
- Authlib：增强后的公共 JWS 探针发现R7候选仍接受已配置扩展的未保护 crit 声明。早期仅测未知扩展的探针不足，已保留版本说明并明确由增强版纠正，不能把初版通过写为漏洞修复。
- 这些均为已参与调优后的开发验证，原版、官方修复、候选用同一探针；不构成独立泛化评估。

## 剩余限制与验收依据

尚不能据平台回归或少数公共探针宣布整体修复能力达标。有效性须以同一实现的固定样本执行结果为依据；原安全基准与公共行为证据分开。CVE-2023-6681 的命名兼容失败、CORS上游新增helper的缺失，以及Authlib真实保护域缺陷须分别列明；不要把所有未通过都解释成测试兼容问题。

全量继续暂停；不为绕过安全检查改测试、添加上游隐藏命名或删除业务。后续按性能优先继续；不再为本次效率验证扩大安全用例或反复抽样凑成功率。
