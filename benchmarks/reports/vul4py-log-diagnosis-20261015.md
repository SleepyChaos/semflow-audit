# Vul4Py 进度与日志问题诊断

2026-10-15，根据原始100项校准/修复回执与端到端日志核对。用户要求CQLLM后台执行期间处理本模块。原结果不覆盖，修复后的结果不能直接混入旧版能力分数。

## 为什么已知位置修复看起来很快

100个结果文件并不代表100次修复：85项因oracle不合格未调用修复模型；15项校准接纳，2项补丁完成测试、1项联合通过。恢复后当前14个阶段ID，另有连接恢复前的历史阶段，账本须去重并保留历史费用。其余早期退出包括上下文预算、取证停滞、快照符号链接和不支持的目标类型，均不是成功完成。

对85项未校准条目的日志做启发式分组：25项出现缺测试模块、8项pytest参数不识别、12项导入/收集错误、13项依赖安装或容器失败、5项其他缺JUnit、22项断言或运行错误。该分组用于排障，不是逐项根因人工裁决；25+8是本轮声明式测试依赖修复的33项候选，不能认为全部会恢复。

旧官方安装命令多为`pip install -e .`，未安装项目已有test/dev extras或测试requirements；同时引导脚本会升级pytest，可能与旧插件约束冲突。明确样例CVE-2024-53848缺responses，pyproject已经声明responses和pytest版本。

## 为什么端到端慢且没有跑完

此前8份状态中：1完整、5部分、1输入失败、1供应商中断。第7项目Scout最后一次调用timeout，在已读取74/213个窗口后停止；运行器又阻塞全量下游，尚未形成100项结果。部分项目虽然读取全部窗口，业务任务仍有unknown或Review未决，不能把窗口读完称作全部审计完成。

实际扫描包含测试、示例及第三方源码：例如case-006读取211窗口，Scout240次调用、约1543秒。不能用空输出、删源码或不记录的排除来提速。第三方`_vendor`目录在当前分类中也可能被视作普通源码，后续应记录角色并验证覆盖代价；本轮没有据此删除待扫描文件。

## 已修正与验证

1. 实现哈希误报已修复：运行产物txt不属于冻结实现；201源码原本未变。CODEQL_PACK_PATH预检及正确路径已接入。原基础设施失败及静态数据库已归档，不计作新的漏洞能力结果。
2. 修复输入准备提取到repair_inputs：纯HTML/配置目标在模型前明确报unsupported_repair_target，避免付费后报“缺少实际源码正文”。该改动没有扩张尚不支持的修复/验收能力。
3. 已有其他代码证据时仍确保实际可修改目标正文被读取，保留精确文件/行关联。
4. Repair2启用已有progressive取证复用机制：保留原证据ID、复用已提供窗口、提供纠正反馈；仍有有限工具预算与重复无进展终止，不能以预算耗尽推断安全。
5. 环境重校准独立版本：仅按项目pyproject可选依赖或明确测试requirements安装，不凭缺失模块名猜包；记录声明哈希与pip freeze，保留原测试/断言、固定镜像和原回执。新目录`artifacts/research/vul4py/20261015-oracle-env-v2`，先验证两个样本，不宣称33项均完成。

23项语义/恢复/新输入回归通过，5项依赖声明及oracle回归通过。首次普通测试因sandbox阻断本地数据库连接产生15项setup错误，未当作实现失败；使用正常权限重测后23项通过。容器环境重校准仍在进行，尚无“修复了85项环境”的结论。
