# 首轮测试后的改进与下一轮验收

日期：2026-10-05；依据：[实际结果](calibration-results.md)。这是待执行计划，未把产品修改或正式成绩写成已完成。

追加[失败溯源](failure-analysis.md)：P1还需处理43候选与16批次槽容量的不匹配；P2还需真实diff/no-op事实校验、unknown不触发实现修复循环；P3先改SQL/NoSQL资料角色的子串错配。原实验计数不覆盖。

## P0：先校准输入与评分，补齐外部比较

原因：匿名化 loader 曾不一致；RealVuln 仍有类别标题提示；QL 派生任务缺完整入口；修复 oracle 尚无人审。错误输入或不可解任务会污染结论。

实施：

1. 将文件名/模块注册集合 invariant 纳入导出；本轮已修未来导出器并留测试，旧产物不改写。补静态可达性/导入关系检查，无需启动服务。
2. 冻结开发/隐藏按仓库根因分组，去掉显式 gold 和类别提示；源码安全语义本身不删除。逐文件保存原/导出 hash 和允许读取目录，隐藏答案只有 evaluator 可访问。
3. 对两个 QL 任务先提供确定性参考查询：开发与隐藏正例均命中、安全变体无命中；若参考查询也失败，修正入口/API模型或排除任务，另立输入版本。
4. 补 runner 普通测试：跨任务文件拒绝、恢复不重复模型调用、失败非空成功、隐藏结果不能回流生成器。已通过的3个评分/loader测试不能代替这些隔离测试。
5. 优先取得 h11 等完整固定 pre/post 和官方纯单元安全/业务测试；人工复核原版正常通过、安全失败、官方修复双通过。正式任务不足明确延期对应分支。
6. 对齐 RealVuln 论文 v1 与本地 v3.1；优先相同子集的作者逐项输出重评分。PatchEval/Vul4Py 固定官方动态清单与严格双 oracle 条件。不可比原表继续只作参照。

验收：任务列表/输入/评分/语料/runner hash 一致；每任务参考 oracle 通过；gold 暴露与 unknown 有登记；具备同子集基线后才计算论文差值。

## P1：双引擎确认能力

原因：粗筛有 4 个额外主根因线索，但 DVNA 43 个候选均未复审；窗口请求超上限；Scout 出现未绑定 `rp()` 假设。

实施：读取工具暴露明确上下限并分页；越界反馈给出合法窗口和 continuation，重复无效读取及时终止该动作。按来源/危险操作/关键 guard 归并根因，先取 import/符号绑定证据，再作漏洞判断。分开“源码缺陷成立”“项目内可达”“部署依赖”，要求证据充分但不强求与静态条件无关的外部部署信息。

验收：同开发项目同预算重跑，覆盖所有待审候选或明确未决原因；新增 supported 根因须 evaluator 复核；FP trap 不确认为漏洞；比较根因级 TP、误删、unknown 和真实时延。不能仅以候选数量增加通过。

## P2：语义上下文的去重与增量更新

原因：15KB 目标文件的简单任务，v2 两次上下文溢出；中位耗时约为旧版 10.8 倍。

实施：项目/模块/目标语义分层保存；源码证据以 file hash+行范围的稳定 ID 引用，重复窗口合并，摘要关联原证据，不重复注入整段源码。每轮提供当前业务不变量、未决事实、目标代码和新增错误差量；工具读取按缺口补充，保留不可变原证据可追溯。超预算时先压缩重复项或缩小修复范围，不能静默截断关键证据；简单局部任务可在明确语义合同后提前进入生成。

验收：同一校准任务 v2 三轮都能形成可评测补丁且通过当前双 oracle；错误反馈能进入下一轮；记录上下文大小、重复比例、调用/秒。然后用多个独立模块验证业务保持和安全变体，单例通过不宣称整体提升。

## P3：规则必须绑定目标源码并验证真实覆盖

原因：五个规则通过开发样例却均零隐藏 TP；未给 Candidate 的入口绕过了目标命中确认；纯向量和 NoRAG 控制不完整。

实施：将漏洞描述、源码 source/helper/sink/guard、资料和范例分别记录为证据。QL 规格显式引用真实 API 绑定，目标路径无候选也必须建立源码目标条件。开发自造样例与原项目单规则命中分开；原项目目标条件未命中只能留失败草稿，不能标“可用检测器”。官方模板可复用，但零覆盖不算新增能力。加入同根因安全变体、不同 API 的同类漏洞和跨仓库任务，排除硬编码样例名/行号。

检索独立建立 qrels，标注漏洞背景、API/QL版本适配、范例可迁移性；报告资料/范例的 nDCG/MRR/覆盖。随后固定证据或用四组同预算生成验证其影响。显式区分角色混合路由与纯模式，支持合理无检索控制（无需伪造 knowledge ID），隐藏评测仍不回流。

验收：校准参考任务可解；真实目标正例命中、安全反例不命中；新规则确实覆盖原 CodeQL 同套件未发现的独立根因；无检索/BM25/向量/混合均可公平运行。编译率、隐藏效果和知识相关性分列。

## P4：质量达标后再测速度

原因：上下文失败和窗口浪费占用了调用预算；阶段顺序测试不能代表并行双引擎端到端速度，机器同时有其他任务。

实施：固定成功任务和质量要求，独占同机时间窗口，分别测首次建库/首次查询/同库查询及完整并行流水线；每项三次，原始时间、超时和失败成本保留。先减少重复读取、重复 embedding 和无效循环，质量证据按现有预算验收；默认内存 OOM 另做资源敏感性试验，不替换主结果。

验收：相同质量和输入下报告 median/p95（样本足够后）、调用/token、真实总墙钟；不得把减少取证或提前失败的耗时下降称速度提升。

## 执行顺序与断点

P0 → P1/P2 开发集修正 → P3 可解性与规则门槛 → 正式 E06 冻结 → E07–E10 质量对照 → P4/E11 效率 → E12 报告。每轮新建 run ID，不覆盖 `20261005-calibration-v1`。续接以 [state.json](state.json) 为准；先检查已有产物，禁止为了恢复上下文重跑付费批次。
