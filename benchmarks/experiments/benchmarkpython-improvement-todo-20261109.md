### G1 技术门与 G2 进展门

**G1 技术门（进入真实小样本前）**：同一冻结快照上完成至少一次实际 public 编排的 Review→Scout→Review 往返；任务和证据身份有效，新候选进入复审、未评估保留 unknown；重复任务不重复付费调用，父子共享预算，恢复不重复生成，取消/失败留痕。工具或模型替身须明确标注。CLI 无平台依赖、Web 既有 public 路径兼容回归通过；不强制新增 GUI 功能。

**四组固定比较**：A 当前流水线；B 同总预算/工具权限的单 Agent 工具循环；C 两 Agent 的一般文字反馈；D 两 Agent 的明确命题/任务反馈。C/D 角色、工具、轮数上限和模型一致；四组共同冻结可见源码范围和成本上限，实际消耗另报。保持最小收据/安全校验一致，避免仅 D 多一道证据门造成混杂。CodeQL 静态事实供给先保持一致，其增量作用在后续专项中单独消融。

**G2 进展门（进入范围选择前）**：六任务按预注册规则运行并保留全部失败；D 至少在两个不同项目的任务上相对 A/C 获得可追溯到新获取或新核实事实的正确改善，固定样本中不新增错误支持/错误排除。相对 B 至少在一个相同预算任务上有正确性收益，或在相同正确性下有可复核成本优势，且无观察到的正确性退化。逐项记录，与 B 持平则标 `inconclusive`，不能认领多 Agent 优势。该门仅是继续投入的开发决策，不是显著性或泛化结论；不得看到结果后改门槛。

G2 不通过：回退缺口表达/取证/角色分工，最多推进有新失败原因解释的新尝试，不以增加轮数、换样本或扩大到全量追求正结果。若 B 与 D 一样好，保留协议价值并重新评估多 Agent 的必要性。

### 协作有进展后，如何决定 CodeQL 能力范围

SCOPE-001 交付表至少包含：语言/框架、漏洞类别、共同缺口、源码与工具证据、原生规则及 pack 版本、构建/提取范围、已知安全近邻、可补充的静态事实/模型、近邻方法、预期收益和不覆盖内容。

候选缺口包括调用目标绑定、包装函数/第三方传播摘要、校验与最终危险值之间的关系；它们目前只是待诊断假设。选择约两类漏洞须有多个独立项目的同类失效证据，并存在可独立核验的修复方向。升级查询包、正确构建或标签修正即可解决的问题单列，不包装为语义能力突破。保留 CodeQL 和 LLM 各自作用、无 CodeQL 消融与安全近邻；不以“CodeQL 没告警”直接推断语义缺口。

SCOPE-002 冻结研究范围后，再制定专项实现和独立测试方案。若需模型/规则生成，算法归 `core-rules` 并经 public 契约调用；共享协议归 contracts，发现协作归 `core-discovery`。GUI、平台任务调度、接受/发布和真实部署不是本阶段算法任务。
