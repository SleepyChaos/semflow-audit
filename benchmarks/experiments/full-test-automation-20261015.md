## 自动续跑顺序

1. 核对检查点和进程。采用同一输出根、固定任务身份；没有获得任务锁的执行器不得派发模型调用。进程仍有效推进时只观察，不并发启动第二套相同任务。
2. 修复基础设施并恢复已知位置修复。归档旧回执和恢复事件，区分连接重试、环境重校准和模型修订。已付费阶段优先恢复/验收已有补丁。不得删除 `.started.json` 后盲目重跑；无法安全重入时新建有父执行引用的恢复尝试，并累计旧费用。
3. 环境校准使用原版与官方修复版，在隔离容器中完成。测试依赖只依据项目依赖声明补齐；保留原校准版本，新版本另存身份。不能修改测试断言、标签或把失败测试从分母中移走。原版/官方版均失败不算模型失败。
4. 已知位置修复恢复完毕，所有 100 项均有可解释终态，才启动完整 100 项端到端。5 个输入失败仍保留在分母；AI supported 与人工确认分开。模型输入禁止接触参考补丁、隐藏测试或评分反馈。
5. 然后冻结 CQLLM 298 行需求、重复 Query_id 身份、测试数据库与评分协议；实现同模型 NoRAG / 当前 RAG 两组，逐项检查编译、执行、定位和正负例。没有定位金标时明确“未评估”，可执行率不冒充正确率。不得把作者答案直接放入生产 RAG。
6. 汇总全部回执、模型阶段去重账本、未知用量、失败分类、协议及相对路径报告；去密钥打包，校验文件哈希及压缩包完整性，上传 GitHub Release 附件。保留原始审计产物在本地，不将项目源码、数据库、`.env` 或凭据提交进代码仓库。上传后保存 Release URL、资产 ID、大小及下载校验结果。

## 自动恢复策略

- 校准容器并发最多 2，付费模型阶段先保持串行；任务之间不混源码。
- 不因累计 token 数停止仍有效推进的整个批次；保留单任务工具、修复次数与无进展限制。模型能力终态不自动重跑刷分。
- 连接异常采用有记录的退避；同一签名连续 3 次失败后标记阻塞，停止该分支继续扣费。收到明确配额耗尽信号时保存状态，待后续唤醒核对恢复条件；不盲目持续发付费探针。
- 每次先查看最近回执及成本变化。连续两次观察无进展时结合阶段活动时间、子进程和容器状态诊断，不能只看 PID；不杀共享数据库/Redis。
- 用户随后明确要求机械化执行、不要定时。已停用聊天 heartbeat，改用本地单进程控制器及独立只读监控器；不由定时模型决定下一步。
- 机器睡眠、网络/审批或配额限制可能阻止本地进程执行；控制器会保存检查点。定时自动化已停用。
