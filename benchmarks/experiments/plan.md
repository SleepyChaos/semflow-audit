# 三条创新链路的正式实验总计划

2026-10-13 后续安排：用户要求对尚未完成全量评测的 **Vul4Py 修复与 CQLLM 规则生成**开展全量测试，执行范围与口径见[新登记计划](vul4py-cqllm-full-test-plan.md)。本页原有小批校准及 CQLLM 仅作参考的范围属于历史计划，不能代替这次全量要求。

版本：2026-10-05 / v1。范围与评分细则以 [评测协议](../evaluation-protocol.md) 为依据；任务进度只登记在 [state.json](state.json)。

## 1. 要回答的问题

| 主线 | 可检验问题 | 主证据 | 不足时如何报告 |
| --- | --- | --- | --- |
| 双引擎发现 | 独立 Agent 能否补充 CodeQL 漏检根因，复审能否降低误报且保留真漏洞？ | 根因级召回、精确率、新增 TP、复审误删率、未决比例 | 不完备标签只报告已知根因召回和已裁决告警精确率；披露未决数量 |
| RAG 规则生成 | 检索是否找到适用知识，生成的 QL 是否能运行、定位和跨项目复用？ | 检索相关性；编译/执行/目标命中；隐藏正负例；新增覆盖 | 编译通过与再现官方规则单列，不包装为新漏洞检测能力 |
| 语义辅助修复 | 业务语义取证是否提高安全修复与正常行为保持的联合成功率？ | 同一任务安全与功能 oracle 均通过；语义不变量覆盖 | 无安全 oracle 时只报告语法与已覆盖功能，不能计为 verified |
| 统一效率 | 在可比质量与预算下，需要多少时间、调用与 token？ | 实际墙钟、分阶段时间、失败耗时、token/调用、质量—成本曲线 | 提速若伴随质量下降，作为权衡报告，不称无损加速 |

本阶段先判断三条链路的实用效果，再决定值得深入的研究机制。所有目标数量是准备目标，不是可用任务数或已经获得的成绩。

## 2. 首轮到扩展轮的执行顺序

### P0：冻结身份与清理输入（E00–E01）

- 固定当前工作树内容摘要，包括未提交的代码/配置模板；明确排除密钥、上传数据和运行产物。记录模型、提示、图流程、CLI、pack、RAG 文档/范例/索引身份与依赖版本。
- 沿用已配置的模型及 embedding，记录真实返回的模型身份；不把密钥写入配置产物。不默认模型支持 seed 或确定性。
- 核对生产 suite 的实际解析路径。旧 `real_pair_baseline.py` 写死 `security-extended`，需要适配，不能直接当成当前标准基线运行。
- 审计旧 18 次规则任务、旧真实项目 pilot、8 个小 oracle、生产 RAG 和本轮候选的仓库/根因/代码重叠。
- 模型输入只导出字段白名单；发现只给源码，规则给源码+漏洞描述+检索，修复给源码+最终审计报告+语义证据。
- 黄金修复、隐藏测试、答案注释和 trace 保留在评测器侧。去标签转换保存差异和哈希，禁止改变原业务行为。

门槛 G0：存在运行配置身份、暴露清单、去标签输入和隔离检查收据。无法确认历史暴露的条目降为开发/案例研究，不声称全新隐藏测试。

### P1：校准任务与实现评测入口（E02–E03）

- 先校准 [首批项目](first-batch.md)，记录根因、合法行为、目标负例与评分范围。
- 修复候选检查原版与官方修复版：正常测试应都通过，目标安全测试应原版失败、官方修复通过。测试本身报错不等于暴露漏洞。
- 分类纯单元、独立环境、服务集成任务；本阶段只纳入纯单元可验证任务。服务型任务保留缺口记录。
- 建立统一 runner 与结果契约，复用平台适配器，替换旧脚本的选样和行号评分。实现输入隔离、失败状态、暂停恢复和隐藏评分器。
- 先做不调用模型的协议测试，再做每链路最多两个开发任务的真实工具/模型接入 smoke。

门槛 G1：每个接纳任务有可核对的根因与评分方法；修复 verified 主榜还必须有已校准双 oracle。没有合格修复任务时暂停该主榜，继续其他主线并报告原因。

### P2：确定性基线与小批校准（E04–E06）

- 对冻结的发现输入跑相同 suite 的 CodeQL；保留数据库提取失败、SARIF、pack 身份和时序。
- Bandit 作为 Python 轻量对照；Semgrep CE 先固定引擎及有明确许可的规则列表，再作为第二层竞品加入。
- 开发集每链路选两个可运行任务，每配置先跑一次，检验输入覆盖、反馈隔离、预算与输出字段，不做优势宣称。
- pilot 前已划定开发组和禁止访问的隐藏候选；pilot 后只允许按开发结果修正实现。正式任务、生成配置、评分与排除理由最终冻结后才能开始隐藏运行。
- 第一批隐藏任务较少，只形成探索性结果；扩展到跨仓库 10–20 个合格任务的目标由可得性决定，不靠重复调用补足样本数。

门槛 G2：基线状态齐全、接入检查通过、正式清单与配置哈希已冻结。新实现/新提示创建新的实验版本，不覆盖上一版结果。

### P3：双引擎发现（E07）

四组：D0 CodeQL；D1 独立 Agent；D2 两者合并去重但不复审；D3 两者合并后取证复审。

- D1 与 CodeQL 并发且不可读取 CodeQL 候选，验证真正独立发现；D3 才可读取两路结果。
- 主因果对照采用同一轮保存的候选池，比较去重与复审的差异；完整双链路的端到端墙钟另实跑，不能用分支之和推算。
- 静态基线无随机种子；含模型组正式运行每任务 3 次。记录 seed 支持情况，不支持时按独立请求重复，不能保证独立随机性。
- 根因匹配由源码、入口、危险操作和必要条件决定，不只匹配文件行号；多个入口去重计一个根因。
- 复审 rejected / confirmed / unresolved 分别评分。未覆盖代码和未决判断不能等同于安全。
- 合并后报告 CodeQL 特有、Agent 特有、共同 TP，以及被复审误删的 TP。盲审未匹配告警，披露待裁决与复核者身份。

可选扩展：VulnGym 证据路径评测、SastBench 告警真假过滤；与从零发现主表分开。阿里 Open Code Review 先检查版本/支持语言/源码预算，完成适配后再加入，不搬用作者成绩。

### P4：检索与规则生成（E08–E09）

先跑检索评价，再跑生成，两个问题独立给结论。

- 检索：同一冻结语料及资料相关性标注，对比 BM25、向量、混合。知识与范例分别标注；报告 Recall@k、nDCG@k、MRR、版本/API 适配与重复率。
- 未标注的相关资料不能默认“不相关”；初期构建三组结果的候选池，再复核相关性，披露标注覆盖率与偏差。
- 生成主对照：R0 无检索、R1 BM25、R2 向量、R3 混合；同一源码读取、受限规格、反馈循环、生成预算。
- 有审核资源时再增加固定人工选取资料组，作为相关性参考；不把隐藏标签注入资料。
- 机制消融第二批开展：去知识库、去范例库、去源码取证、去开发执行反馈。先主对照，避免一次形成不可解释的大矩阵。
- 第一批每任务每主对照 3 次；编译失败、执行失败、空结果、命中根因、隐藏负例误报分项报告。
- 任务选样覆盖两类：基线漏检的增益任务、基线已覆盖的再现/回归任务。若前者不足，直接报告不足，不能硬称扩展能力。
- 规则开发样例可以反馈，隐藏原版/同根因修复版/新仓库/安全变体只能评测器读取。禁止硬编码文件、行号、case ID。

保留 Py/JS 衍生任务身份与上游引用。QLCoder、IRIS、CQLLM 当前作方法依据；没有完整同语言适配就不列作已实跑竞品。

### P5：语义辅助修复（E10）

先做固定正确漏洞描述的修复，分离发现能力；再接平台最终审计结果做端到端修复。

- F0 无额外语义取证；F1 项目摘要；F2 项目→模块→修改点的分层语义与源码工具；F3 F2 加失败反馈循环。
- 固定模型和总调用/token/时间/修订预算；F3 只读取允许的开发验证反馈，隐藏测试结果不回流。
- 语义摘要必须对应源码证据，并转换为可验证的返回/异常合同、合法输入、权限、数据与副作用不变量。
- 在独立副本运行已校准纯单元 oracle，补丁只能写候选工作区，不得修改评测测试、依赖和评分器来过关。
- 安全通过且功能通过才计联合成功；静态复扫、语法检查、LLM 互评单列辅助证据。
- 端到端同时报告“全部冻结漏洞任务中的正确修复比例”和“已发现并确认任务中的修复比例”；未发现不能从总分母消失。
- 通过覆盖的测试只能支持这些合同，不能证明没有任何新漏洞；新增扫描告警仍需源码裁决。

第一批每合格任务每组 3 次；双 oracle 合格任务少时只做有边界的案例研究，不提前报告普遍业务语义保持。

### P6：效率与总结（E11–E12）

- 三条链路都记录时序，不到最后才加计时；本阶段汇总冷缓存/暖缓存、检索/编译/扫描/取证/修复的耗时与调用。
- 生产 DB/索引不清空。专用实验缓存记录首次与复用身份、OS 缓存限制、共享产物；组间交错运行，控制并发竞争和网络波动。
- 先质量与成本描述；质量相当的配置才比较加速。优化实验作为新版本，使用开发集调预算，不用隐藏反馈迭代。
- 以仓库/任务组为统计单位，重复请求不能当新项目。报告原始计数、配对差值、组级区间；小样本不强做显著性结论。
- p95 在少量项目下仅作描述并标注样本数；分开端到端真实墙钟、候选池复用成本与后续规则复用成本。
- 成功、失败、超时、unsupported、未决和排除均有数量；报告首次冻结分母和有效评估分母。

门槛 G3：每项结论能回到固定任务、配置、原始结果和评分证据。输出结果报告、失败分类、下一轮改进假设与用户校准清单。

## 3. 预算、扩展与停止条件

- 正式调用量由最终接纳任务数计算：发现 3 个含模型组×3 轮；规则 4 组×3 轮；修复 4 组×3 轮。一次“任务运行”可能包含多次模型请求，另外统计请求与 token。
- E00 记录产品现有默认预算，E05 用开发集核对后冻结具体 token、工具次数、修订次数、超时和每批调用上限；检索 top-k、上下文 token、知识/范例配额与数据读取范围同样固定。数值未冻结不得启动正式组。
- 相同输入失败不无限重试：区分允许的模型修订和基础设施重跑；都保留原尝试，不挑最好结果。
- 小批顺序先跑，完成收据后再扩展。超过预算或出现输入泄漏、评分器被修改、重复结果身份冲突，停止该批并记录原因。
- oracle 不足、源码不可提取、许可证/环境受限都可形成明确未完成报告；不得编造可用率或借旧成绩填新表。

## 4. 交付物

公开版本管理：本计划、任务状态、匿名结果汇总、配置去密钥摘要、选样/排除口径与论文来源。

本地独立保存：冻结任务答案、源码及转换收据、完整候选规则/diff、模型输入输出、SARIF、测试日志、逐运行计时与评分明细。路径与恢复规程见 [runbook](runbook.md)。
