# 当前三模块测试方案 v1

日期：2026-10-11。状态：**历史详细设计，当前执行入口改为[项目完整测试方案](simple-three-module-test-plan.md)**。本文原有小样本安排不作为全量验收标准。本详细设计未执行。分类遵循[功能→测试意图→材料类型](../test-programs/classification-draft-v2.md)，已有成绩查[结果分类表](../test-programs/collected-results-classification.md)。

本轮要分别回答：双引擎能否找到有源码证据的真实缺陷；修复能否消除缺陷并保持正常业务；生成规则能否达到声明用途并经过独立验收。最后检查三模块通过持久化证据、人工确认和版本化产物衔接。

选样人员先冻结来源快照、任务范围和标签；模型只见源码与必要业务合同。金标、参考补丁、隐藏测试及作者答案放evaluator-only，不进入上传包、Prompt、RAG库或日志正文。已评分样例转回归；评分后调参必须换预留集。

新任务准入须同时具备固定源码、语言/工具可运行性、明确评分单位、可核对标签和使用许可边界。修复还须满足“原版正常通过/安全失败、参考补丁正常和安全均通过”。两名独立审核者裁决，分歧留待裁决；无独立人员时标“内部校准”，不宣称正式盲测。

能力门槛建议：NEW-AUD总体P≥80%、R≥70%、F1≥75%，且每语言分别满足；相对同输入CodeQL的F1增加至少5个百分点。必要状态/证据门槛优先于分数。报告95%区间和配对差异，小规模达标仅表示达到内部目标，不宣称统计显著提升。

模型未输出可用判断的正例计入端到端漏检；负例未完成不计为“确认安全”，列未评估。另报已完成任务的指标和全计划完成率，正式评分要求完成率≥95%。阶段错误、缺标签或金标未准入时保持失败/缺口，不通过删样本提高分数；无预测时精确率标未定义。

业务关键正例在回归中不得出现无依据排除；证据不足允许未决，但计入未知/端到端未命中。关闭Scout候选的对照必须保存相同静态输入、Review预算和实际版本，不用历史混合结果替代新配对执行。

能力门槛建议：NEW-FIX的预算内联合通过≥16/20（80%），各语言≥8/10；全部被接受补丁必须通过该任务正常＋安全联合检查，修改范围和证据约束100%满足。固定任务以1个根因计1项，20任务不能因多候选变成60个案例。

每任务最多3个候选，首候选和最多3候选结果同时报告；开发反馈只用可见项目测试/开发检查。最终评分的隐藏检查仅在冻结候选后执行，不把隐藏失败信息回送用于该验收任务继续调分。安全验证、复扫无告警和“业务/安全完全正确”三个结论不能等同。

历史Repair1可作同任务研究对照，但须冻结预算及候选策略；否则只报告不同策略成绩，不做公平排名。普通BugsInPy任务不能代替安全修复，未校准的PatchEval/Vul4Py条目不能进入正式分母。

能力门槛建议：12用途任务全部进入评分；至少10/12编译/开发执行成功，至少9/12独立验收通过，且每用途≥4/6。单个可发布规则必须通过其全部强制正反例；不得用总体75%替失败规则放行。独立集需先核对当前接口能否使用；不支持直接注册时采用外部评测器，外部失败则本次操作者保持草稿、不执行发布；不将外部检查冒充内置发布门。

Python XSS包装返回遗漏列强制回归；首轮基于内部样例，只声明有限机制覆盖。framework_model和扩展策略可另设专题，未完成时不并入两用途平均分。RAG和反馈消融每因素至少12个独立基础需求的同任务配对（按语言/用途分层，P3需补需求），每臂预算一致；独立重复只报告稳定性，不增加独立需求数。

这些入口需已初始化的专用测试数据库和所需服务；在启动前完成隔离配置。模型替身用于契约测试，不能替代S2/S3/S4真实模型。历史chain/supplemental脚本含账号逻辑，列为待适配工具，不直接作为当前端到端命令。

门槛均为本方案提出的内部目标，**未表示当前实现已达到**。冻结后不因结果差而下调门槛；未达标建立改进任务，回归后用另一预留验收批次重新评价。材料不足时可完成P0/P1并报告“能力验收缺口”，不能宣布全部达标。

## 8. 环境、预算和运行控制

| 项目 | 执行规则 |
| --- | --- |
| 运行隔离 | 专用测试数据库、Redis/独立Celery队列、独立API/前端端口与ARTIFACT_ROOT；只清理本轮ID，不删除共享任务/语料。 |
| 环境身份 | 运行时实测OS/架构、Python后端/CodeQL抽取器、Node、CLI/pack/suite、锁文件、镜像ID/digest和数据库迁移；不复制10-09快照冒充当前环境。 |
| 模型身份 | 保存请求别名和实际响应模型、thinking、输出上限、各阶段预算及异常；embedding模型/修订/维度与语料内容指纹单独记录。 |
| 预算设计 | 首轮按源码默认上限24调用/100000 token/300秒每阶段，修复最多3候选；这些是代码默认，不代表本地实际配置。执行前固定生效值，超限保留失败/未完成。 |
| 批次预算 | 先完成Py/JS各一条smoke，按manifest的阶段数计算全批调用/token上界再冻结；不靠缩减上下文临时平衡成本。 |
| 公平比较 | 同源码、任务、输出/候选预算与工具配置，交替执行模型对照，性能任务不并发干扰；静态分支无模型预算，记录实际工具资源。 |
| 重试和恢复 | 技术重试保留旧失败并关联新执行；恢复校验实现/输入/配置未变。变更后开新run，不能直接接续旧10-09 checkpoint冒充同版本链路。 |
| 验证容器 | 按现有验证器无网络、非root、资源受限，输入只读、修改在副本；不将上传项目源码或密钥提交Git。 |

所有步骤先校准后运行，准备失败不继续依赖步骤。每阶段留存开始/结束、实际预算、独立ID和终态；缺运行收据保持未评估，不依据页面截图或文件存在推断成功。

## 9. 结果记录与按改进版本归档

建议本轮campaign前缀 `three-module-20261011`，实际执行生成唯一run_id。分开 `regression`、`new-acceptance`、`workflow`、`ablation` 四类用途目录，但一级功能仍只有三类。

每条记录保存：功能、意图ID、材料类型、material/task ID、暴露/准入状态、计分单位、项目改进归属、Git及未提交内容哈希、当次阶段/Prompt、环境/语料、原run/stage ID、成功/失败/unknown/未评估、引用产物和实际调用。

同一次对照记录多个实际实现；“报告归属本轮改进”不等于“所有对照臂用本轮代码”。模型意见、操作者确认、独立人工金标三种身份分开。重复运行和历史复用有来源标识，不重复累计独立样本或费用。

执行后依照[归档规约](README.md)创建新的不可覆盖归档，关联归档ID＋RES ID＋完整SHA-256＋历史版本收据。旧workspace-v1/v2/v3和旧分数保持原样；缺实际版本/环境证据保留未知。

最终报告必须分别给出：各模块是否达到工程门槛、是否达到能力门槛、两语言链路状态、失败与待测清单、与同输入基线的差异、适用范围和版本可追溯性。不得以“所有普通测试通过”代替三个模块能力验收。
